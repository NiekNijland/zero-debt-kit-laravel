# Guards, ratchets, dashboard

The guards need one pattern too, or agents copy whichever guard style they see first. Each kind of rule gets one mechanism.

## C1. One mechanism per kind of rule

The last column is the worked example: the strict Laravel starter (`reference-project/README.md`; `reference-project/files-to-copy.md` lists its paths), a running application. A name the starter does not have is in `reference-project/examples/` (an example that does not run) or in `docs/starter-variants.md`.

Rules for writing a guard:

- **The failure message names the replacement** and, only where the guard knows the guide, the guide that holds the example. The reference guards all name the replacement; a guard that does not know a guide cannot name one, and the example is then found through the one-pattern table. A guard that can also name the example file does so.
- **A guard is a detector class plus a thin test with three parts**: inline examples that must fail (each with the words the message must contain), inline examples that must pass (the accepted spellings and the near misses), and one case over the real tree. The examples are the guard's own test: a detector that goes blind fails them. Example, in the starter: `tests/Unit/UniqueJobArchitectureTest.php` with `tests/Support/Architecture/UniqueJobGuard.php`.
- **A guard test file is a test file that names a class of the guard support folder.** The contract test and the guard over the guard folder find the guard tests that way, never by file name.
- **The detector is plain code; only the thin test knows the test framework.** In PHP: with Pest, a dataset of the failing examples and one real-tree case, in the group `arch`; with PHPUnit, a test class with a data provider of the same failing examples, one real-tree test method, and `#[Group('arch')]`. A shape rule that Pest writes with its `arch()` helper is, in PHPUnit, the same detector-class form; no architecture package is used. The starter is the Pest worked example: a PHPUnit project copies the detector class unchanged and rewrites only the thin test. The exception is the five detectors whose subject is the test syntax itself, all under `tests/Support/Architecture/` of the starter: `BannedTestCallGuard.php`, `TestAssertionGuard.php`, `TestHelperFunctionGuard.php`, `TestTierGuard.php` and `PestBindingReader.php`. They read Pest's functions; a PHPUnit project rewrites them for PHPUnit's forms, with the PHPUnit column of "One spelling in a test" (`catalog/tests-database-ci-docs.md`) as their failing examples.
- **List the other spellings of the construct before you write the detector, and give each a failing example.** The same thing can be written through inheritance (a parent class that already implements the interface), a sub-interface (a contract that extends the one you look for), the function form and the method form of one call, an alias, a group import, a fully qualified name, a facade and the class behind it, a modifier between keywords. The accepted examples hold the near misses too: a function with the same name from another namespace, the same method on another class. A guard whose examples hold only the spelling its author thought of is blind to the others, and only a reviewer finds that.
- **A sentence that claims a check matches what the guard does.** Write the rule in the guides from the guard's failing examples, not from the intent. What the guard cannot decide stays a review item and is written that way ("review checks that, the guard does not"); the rubric lists it in its review-only column.
- **No exception list.** During the burn-down the counted list of C5 is the only list: one file, a "no new" test, a "no stale" test (an entry that is fixed fails until removed), and a ratchet row so it cannot grow. At zero the list file is deleted (`06-lock-and-audit.md` E1).
- **No literal path.** Find files by reflection or directory scan; a guard that needs a table of folders (the layout guard) reads it from the document that holds the table. A literal path in a detector is itself an exception entry: the guard over the guard folder fails it (`catalog/tests-database-ci-docs.md`, "Guard shape"). The same guard holds the three parts of every guard test.
- **A list that cannot be emptied is a permanent exception**: when every entry of a counted list is a member of one category (URLs that have no route name, such as a probe of a removed route, a route a test registers itself, a health check), the guard gets the category, with failing examples for the near misses, and the list is emptied. The row counts lines of a list, not findings, so a count column cannot be summed by it.
- **A banned call that tests need once** (`unserialize` for a payload round trip) is allowed in one counted place, a test support class, as a counted allowed path of the banned-call rule: not a baseline line per payload test, and not a detour through a framework class to avoid the baseline.
- A register is not an exception list: it names every member, the guard fails in both directions, and an entry is added with the class, not to get a build green.
- A rule about append-only history (a migration that has run in production cannot be rewritten) holds from one file on: one constant in the guard that names the first file under the rule, never a list of exempt files, and the constant never moves forward. Example, in the starter: `tests/Support/Architecture/MigrationShapeGuard.php`.
- A guard filters on the path relative to the repository root, and its test has a case for a checkout that sits under a dot directory.
- A banned call that one layer owns (an HTTP library inside the client classes) is configured per layer. A global ban gives hundreds of errors and no way to converge.
- A guard that reads source code goes through the shared reader, so there is one parser, not twelve regexes. The reader is ONE family of classes, shipped in `tests/Support/Architecture/` of the starter (`PhpSource`, `PhpFileInspector`, `PhpCallReader`, `ClassGraph`, `TypedReceivers`; `reference-project/files-to-copy.md`), with the counted list as an example that does not run (`reference-project/examples/php/tests/Support/Architecture/CountedList.php`): the parser and visitor entry, the call reader, the declaration reader and the counted list. A builder depends on it and extends it in place when a question is missing; a guard that parses, resolves names or reads a list by itself is a finding (parallel builders that each wrote their own reader cost three renamed classes and a codemod in a first run). A guard over files it cannot find in the examples (the guides, the test tree) takes the root as an argument, and its examples build a small tree in a temporary folder (`tests/Support/SourceSandbox.php` of the starter).
- Every pure guard runs in the fast checks step, not in the long test step. The contract test over the CI files asserts that every guard test file runs in a step.
- **A detector with more than three rule groups is built as several classes from the start** (a guard file over the size limit is its own debt). Guards share one reader of the tree: the first commit of step 3 lands it (parsed file, call reader, lineage, counted list, sandbox) and nothing else, and no guard branch starts before that commit is in the integration branch: every builder branches from it, or three guards carry three readers.
- **Select the subject of a shape guard by the folder name and by lineage**, not by namespace: a namespace changes at the first move of step 5, a folder kind (`Actions`, `Controllers`, `Dto`) and what the class extends or implements, resolved through the project's own parents, interfaces and traits, do not. A folder name that means two layers (a top-level support folder and a module's support folder) is selected with its depth, and the guide row says so.
- **A list inside the guard is an exception list in disguise** (a verb list, a table of folders, a set of allowed names): it lives in a table of the guide that the guard reads, and the test extracts it from the guide and pins it (the parsed areas, module names and verbs, so a new row cannot weaken the guard silently). A table reader ends a table at a blank line, not only at a heading.
- **Every guide sentence a guard reads is pinned by the test**: the test fails a weakened guide as well as a weakened guard. The standard shape is the rules guard of the table above: one table, two directions.
- **Prefer a static reader to a booted application** for a guard (route files read through their groups, not the route list): the unit tier may not boot the application, and a feature test may not carry the guard group. A rule that needs the booted table takes it as an argument (the named-route row of the table).
- **A hand-written guard passes the project's own checks** (analyser at its top level, the refactoring tool, the formatter, the lint limits) before the first push, like any file; the project's narrowing helpers are known to the author from the brief. A guard's examples are counted by the ratchet rows too: write them so no banned spelling stands in them literally (split the literal, or use a near-miss spelling: the operator of a GitHub expression is built from two string parts, the slashes of a comment inside a string that holds example source are built the same way, since the rows read text and cannot tell it from code, and the multibyte string functions are written for a path), and run `ci-ratchets.sh` against the PR's base before the first push, not only the guard group. The same holds for prose: the row `comments` counts every docblock line that is not a tag, so a guard copied from the reference carries no prose (the reference's own guards carry the tags `@param`, `@return` and `@var` and nothing else, and the prose of its README is for the reader of the kit); a project's guards say what they need in names and in the thin test.
- **A rule about something that does not exist yet** (a queue enum nobody has made) is built and proved on examples and listed in the PR as "not exercised by the real tree". Two cases of it that a first project met:
  - A shape rule written with Pest's `arch()` over a namespace that holds no class (`App\Modules\*\Exceptions` before any module has an exception) throws `DirectoryNotFoundException` instead of passing, and `arch()` has no example form to prove it on. Such a rule is added in the PR of the first class of that folder; until then the names of the folder are held by the layout guard (the Name column of the layout table), and a rule of a kind that will exist is a guard class with examples (the detector reads the folders that exist and passes over a module without that folder). A glob over folders of which some may be absent is read as the union of the ones that exist; a glob that matches none of them is an error for a rule whose folder the project has, so a rename is not an empty pass.
  - A guard whose subject is a list the application may have none of yet (the schedule of `routes/console.php`) passes on an empty list when the file exists, and fails when the file is missing. "Nothing was read" is an error for a missing file, not for an empty schedule: no task is invented to give the real-tree case something to read, and the guard's examples carry the proof until the first task exists.
- **Proof without a test run.** Where the verification policy forbids local test runs, prove each guard with a throwaway runner: a script that stubs the test framework's functions, loads the real detector, and runs every case of the guard test against the inline examples and the real tree. The runner is not committed. It proves the detector, not the wiring (paths, groups, autoloading): the first pipeline run is still the first test run.

**The standing blind-side list.** Every detector starts from these; each spelling gets a failing example, and each near miss a passing one. In a measured run, about ninety scratch spellings produced seven blind sides in two guards, and the same ones came back in every review.

| Kind of guard | Spellings and traps |
| --- | --- |
| Any guard that compares names | the facade by its global alias (`\DB::`, a bare `Route::get()` in a route file with no `use`: map a single-segment name through the framework's own alias table, not a copy of it) and with a leading backslash; an alias import; a group import; a fully qualified name; a trait as well as a class; a nullable or union type; an alias variable of a parameter; `self::` and `static::` (the name resolver leaves them; map them by hand wherever constants are followed); a name that is only a function name (`app`, `config`) collides with a folder name: pass it as a class constant or list it as a known blind spot in the guide sentence |
| Class relations | a parent that already implements the interface; a sub-interface; an interface the framework returns where the rule names the class (list the methods of both); a vendor parent (resolve through the autoloader, and keep the parsed tree for the project's own classes so sandbox tests work); a hand-copied method list of a framework class goes stale at every update: write `Class::*()` with an exclude for the allowed methods, and let the test read the methods by reflection |
| Call forms | the function form and the method form; a chain on `$this` or `test()` and the imported function; a closure in a variable or an array; state kept in a property (`$listen`); a pending object held in a variable or an injected factory. Count the real tree for each spelling before calling the list complete: a missed form can be the majority of the sites |
| An expression read for one shape | the wrappers a migration produces: `->value`, `??`, a ternary, `match`; each gets a failing example and a near miss |
| A guard over an analyser's report | never prefill the result for every example path: a passing example the tool could not process (a non-empty `errors`) must fail; the sandbox refuses a duplicate path; a rule's keyword forms (`goto`, `global`) are reported as "Using ...", not "Calling ..."; a static call is a different list from a method call (a rule put in the wrong list never fires and nothing says so: the failing example shows it); a wildcard rule appends text to the message, so the baseline lines of its sites change and need the tag `[ratchet: analyser-baseline]` |
| A guard over the guides | an HTML `<code>` span; a link target; an image; a `:line` suffix; trailing punctuation; a command span; a fenced and an indented block; case; an untracked file that exists on disk; a glob or folder in a baseline; "lands with" outside the Copy column |
| A guard over guards | `describe()`; a file-level group; an alias; `sprintf`; `DIRECTORY_SEPARATOR`; `__DIR__ . '/..'`; a message that names a path (pass the path in); a group name inside a data-set string; a real-tree test contains the root call itself (`dirname(__DIR__, 2)`), so shared state takes the root as an argument |
| A frontend layer rule without a TypeScript parser | the rule read from the guide table and applied to import statements by pattern, with the blind spot named (an import through a variable); a TypeScript reader in the guard folder removes it. A page rule skips test files (a page test imports its own page: give it a fixture), and the file-name rule accepts the split-test name the catalog recommends (`<file>-<topic>.test.tsx`) |
| A rule about files | a test location rule is about two trees (the classes and the tests): state which reading the guard checks; select "a model" by its ancestor (model, user, pivot), not by the folder `Models` (casts and scopes live there too); a rule that needs the application's classes next to the tests takes the list as an argument |
| Before the PR is opened | grep the tree for the common spelling of the thing the rule bans: a list of a handful for a habit that appears hundreds of times means the guard is blind |

**A guard's own review** is by an agent that did not write it, with this list and the guard's examples only; the findings of that review are the kit's measure of the list. Human review of the pull request then reads commit by commit.

## C2. The ratchet script

`tools/ci-ratchets.sh` compares counters between the merge base and the head of a PR. It is the missing half of every list: a "no new offenders" test passes when someone adds their violation to the list; the ratchet fails that. How it works, its methods, its config block and how it treats new, redefined and removed rows are in `tools/README.md`. The rules the program relies on:

- A `max` row only goes down, a `min` row only up. The merge base is counted with the base's own definition of the row, so a changed regex or path cannot hide growth.
- A wrong-way move fails, unless a commit that touches one of the row's files carries `[ratchet: <name>] <reason>`. A `max` row at 0 accepts no override, except the rows named in `OVERRIDE_AT_ZERO` in the config block of the ratchet script (default `comments,cap-dependencies-majors-behind,cap-dependencies-abandoned,audit-exceptions`: a justified comment, a pinned major, a dated audit exception; each is a decision that a reviewer reads): this is the one place that says so. This includes a cap at 0: it is never raised, so new debt of that kind is fixed, not capped. A row is added to `OVERRIDE_AT_ZERO` only with a decision row and the script tag. The reviewer reads the reason of every override (rubric item 6).
- A row that is new in a PR passes: that is how a guard arrives together with its counted list. From the next PR on it is enforced.
- A row that is removed fails, unless it was a `max` row at 0 on the base or the commit that removes it carries `[ratchet: <name>] <reason>`. The PR that empties a list and deletes it with its row therefore carries that tag (`06-lock-and-audit.md` E1).
- The source, test and frontend folders of the config block cover every tracked source file: the run fails on a source file outside them, and the dashboard shows their count as the row `files-outside-row-paths`. A folder that is deliberately not counted is named in `UNCOUNTED_PATHS`; the step audit reads that list (`09-reviewer-brief.md`, auditor item 1).
- **The scripts and the pipeline are guarded.** This is the one place that states the rule; other files point here. A change to the ratchet script outside its table, a move of it, and any change to a file in `GUARDED_FILES` fails the run, unless a commit that touches that file carries `[ratchet: script] <reason>`. `GUARDED_FILES` holds the other scripts in `scripts/`, the shared `kit-config.sh` among them, and the pipeline files of the three hosts. So an edit to a pipeline file needs the tag, and so does a new `COMMAND_ROWS` or `ROW_ADVICE` line, a new entry in `SHRINK_ONLY`, a changed `ANALYSER_SWITCHES_TARGET` or a changed `DASHBOARD_MODE`. A file is guarded from the moment it is on the base: in the PR that installs the tools the scripts are new and need no tag, and a pipeline file that already exists does. Adding a row to the table needs no tag; a lowered cap needs none; a raised cap needs its own row's tag, `[ratchet: cap-<key>] <reason>`. Only the lead makes a tagged change, and the reviewer reads each one line by line (rubric item 2).
- **A PR that edits the ratchet script.** The script that runs is the pull request's own, so a PR that makes it exit early passes its own run. `scripts/checks.sh` therefore first runs the base's copy of the script with `--guard <path>`, which sees the edit and fails it without the tag. A PR that edits both `scripts/checks.sh` and the ratchet script has to pass the reviewer.
- **The tag is written by the author, so a person reviews the files that carry it.** The override tag sits in a commit message that the author of the pull request writes; nothing in the pipeline can tell a tag with a real reason from one written to get past a guard. The guarded files (`scripts/`, the caps file, `kit-config.sh`, the pipeline files, the guard folder) and the code-owners file itself are covered by a code-owners rule that names a person or a team, and the host requires the owner's review on the main branch and on every other deploying branch (GitHub: branch protection "Require review from Code Owners", no bypass; GitLab: "Require approval from code owners"; Bitbucket: default reviewers and the merge checks). `ci/CODEOWNERS.example` is the file; C4, point 22 is the test, and `07-process.md` section 12 is the process. The setting itself is not in the repository: the owner sets it and confirms it. Where the host cannot enforce it (a private GitHub repository on a free plan: the API answers 403 "Upgrade to GitHub Pro"), the file stays, the contract test reads it, and the profile says in plain words what is then not enforced: the unenforced mode of C4, point 22.
- **`--self-test`.** `bash scripts/ci-ratchets.sh --self-test` runs every regex row against a fixture of the spellings it must count and the near misses it must not (224 cases in the script now), in a scratch repository. It fails when an expression stops counting a spelling, which is what a renamed or removed rule looks like from the outside. The `gate` part of `scripts/checks.sh` runs it next to the ratchets (`tools/README.md`, "What a run checks", point 5). A row with a new or changed expression gets its cases in the same commit.
- Rows that grep source or test folders exclude `*.md` (`:(exclude)*.md`): a guide that quotes a banned call must not raise a row.
- **Fix forward**: a revert cannot pass (`07-process.md` section 5).
- A baseline is counted per entry, and three counting methods execute code from the pull request: `tools/README.md`, "Adding a row" and "The table".

Start set of rows, with these 23 names in every project:

`analyser-baseline`, `analyser-ignore`, `analyser-level`, `analyser-switches`, `refactor-skip`, `refactor-sets`, `formatter-rules`, `advisory-block`, `audit-ignore`, `audit-exceptions`, `test-skip`, `test-doubles`, `event-fake-all`, `lint-disable`, `lint-config-off`, `lint-config-ignores`, `lint-baseline`, `type-baseline`, `ts-suppressions`, `frontend-test-skip`, `comments`, `todo`, `ci-skipped-steps`, and one `cap-<key>` per key of the caps file.

What each row counts, and what it cannot see: `tools/README.md`, "The rows that ship". Four are `min` rows: `analyser-switches`, whose target is `ANALYSER_SWITCHES_TARGET`, and `refactor-sets`, `formatter-rules` and `advisory-block`, whose targets are in `MIN_ROW_TARGETS` (C3).

A row whose subject the stack lacks stays, with its config value empty: it counts 0. Add one row per list step 1 found (an allowlist file, an exemption call inside a test, an excluded path); the project names those. Rows the project adds under a fixed name (`tools/README.md`, "Adding a row"): `coverage-floor`, `frontend-coverage-floor` and `mutation-floor`, each a `min` row with the method `number` over the committed threshold; `frontend-logic-coverage-floor`, a `min` row over the 95 threshold of the frontend's logic folders; `strict-types-missing`, a `max` row over the PHP files without the strict-types line (`05-program.md` D2, step 2); `loose-comparisons`, `mutable-dates` and `byte-string-functions`, the `max` rows that count the sites of a formatter rule before it goes on (`templates/tool-configs.md`, "Rules that can change behavior"); `queue-bus-fake-all`, a `max` row over bare queue and bus fakes in the tests (`catalog/tests-database-ci-docs.md`, "Fake events and queues"); `model-strictness-violations`, a `max` row over the counted list of step 4; `guide-future-tense`, a `max` row over the guides, from step 3; `cap-autoload-conformance`, the cap row of the caps key `autoload-conformance`: the dashboard counts the classes whose namespace and name do not match their path under the PSR-4 roots (tests, factories and seeders included) with a command that counts the "psr-4" lines of `composer dump-autoload -o` (`tools/README.md`, "Adding a row", point 10), from step 2 (a class declared in a namespace block of a test support file, as native-function shadows tend to do, is skipped by the autoloader and logged, never failed: keep the shadow functions in the namespace block and the state or fault holders as ordinary classes under the tests namespace); `unused-ignore`, a `max` row over the ignore list of the unused-code tool; and `cap-ci-duration-minutes`. Each of these has its cases in `--self-test`.

The ratchet is installed in step 2, in the same PR as the baselines it counts. Where it runs in the checks step: C4.

## C3. The dashboard

`tools/debt-dashboard.sh` prints every counter with its target. It is the single source for the plan's numbers. The PR template asks "which counter does this change, and by how much?", answered by running it. Flags, modes and the rows it ships with are in `tools/README.md`. A counter of the project's own is a row the project adds (`tools/README.md`, "Adding a row").

**The dashboard is a gate.** A dashboard nobody has to pass is a report, and its rows reopen. It runs in CI as a blocking step right after the ratchets: in its default mode from step 2, and with `--final` as the exit of step 10 and from then on (`tools/README.md`, "Modes"). So a fresh baseline of thousands is green from the first day, and it cannot grow. A row that is `OPEN` prints one line of "do this" under it: the failure names what brings the row to its target.

Rules for the blocking run:

- `--offline` skips every row that needs a package registry, full git history or today's date. A CI clone can be shallow and a registry can be down; neither may fail a pull request. A row that depends on the calendar (`docs-older-than-limit`) turns red with no code change, so it is never in a pull request's run. On a shallow clone the row is skipped in the gate with the reason printed, and is `UNKNOWN` (a failure) in `--final`: the age of a doc needs the full history, and a scheduled run that cannot read it must not pass.
- **The skipped rows still gate**: the scheduled job of the pipeline runs the full dashboard once a day (`bash scripts/checks.sh --scheduled`), and a red scheduled run is fixed before the next program PR opens; after the program closes, by the repository's maintainer (`06-lock-and-audit.md` E3). The lead also runs it at the end of every step (`05-program.md` D4).
- **An advisory or an abandoned package with no fixed release yet does not stop the program.** The lead writes a decision row (the advisory id, why the code path is not reachable or what mitigates it, the upstream issue), and the package is removed, replaced or patched in a PR of its own as soon as that is possible. Until then the row is red in the scheduled run only, the decision row answers "fixed before the next program PR opens" and the green scheduled run of step 10, and the backlog holds it as an open loop whose "start when" signal is the fixed release. No ignore entry and no cap is added for it. What keeps the pull request pipelines green in the meantime is a time-boxed exception: one line in `scripts/audit-exceptions.json` (advisory id, reason, `added`, `expires` at most 7 days later), added in a commit that carries `[ratchet: audit-exceptions] <advisory id>` because the row `audit-exceptions` counts the lines. The gate fails the audit from the end date on, and the line is deleted with the fix; it is never renewed: an id that comes back in a later diff is a renewal, and the reviewer reads it as a ratchet override (rubric item 1). Exceptions are for advisories only, never for an abandoned package (a cap in the dashboard covers that). The dashboard row `dependency-advisories` and the pipeline's `Audit` task run the same command, so the two numbers agree (`tools/README.md`, "`audit-gate.sh`").
- **One row is shown and never fails**: `dependencies-behind`, the packages a minor or patch version behind. It moves with every upstream release, and the updates are the dependency bot's work. A major behind, an advisory, an abandoned package and a doc past the age limit do gate.
- **`--final` holds `analyser-switches` to `ANALYSER_SWITCHES_TARGET`**: the switches the catalog names, added up over the configs that hold them.
- **`--final` holds every other `min` row with an end goal to its number in `MIN_ROW_TARGETS`**, in the config block of the dashboard script: `coverage-floor` and `frontend-logic-coverage-floor` at 95, `refactor-sets` at 18, `formatter-rules` at 21, `advisory-block` at 1. The numbers are the kit's, not the project's. A name in the list that has no ratchet row fails `--final` too, so the row cannot be dropped to pass; a project without the subject of a row (no frontend, no PHP) removes the entry, with the script tag. A project that has the subject in part sets the entry to the number it can reach, with the script tag and a decision row: where the organisation hosts the formatter config (the owner's exception of step 1), `formatter-rules` is held at the number of rules the hosted config has, and the decision row names each missing rule. The dashboard prints a number below the kit's in every run. In the gate the row is held by the ratchet and shows its goal.
- `--details` in CI, so a red row names the files.
- **Caps.** A dashboard row that cannot be at zero yet gets a cap that only goes down. The caps live in one JSON file, `debt-caps.json`, one key per row, never as a number inside a script: a number in a script is changed in the same diff as everything else and nobody sees it. Each key has its own ratchet row `cap-<key>`; there is no row over the sum, because a sum lets one cap rise by what another falls. While a cap is above 0, the override tag `[ratchet: cap-<key>] <reason>` is the only way up, and "new code without its test" is not a reason. A cap that reaches 0 stays in the file, at 0, and from then on it is not raised: only `cap-dependencies-majors-behind` takes an override at 0 (`OVERRIDE_AT_ZERO`, C2).
- **A cap follows its row down.** The lead lowers every cap to the measured value of its row at the end of every step (`05-program.md` D4, point 2), and `--final` fails a cap that is above its row. Without that a row at 10 under a cap of 50 can grow to 50.
- A cap that cannot reach 0: `01-principles.md`, "Shrink-only rows".
- In step 2 every row that is not at zero and has no ratchet row gets its measured value as its cap.

## C4. CI shape

This section holds the rules of the pipeline: its runs, the order of the checks step, the contract test that keeps it honest, and the reasons that are not obvious. The rules a ratchet row or a step of its own holds are the table "CI and dependencies" of `catalog/tests-database-ci-docs.md`.

**The skeletons.** `ci/` holds one per host (Bitbucket, GitHub Actions, GitLab). Each fetches the full history in the runs that compare with a base or read history (checks, the scheduled run, and the test run, for the mutation run of step 9), hands the base branch to the scripts as `CHECK_BASE` (and the head as `CHECK_HEAD` only where the job checks out the branch as it is, which is GitLab: Bitbucket and GitHub merge the base in first, so HEAD is that merge and `CHECK_HEAD` stays unset), pins the image the jobs run in (by digest; on GitHub a `container:` with the digest, the runner label only names the machine; or the runner form, `ci/github-actions-runner.yml`, where the jobs set up PHP and Node with actions pinned by sha and there is no image), gives every step a maximum time, and has these runs:

| Run | When | What |
| --- | --- | --- |
| checks | every pull request, no path filter | `bash scripts/checks.sh --part <name>`, one pipeline step per part of `PARTS` in `scripts/checks.sh` (together they are `bash scripts/checks.sh`) |
| checks on a deploying branch | every push to the main branch, and to every other branch that deploys | `bash scripts/checks.sh --main --part <name>` per part; `--main` has no base to compare with, so the script guard, the ratchets, the commit-message check and the secret scan are left out |
| tests | every pull request and every push to a deploying branch | the backend and frontend suites with coverage held at the committed floor (`tools/README.md`, "Coverage"); from step 9 on, on a pull request also the mutation run on the files it changes |
| smoke | every pull request and every push to a deploying branch; where the main-branch pipeline is the deploy pipeline, the smoke step sits in front of the deploy step | the smoke suite against a stack booted with seeded data and the production drivers |
| scheduled | once a day | `bash scripts/checks.sh --scheduled` (the full dashboard, with `--final` from step 10 on) and the mutation run over the whole tree |

"The main branch" in the rows means every branch that deploys: when a branch ahead of the main line deploys the test environment, the checks, tests and smoke run on both. An existing pipeline is never overwritten (`05-program.md` D2, step 2). On Bitbucket and GitLab its file takes the skeleton's steps and jobs, because a pipeline is chosen per trigger there. On GitHub the kit's jobs are a file of their own, `.github/workflows/kit-checks.yml`, and the existing workflow is not edited: the `on:` block belongs to the whole file and a job runs on every event of it, so a `pull_request` and a `schedule` trigger added to a workflow with a deploy job would run the deploy, with its secrets, on every pull request and every night. The existing workflow keeps its `push` trigger and its deploy; its own test jobs move into the kit's file (a suite runs once per trigger); a deploy that must wait for the tests is a workflow on `workflow_run` of the kit's workflow (conclusion `success`, event `push`, the deploying branches) or a job of the kit's file with `needs: [checks-main, backend-tests, frontend-tests, smoke]` and `if: github.event_name == 'push'`.

**The image of the GitHub form.** On GitHub every job runs in a `container:`, and nothing in GitHub supplies the image: it is the project's. One image holds the project's PHP with its extensions, Composer, Node and the tools of the run: `bash`, `git` 2.18 or newer (older, or none, and `actions/checkout` falls back to a download without history, so `fetch-depth: 0` does nothing), `curl`, `tar`, `sha256sum`, `ca-certificates`, and `gh` for the scheduled job (which installs a pinned copy when the image has none). It is Debian or Ubuntu based (an Alpine image is a known trouble spot for the runner's own Node: unverified) and runs as root, because the gitleaks install writes to `/usr/local/bin` and the runner mounts its folders into the container (or the container says `options: --user root`). The project builds it in the repository (`ci/ci-image.Dockerfile.example` is a starting point), publishes it to a registry the runner can read, and writes it as `image: <name>@sha256:<digest>`; the digest comes from the registry, never from memory, and the dependency bot moves it. A private image in the GitHub registry needs `permissions: packages: read` and `credentials:` (username `github.actor`, password `secrets.GITHUB_TOKEN`) in every `container:` block; a pull request from a fork gets a read-only token and cannot pull a private image with it (unverified), and the skeleton does not support fork pull requests. For a private repository without forks the question does not exist: GitHub refuses the fork-approval setting there (HTTP 422, observed), so the owner's checklist reads the default workflow permissions (`gh api repos/<owner>/<repo>/actions/permissions/workflow`: they should be `read`) and sets a fork policy only on a public repository. **The runner form** (`ci/github-actions-runner.yml`) is for a project with no image of its own, and is the simpler one: no `container:`, so no Dockerfile, registry, digest or credentials; the toolchain is `shivammathur/setup-php` (version, extensions, Composer, coverage driver) and `actions/setup-node` in each job, pinned by sha; `gh` and `git` are on the runner; a service is reached at `127.0.0.1` on a port it publishes (`ports:`), never by its name; the runner user is not root, so the gitleaks install is `sudo install` (the one observed to fail without it). It gives up the digest-pinned toolchain of point 7: that is an owner exception named in the profile, the baselines are made on the same runner label, and a number that moves without a code change is looked up in the runner image notes. One file per repository, never both forms; the contract test reads either. The container form was not run on a runner; the runner form was, once ("What has run").

**What has run.** The Bitbucket skeleton has run in the pipelines of three Laravel projects, all hosted on Bitbucket. The GitHub Actions skeleton ran once on a real repository (a private repository of a free plan, runner form, the checks matrix with its aggregate job, the three test jobs, a push run on the main branch), and these things were seen: the pull-request run checks out the merge ref, a different commit from the head; the gitleaks download with its checksum passes with `sudo install`; MongoDB and Redis services with `ports:` at `127.0.0.1` reach the smoke suite; a failing part makes the aggregate job fail; the skipped jobs of the other events show as `skipping` and do not fail a run. Not seen: the container form, the schedule firing, the retarget of a stacked pull request, a required check (the plan has no branch protection), and the `edited` trigger (listed in the skeleton; the findings of that run do not show it): treat each as unverified. The GitHub actions the kit's own CI and the skeleton's examples pin are releases that declare `using: node24` (read from their `action.yml`): the earlier pins were `node20` actions, GitHub's changelog says the runners no longer offer Node 20, and what a `node20` action does there is unverified. The GitLab skeleton has not been run at all. The mutation commands for Infection and Stryker are written from the tools' documentation and are unverified (`tools/README.md`, "Mutation").

**The order of the checks step.** This is the one place that states it. The step is one file, `scripts/checks.sh`, copied from `ci/checks.sh`; a developer runs the same file before a push (`scripts/prepush.sh` runs every part side by side), so the result before a push is the result in CI. It is split into **parts**, one pipeline step each: a lone check on four CPUs ran two to three times faster than the same check among thirteen (analyser 302 s contended, 83 s alone), and every part starts at once and every red part is reported in the same run (`fail-fast` is off on purpose: one run shows all four results; a part that must wait for a cheaper one costs wall time and is not the default). The `PARTS` table in the config block names the parts (`gate`: the guard of the ratchet script, the ratchets, the dashboard; `static`; `guards`; `repo`), and the script stops when a task is in no part or in two, and when a part names a task that does not exist, so no check can fall out of a split pipeline. The cost is about 2.7 times the build minutes. A run without `--part` runs everything in the order below.

1. the base's copy of the ratchet script with `--guard` (C2);
2. the ratchets, then their self-test (`bash scripts/ci-ratchets.sh --self-test`, C2), which reads no base and so also runs on a push to the main branch; an upgraded tool that renamed a rule shows up as a failing case as well as a falling `min` row;
3. the dashboard gate (`--offline --details`, with `DASHBOARD_MODE` in front of them);
4. side by side, through `tools/ci-parallel.sh`: the formatter check on the whole tree, the refactoring tool's dry run on the whole tree, static analysis and the type check on the whole tree, type coverage, the linter on the whole tree with zero warnings allowed, the guard tests (the fast guard group, the guard over the guides and the contract test among them), the commit-message check and the secret scan.

The parallel call also ships the refactoring tool's dry run and the type coverage at 100 as lines of their own. The project adds its other whole-tree checks as further lines of that call: syntax lint, dependency audit, manifest validation, the manifest floor (`composer bump --dry-run`), generated-file drift, keyed baselines, unused code, unused packages, build. The script refuses to run while a `<placeholder>` is left in it, in `scripts/kit-config.sh` or in the config block of the commit-message check, and it stops when it cannot fetch the base. Only a part that reads the base fetches it (`gate`, and a part that holds the commit-message check or the secret scan), so a failed fetch cannot fail `static` or `guards`; `scripts/prepush.sh` fetches the base once before the parts start, because four parts that fetch the same ref at the same moment fail with "cannot lock ref" after anyone merged. The secret scan reads the range to `CHECK_HEAD` when it is set, to `HEAD` otherwise; a secret that exists only inside a merge commit is not scanned (the merges of Bitbucket and GitHub add none).

**What the contract test asserts.** One test, in the guard group, over the pipeline file and the scripts in `scripts/`. It exists from step 2. Its detector class reads those files directly: the rule that a guard test reads source only through the shared reader is about source code and does not apply to it. The thin test passes the paths; the detector holds none. It parses the pipeline files with a YAML parser (`symfony/yaml` as a development dependency) and reads the shell scripts as text. The earlier extract held three readers, and the starter ships a GitHub reader of its own form (`docs/starter-variants.md`); the points below are those of the three: Bitbucket (`CiContractGuard`), GitHub (`GithubWorkflowGuard` with `GithubWorkflowRules`, `GithubChecksRules` and `GithubJobRules`: the triggers, the jobs, the matrix, `timeout-minutes`, `uses` with their sha, `fetch-depth`, the services, the concurrency group, the permissions, the default shell, a placeholder or a secret anywhere in the file) and GitLab (`GitlabPipelineGuard`); all three read the parts from the `PARTS` table of the checks script itself (`ChecksParts`), never from a copy, and the GitHub reader flags the kit's own workflow file and any file that holds a kit job (one that runs the checks script), never a pre-existing deploy workflow, which it only counts for point 19 (the owner may name such a file in the `hardenedWorkflows` argument to have its jobs and its hazards read: `pull_request_target`, a `workflow_run` that checks out the pull request, a secret in a file a pull request or the schedule starts); the host's reader is the only part that differs, the points are the same. A YAML 1.1 parser reads the GitHub key `on` as `true`: tell it, or read the key as `true` too. It asserts:

1. the pipeline has the five runs of the table above, each on its trigger, and the checks run has no path filter and no condition besides its trigger (a docs-only PR is the PR that edits the guides); a path filter may sit on a test run only. The scheduled run exists in the host's schedulable form: a `schedule` trigger on GitHub, a custom pipeline named `scheduled` on Bitbucket, a job whose rule is the schedule source on GitLab;
2. every part of `PARTS` (`bash scripts/checks.sh --list-parts`, read by the guard from the table in the script) has a step in the pull-request run, with no condition, whose script holds exactly `bash scripts/checks.sh --part <name>` (and in the main-branch run the same with `--main`); nothing replaces a line of it; the clone of the checks run and of the scheduled run has full history; `CHECK_BASE` is set from the host's variable, and `CHECK_HEAD` only where the job checks out that same revision (never on Bitbucket or GitHub, which merge first). On GitHub the checks run reads `pull_request` with the types `opened`, `synchronize`, `reopened` and `edited` (an `edited` run follows a retarget; a run for an edit of the title is the price), with no `paths` and no `branches` filter (a pull request that targets a parent branch of a stack matches no `branches` list), and its job has no condition besides `github.event_name == 'pull_request'`; the matrix of the job is compared with the parts read from the script, has no key besides `part` (no `exclude`, no `include`), the checks step sets no `shell`, `working-directory` or base of its own, and the checks jobs `need` nothing; a part added to `PARTS` and forgotten in the matrix fails;
3. `scripts/checks.sh` runs its four stages in the order above, the dashboard with `--offline --details`, and holds no `<placeholder>`; neither do `scripts/kit-config.sh` and the pipeline file;
4. every guard test file is in the guard group, and the group's command is a line of `scripts/checks.sh`;
5. every check names the whole tree: no command takes a list of changed files, the linter runs with its zero-warnings flag, the formatter in check mode. The one exception by category is the mutation run of a pull request, whose whole-tree run is in the scheduled job;
6. no command in the pipeline or the scripts writes, commits or pushes, except the steps the profile names as owner exceptions (an autofix commit the owner kept in step 1, passed to the test as an argument); `.git-blame-ignore-revs` exists, and every hash in it is a commit reachable from the head;
7. every image, action and downloaded tool is pinned to a version, a digest or a commit, and none is `latest` or another moving tag; a downloaded binary is checked against its checksum. On GitHub every `uses:` ends in a full commit sha (a local `./` path is exempt; `docker://` needs a digest), the runner label is not `*-latest`, and the job image is pinned by digest; a downloaded binary (a `curl` or `wget` in a run line) needs its `sha256sum -c` in the same job and is never piped into a shell (a call whose every address is local, `127.0.0.1`, `localhost`, `0.0.0.0` or a variable that the workflow's or the job's `env` sets to one of them, is a request to the application under test and no download; an address from a variable that sets none, or from another host, stays a download); a `container:` takes no option besides `--user`, `--cpus`, `--memory` and `--shm-size`. In the runner form (a job with no `container:`) there is no image to pin: the digest is replaced by the setup actions, pinned by sha like every `uses:`, and a job that runs a PHP tool (`composer`, `php`, `pest`, the checks script) must have a `shivammathur/setup-php` step, a job that runs a Node tool (`npm`, `npx`, `node`, the checks script of a project with a frontend) an `actions/setup-node` step: the runner image decides the version otherwise. Each way to get the form wrong has a failing example in the test. The service image is the one exception to the digest rule: it is compared with `DATABASE_IMAGE` as written (point 10), and a bare name with no tag fails. A formatter config that the organisation hosts as a URL is allowed where the profile names that URL (an owner exception, the second argument of the test); a config in the repository is the default;
8. every step has a maximum time (GitHub: an integer `timeout-minutes` on every job, at most the guard's `maxTimeoutMinutes`, 120 by default, since GitHub's own default is 360 minutes; GitLab: `timeout`);
9. no check has a manual trigger; nothing is allowed to fail. The row `ci-skipped-steps` counts the spellings a regular expression can see; it cannot tell a check from a deploy, so the manual trigger is held here;
10. the smoke run boots the production drivers (cache store, queue, database engine), and the database service image of the backend test run, the smoke run and the scheduled job equals `DATABASE_IMAGE` in `scripts/kit-config.sh`, which the lead sets from the profile: the production engine in the production major version. The service must exist in those three jobs (a project without a database passes an empty `DATABASE_IMAGE` and has none), carry the password variable and the health tool of the engine the guard reads from the image name (postgres: `POSTGRES_PASSWORD`, `pg_isready`; mysql: `MYSQL_ROOT_PASSWORD`, `mysqladmin`; mariadb: `MARIADB_ROOT_PASSWORD`, `healthcheck.sh` or `mariadb-admin`), and be the `DB_HOST` of its job (a container job reaches the service by its name; a runner job, with no `container:`, at `127.0.0.1`, and the service publishes a port: the name on a runner, `localhost`, a missing `ports:` and `127.0.0.1` in a container job all fail): the official images exit at start without their variable, and GitHub then fails the job at "Initialize containers" before a step runs. MongoDB (`mongosh`) and Redis (`redis-cli`) need no password variable; a Redis service beside the database (or beside MongoDB as the database) is named to the test as an auxiliary image and read with the same rules, and the variable that holds the database host is an argument (`DB_HOST`; `MONGODB_URI` for MongoDB, read as a URI). The mysql and mariadb pairs are the images' documented values and have not run on a runner; MongoDB and Redis with ports at `127.0.0.1` ran in one project's smoke job. The drivers of the smoke run (cache store, queue) are not read by any guard;
11. installs come from the lock file (`composer install`, `npm ci`, `yarn install --frozen-lockfile`, `pnpm install --frozen-lockfile`; `composer update`, `composer require`, `npm install` and the like in a pipeline line or in `checks.sh` fail);
12. the type-aware lint run has no content cache: a file's result depends on other files, so a per-file cache hides new violations in unchanged files (the analyser's own result cache is kept between builds); an `eslint` line with `--cache` fails;
13. the scheduled run calls `scripts/checks.sh --scheduled` and the whole-tree mutation run; in the weekly variant the mutation step carries `if: github.event.schedule == '<cron>'` for one of the crons of the `schedule` trigger and no other condition (a condition that is never true would switch the run off unseen);
14. the backend test run holds its coverage at the committed floor (PHP: the line `scripts/checks.sh --coverage <report>`, which the GitHub reader requires in `backend-tests`, or as a command of the Composer script behind the backend test command when the job runs that script: the text of the script is the `backendTestScript` argument, which the thin test reads from `composer.json`); from step 9 on, the test run of a pull request calls the mutation tool on the changed files;
15. the analyser config's paths name every folder of `SOURCE_PATHS` and `TEST_PATHS` of the ratchet script that exists (an optional entry such as `lang?` only where the folder exists, so a project that has `lang` lists it and one that has none does not) and the public entry folder; the `bootstrap` entry is met by the two files `bootstrap/app.php` and `bootstrap/providers.php`, never the folder, whose `cache` holds generated files the analyser and the refactoring tool both choke on; and the config includes the bleeding-edge file and each extension by name;
16. (the task runner) the strict-model union check stays wired: the test scripts of the manifest start with the reset, end with the check, exclude its group from the workers and set a finite memory limit, and the check fails when the recorder was never wired (a run with an empty list and no log file looks like a clean run); the command is passed to the guard as an argument, not held in it. The task runner's scripts (PHP: the `scripts` of `composer.json`): the six names of the row "Composer scripts" exist, `test` is `bash scripts/checks.sh`, every command of `test:lint`, `test:types` and `test:type-coverage` is a line of `scripts/checks.sh`, `lint` is called by no CI file, and no event key (`post-update-cmd`, `post-install-cmd` and the like) holds an update or a bump command; the dependency bot's config file exists and holds the keys of the kit's (`templates/tool-configs.md`: `renovate.json`, or `.github/dependabot.yml` with its three ecosystems, the commit-message prefix and the `github-actions` ecosystem that moves the sha pins; no reader implements this point yet);
17. where the project has a frontend source folder, the smoke run installs a browser and its command runs the browser group (the GitHub reader takes the text that command holds as an argument and requires a line with it in `smoke`);
18. every step whose task reads history (the blame-revisions check, the commit-message check, the ratchets, the mutation run on changed files) clones the full history; a shallow clone stops working after a few dozen commits. On GitHub every checkout has `fetch-depth: 0`, `checks-main` and the test jobs included (the guard group reads history, point 6), and none sets `persist-credentials: false` (the checks script fetches the base with the credentials the checkout leaves); GitLab: `GIT_DEPTH` is 0 and no job sets `GIT_STRATEGY: none`;
19. a branch runs each suite once before its deploy: no backend test run twice on one trigger (a pull-request pipeline and a branch pipeline that both match);
20. `DEFAULT_BASE_BRANCH` in `scripts/kit-config.sh` is the branch pull requests target (the answer of 1.1), the same as the pipeline's `CHECK_BASE`;
21. the audit of a deploying branch covers production dependencies only (`npm audit --omit=dev` and the production Composer audit), so an advisory in a development tool with no fix cannot stop a hotfix; the full audit runs on the pull request and in the scheduled job (the safety guard reads `checks.sh`: the `Audit` task of the `--main` run carries a production flag, the one of a pull request does not).

22. the files that carry the guards are covered by a code-owners rule that names an owner: `scripts/` (the ratchet script, the checks script, `kit-config.sh`, the caps file, the floors), the pipeline files (GitHub: the workflow directory), the guard folder and its thin tests, and the code-owners file itself, so a pull request cannot drop its own review by editing it; the last matching rule wins, so a later rule with no owner takes a file out. Why: the override tag `[ratchet: <name>]` is written in a commit message, the author of the pull request writes the commit messages, and nothing in the pipeline can tell a tag written for a reason from one written to get past a guard; only a review by the file's owner can. The test reads the file where the host has one (GitHub `.github/CODEOWNERS`, GitLab `CODEOWNERS` or `.gitlab/CODEOWNERS`; `ci/CODEOWNERS.example`) and fails on a guard file that no rule covers. The host setting that makes the review required is not in the repository, so no test can read it, and it is the owner's to set and to recheck (`07-process.md` section 12): GitHub branch protection (or a ruleset) with the option that asks for review from code owners (the label differs between the two and was not read against the settings page: unverified) and no bypass on the main branch and every other deploying branch; GitLab "Require approval from code owners" on the protected branch (or approval rules with the owners as approvers, where the plan lacks it); Bitbucket, which has no such file: default reviewers on the repository plus the merge checks for a minimum number of approvals and of default reviewers, named in the profile, with the test created with the host-enforced argument. The owner is a person or a team, never a bot or an automation account (the test fails a rule whose only owners look like one: `[bot]`, `-bot`). Two limits are stated, not hidden. First, a pull request runs its own copy of the workflow file, so the required review is the only barrier for a change to the workflow itself; without it the guards of the pipeline are advice. Second, the author of a pull request cannot approve it (documented GitHub behaviour, unverified on a repository): where the agents push with the owner's own credentials, no approval of the owner counts and the pull request cannot merge without a bypass. Where the host cannot enforce the rule at all (a private repository on a free plan has no branch protection, no ruleset and no enforced code owners), the **unenforced mode** applies: the file is kept, this test still requires and reads it (it differs from the host-enforced argument of Bitbucket, which excuses a missing file), the lead merges only when `gh pr checks` shows every check green, the aggregate `checks-result` included, and the profile says what is not enforced: no merge is stopped without the owner's review, and a pull request can edit the code-owners file and the workflow. The honest states are the agents under a second identity (a machine user or an app: the author may be a bot, the owner of the files may not) with the owner approving; a second person as owner; or a solo owner who is a bypass actor, in which case the rule stops only identities without the bypass and stops nothing when the agents use the owner's token. The last state is written in the profile as it is; `ci/CODEOWNERS.example` and `07-process.md` section 12 spell the states out.

A check that narrows fails this test: that is the guard working. Change the test only with the reason in the PR.

- *No image of its own* (`ci/github-actions-runner.yml`, the runner form): the jobs run on the runner with the pinned setup actions (`shivammathur/setup-php`, `actions/setup-node`), and the point-7 pin of the job image does not apply. The reader that finds the names must also find the indexed forms: `secrets['NAME']`, `secrets[format(...)]` and `toJSON(secrets)` read a secret too, and a reader that matches only `secrets.<NAME>` passes them; the first yields its name, the other two have no static name and fail the file unless the owner names the exception. A kit file, and an auxiliary file with no declaration, keep the generic rule. Failing and passing examples: `examples/php/tests/Unit/AuxiliarySecretRuleTest.php`.
- *The checks script outside a pull request*: `bash scripts/checks.sh --part <name>` stops with "no base branch" when the run has neither `CHECK_BASE` nor a pull request, also for a part that reads no base. A scheduled or manual run passes `--main`, as in `bash scripts/checks.sh --main --part static`.
- *A checkout of the kit next to the project in a workflow*: put it outside the workspace (`path:` under `$RUNNER_TEMP`, or move the folder before the static part runs). Inside the workspace its 250 reference files are part of the tree, and the formatter's check then fails on them.
- *A workflow that has only `schedule` and `workflow_dispatch` triggers* and arrives in the first push of a new repository was not registered on GitHub in the run that reported this: `gh workflow list` did not list it and `gh workflow run` answered "workflow not found on the default branch" until a later push to the default branch changed the file. Observed once on GitHub, not reproducible offline; a project made from a template repository needs one more commit that touches such a file before the first manual run.

**Reasons and traps inside that shape:**

- **No autofix bot, by default.** Format the whole tree once (step 2), then CI is check-only. A bot that commits fixes puts imports at different positions per branch, and every merge conflicts. This is the kit's reason, and it goes to the owner as a question with that reason (`02-step-1-discover.md` 1.1) before any pull request removes a bot: where the organisation keeps its autofix commit, it stays, the profile names the steps that may write, and the contract test takes them as an argument. Never remove a pipeline behavior of the organisation first and explain afterwards.
- **What the measurements said** (one measured run, same code before and after): the pipeline wall fell from 473 s to 333-361 s and the heavy checks from 244-383 s to 45-229 s by the split into parts; result caches were the second lever (Pint with its cache file and Prettier with a content cache: 131 s to 4 s warm; the refactoring tool 101 s to 45 s; the analyser 181 s to 91 s). A host that saves a cache once per key and does not refresh it for days makes a result cache a snapshot of its first run. After the split the bottleneck is the backend test step: shard it with a coverage merge step from the start if the suite passes four minutes. Do not tune the worker count on one run (the noise between runs of one setting, up to 120 s, was larger than any effect). A pipeline with many parallel steps can queue behind the workspace's concurrency: measure a step from its start. Measure the baseline on the same code: a throwaway branch pipeline with the old step definitions (the pipeline file is guarded, so its commit carries the script tag) gave the real "before"; numbers from before the tests existed are not comparable.
- **CI speed is a pre-condition of step 3, not a luxury**: a pipeline of 20 to 40 minutes per push is where a program loses days. In the skeleton, cache the dependency directories and the tools' downloads by the hash of the lock file; keep the analyser's result cache between builds (the type-aware lint cache stays off, point 12 above); run the independent checks side by side (`ci-parallel.sh`) and the test suites in parallel jobs; switch the package manager's process timeout off for the long scripts (Composer: `Composer\Config::disableProcessTimeout` as the first entry of a script, or the 300-second default kills the formatter on a big tree); download a hosted formatter config once per run and cache it, never copy it into the repository (the config stays the organisation's); and fetch the lock-file install once per job.
- **A check that fails every open PR** when it lands (whole-tree formatting, a stricter commit-message rule, a new rule without a list) lands by `07-process.md` section 10.
- **The secret scan** reads every commit in the range, so a token-looking literal that a later commit fixes still fails: never write one in a test or a fixture (not a key shape, a token prefix or a long random string; build a fake value from short words at run time). History cannot be fixed: if one lands, a fresh branch with clean commits replaces the PR. Baseline fingerprints can hold the commit and the path, so a moved or split file needs new ones.
- **GitHub Actions cost** is read before the schedule is chosen, not after the first bill. The included minutes belong to the plan of the account that owns the repository (GitHub's published figure for the free plan is 2,000 Linux minutes a month; read the number for the account, UNVERIFIED as a general rule here), a public repository pays nothing, and every job rounds up to a whole minute, so a run of many short jobs bills more than its wall time. Reading it with `gh`: the plan is `gh api user --jq .plan` (the plan name of the signed-in account, for example `free`; it needs the `user` scope, and without it the call is refused with the command that adds the scope: observed), or `gh api orgs/<org> --jq .plan` for an organisation; the billable time of a run is `gh api repos/<owner>/<repo>/actions/runs/<id>/timing --jq .billable` (ran: it returns `UBUNTU.total_ms` per job, 0 for a public repository), and the wall time of the last runs is `gh run list --json workflowName,startedAt,updatedAt`. The billing endpoints (`users/<user>/settings/billing/...`) answered 404 for a token without the right scope: where no call works, ask the owner to read Settings, Billing. Then add up: minutes per pull request (every job of every run, rounded up) times the pull requests a month, plus the pushes to the main branch, plus the schedule. The skeleton's daily schedule includes a whole-tree mutation run, which can break the allowance by itself: the weekly variant keeps the daily dashboard run and puts the mutation step on a cron of its own (`cron: '23 4 * * 0'` and `if: github.event.schedule == '23 4 * * 0'` on the step; the skeletons show it, point 13 accepts it). Measured on one run of one project (one mutation tool, six workers): the whole tree took 30 minutes, and the estimate the kit's method gave (a timed run on a sample of ten classes, scaled to the tree by size) was 85 minutes, about 2.8 times too high. That is one observation, not a rule and not a correction factor: time one whole-tree run before the schedule is decided, and read the number the run prints.
- **CI duration** is a row the project adds, because only the host knows the number (`tools/README.md`, "Adding a row"); its cap is set after step 2, which makes the pipeline longer.
- **Red for infrastructure reasons**: `07-process.md` section 11.
- **GitHub, what the skeleton settles** (server behaviour that no test here could run is marked so in `ci/github-actions.yml` and in the owner's checklist of `CONTINUE.md`): the kit's jobs are a file of their own (above). A `pull_request` run checks out GitHub's merge ref, so every job tests the same merge of the pull request and the base as it was when the run started, as on Bitbucket; the ref is not made again when the base moves later, so the repository setting "Require branches to be up to date before merging" (or a merge queue, which needs a `merge_group` trigger the skeleton does not have) is what makes the last merge the tested one. The required status checks are the aggregate job `checks-result` (it fails unless every part of the matrix passed) and the three test jobs, never the four `checks (<part>)` names: a new part of `PARTS` is then required without anyone editing the rule, and a skipped job reports success, so no job of the kit's file carries an `if` on anything but its own event (`github.event_name == '<event>'`), and none on the changed paths. The `concurrency` group cancels the older run of a pull request and never a push to a deploying branch (a group that cancels everything would drop the checks of the first of two quick merges). The jobs run in one image pinned by digest, so baselines and analyser results do not move with the runner image; a service container needs the password variable and the health check of its engine (point 10) and, from a container job, its name as host (`DB_HOST=database`, as the GitLab alias); where the image comes from is "The image of the GitHub form" above. A run that GitHub cancels for a newer one of the same pull request still runs the aggregate job, which then reports a failure for the older run; whether the merge box ever shows that is unverified, and the skeleton names the one-line change if it does. `schedule` fires only from the default branch's copy of the file, in UTC and sometimes late at the top of the hour; in a public repository it is switched off after 60 days without activity. `pull_request_target` and a `workflow_run` that checks out pull-request code are never used: the ratchet rows, the composer scripts and the tests all execute that code, and those events carry secrets. The smoke stack runs the production drivers (cache store, queue, database engine), not the production environment: where the application forces https in production (a `URL::forceHttps()` call), a stack served over plain http renders blank pages, so it boots with `APP_ENV=staging` and the drivers of production set by name. The repository settings the kit reads in step 1 (`02-step-1-discover.md` 1.1), because the skeleton relies on them: whether the plan allows branch protection, whether "Automatically delete head branches" is on (it is off by default: a merged branch stays until someone deletes it, and a stacked child is not retargeted, `07-process.md` section 9), and whether the repository uses Dependabot or Renovate.
- **GitLab, what the skeleton settles**: "Pipelines must succeed" accepts a pipeline whose jobs were all skipped, so the contract test asserts that the merge request pipeline holds the checks job; the branch rules start a pipeline for the push source only (a manual run on the main branch would start the tests and not `checks-main`); merge requests from a fork are not supported (the target branch is not in the fork's origin).

## C5. Guards go in first, in baseline mode

Install every guard before the burn-down, at its final strictness: the checks that need no decisions (analyser at its top level, linter, type checker, formatter) in step 2, the ones that need the layout table and the documents in step 3.

- the guard is written for the target rule;
- today's violations go into one counted list (an allowlist file, an analyser baseline, linter bulk suppressions, a keyed baseline);
- a "no stale" check fails on an entry that is fixed, so the list shrinks itself;
- a ratchet row stops the list growing.

Then each burn-down PR empties part of a list, and the last one deletes it (`06-lock-and-audit.md` E1).

Why first: `01-principles.md`, rule 5. A guard that arrives mid-run also hits every open branch after a merge of the base.

**A tool without a baseline mechanism** (a type-checker flag, the unused-code tool) gets a keyed baseline, written and checked by `tools/keyed-baseline.sh`: one line per finding without line numbers, compared with a committed file, in the format of the tool (`--format tsc`, `--format knip`). Step 2 writes the first file of each with `--init`; afterwards `--write` only drops fixed lines and refuses a finding the file lacks. The ratchet row `type-baseline` counts the lines. It touches no source: suppression comments are never inserted to build a baseline (`tools/README.md`, "`keyed-baseline.sh`").

A list keyed by path is rewritten from the move map when files move (step 5), in the same commit as the move and with a check on the count: the same count, minus the entries whose class the move fixed (a renamed data class leaves the naming list, a test at a mirrored path leaves the location list), each checked by the guard's own no-stale test; it is never regenerated, because regenerating hides a swap (a fixed finding replaced by a new one). Every list says which key it uses (a path, a class name, a rule and a count), because a class-name key survives a move of folders and not a rename.

**Three more rules for a counted list.** (1) A ratchet row over a list counts lines, so a swap passes (fix one, add one, count unchanged): the reviewer reads every added line of a list (rubric item 1), and where a codemod moves findings between files, a per-rule total check allows a new key only while that rule's total does not rise. (2) A list for a guard that is a test (the layout list) is a sorted file with a ratchet row (`grep ^.`); `keyed-baseline.sh` is for a tool that prints findings. Keep such lists outside the `baselines/` folder, which the row `type-baseline` counts whole. (3) Generate and check every baseline in the pipeline's own image, never on a developer's host: the extensions of the host change what the analyser reports (an entry for a function from an extension the host lacks is stale on the runner, and `ignore.unmatched` cannot be ignored). The profile names the extensions the host lacks.

An entry that exists only locally (an optional package that is not installed) is stripped before every push, or CI fails on it as stale. A long-lived second branch that runs the same checks cannot use the main branch's baseline: the profile says what it does when one lands (merge the main branch first, or regenerate on its own tip). A percentage has no baseline: a message that holds totals (type coverage: "out of 7234 possible param types") stops matching every entry when any parameter is added, so type coverage is held by its measured number in the config and a `min` row, not by baseline entries.

## C6. Judgements, and counters where a test cannot judge

Review only is for judgements: a design per feature, "one extraction, not a call shape", whether a test is worth its name. Each is a numbered item in the review rubric and is not faked with a regex. Everything else gets a guard; when a reviewer has to flag the same thing twice, it gets a guard.

**A counter where a test cannot judge.** Some rules are a judgement per case but a number over the tree. The pattern is the comment counter. "No comment unless a future reader would act differently because of it" cannot be a yes or no test; the number of comment lines can only go down. The ratchet row `comments` counts comment lines in every source folder (what it counts and what it cannot tell: `tools/README.md`, "The rows that ship"). Type tags the analyser needs are not counted. A comment that earns its place needs the override tag in a commit (`[ratchet: comments] <reason>`), and the reviewer reads that reason against the rule (rubric item 22). `comments` is in `OVERRIDE_AT_ZERO` (C2), so the override stays available at 0: any other `max` row at 0 takes none, unless it is named there too.

The same pattern holds a direction where the tree is far from zero and each site needs thought. Two rows count lines in the tests that go the wrong way: `test-doubles` (a mocking-library double of one of the project's own classes, in every spelling the test framework and the mocking library have) and `event-fake-all` (an event fake with no list of events, which silences every listener). A new test uses the real class or a hand-written fake and names the events it asserts; a test that is converted lowers the row.

These three are the fixed shrink-only rows (`01-principles.md`, "Shrink-only rows").

Test a counting regex with the tool that runs it and against a hand count of one file, and cover the modifiers the language allows between the keywords: a counter on `new class` is evaded by `new readonly class`.

## C7. A candidate guard: measure, then decide

For every rule the rubric holds as review only (the sweeps of steps 3 and 10), every rule a step audit finds, and every rule found after zero (`06-lock-and-audit.md` E3):

1. Write the detector and count today's violations over the real tree.
2. Zero: build the guard.
3. A handful: fix them and build the guard in the same PR.
4. More, and the fix is the same at every site: the guard goes in with its counted list, as a new ratchet row, in the PR of the step that found it. In steps 4 to 9 only the lead adds it. After zero there are no lists: fix the sites and build the guard in one PR, or report the count and what converging takes as a backlog row with its "start when" signal; the rubric keeps the rule with its count.
5. More, and every site needs its own answer: the rule is a **decision list**, not a guard yet. Record the count and the sites in the backlog (`templates/backlog-and-continue.md`, "Decision lists"), with the question each site asks. The lead answers each site with evidence; a site whose answer changes behavior goes to the owner. Build the guard now for the part every site already meets; the full guard lands when the count is zero. Example: "the lock of a scheduled task expires at most at the task's interval" fails many tasks, and the right expiry depends on the longest honest run of each; the guard that can be built at once checks that an explicit expiry is declared.

A rule can also wait for one decision before it has a count worth acting on, because the decision defines what a violation is. Ask these in every run (each is a candidate: measure it, then decide):

| Candidate | The decision it waits for |
| --- | --- |
| Direct HTTP client calls outside the one wrapper per external system | which wrapper each remaining call belongs to |
| Iterating a query in fixed pages or with a cursor | whether each site can be ordered by id |
| A case-sensitive pattern match on a column | whether case matters at that site |
| A test named after a class that never references it | read each file: rename, move or rewrite |
| A route that is a closure | where its logic goes |
| The error-suppression operator | what each site does with the error instead |
| An exception that extends the base exception class directly, and a generic built-in exception thrown from domain code | the project's exception hierarchy |
| A shell or process call, or a native file function (a temporary file, a stream) | which class owns each binary and each kind of file work (the mechanical form: a binary is run by one class) |
| Global helpers that reach for the request, the signed-in user or the event dispatcher | the replacement per layer |
| Text for users written in code or markup instead of the translation source | whether the project translates at all, and which files are exempt by category |

What the starter does not build, and what the earlier extract had that the starter lacks, is in `reference-project/README.md` and `docs/starter-variants.md`.
