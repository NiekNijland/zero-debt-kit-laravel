# Catalog: tests, database, CI and dependencies, docs

The test and database tables are the PHP and SQL form; the CI, translation and docs tables are technique-neutral.

Every project converges to these patterns; code that differs is debt (`01-principles.md`, "Who decides what"). Counts are text matches in tracked files, run from the repository root on the main branch. The Guard column reads as in `catalog/backend-laravel.md` ("Reading the Guard column"): a file name is the worked example in the starter, written in Pest; the written rules of that example are in its `tests/AGENTS.md`.

**Pest or PHPUnit.** The test framework is a technique: one per project, never mixed (`03-conventions.md` B4). A row that prescribes how a test is spelled gives both forms. Every guard works in both; what a PHPUnit project copies and what it rewrites is in `04-guards.md` C1.

**Routes built by hand in a test.** A coverage test over routes needs synthetic routes for its failing examples. Only the router's own `addRoute` turns an invokable class name into `Class@__invoke`: `new Illuminate\Routing\Route(['GET'], 'notes/{note}', ShowController::class)` has no controller class, so `signatureParameters()` reflects a method called `null`. Build the route through the router, or set the action by hand: `'uses' => ShowController::class . '@__invoke'`. A helper in the test support folder does this once.

**The list of the banned-call guard.** One list, which the rows above point to. Each entry has a failing and a passing example in the guard's test. Spellings: `test(...)` where the kit's spelling is `it(...)`; `sleep()` and `usleep()` (the analyser's rule of "Wait" bans them too, in tests included; the guard names the replacement for the test form, the fake); `Http::allowStrayRequests()` and `Process::allowStrayProcesses()`; `preventStrayRequests(false)` and `preventStrayProcesses(false)`; `Config::set()`; `setTestNow()` on each clock class; `withoutExceptionHandling()` and `withoutMiddleware()`; the loose matchers `toBeTruthy()` and `toBeFalsy()`; `->only()`; `->ignoring()` on an architecture rule. The bare event, queue and bus fakes are held by their counting rows until those reach zero ("Fake events and queues"). A row of the catalog that says a call is on the guard's list is a row of this list; a name added to one is added to the other in the same commit.

### What the presets assert

Read in Pest 5.1; verify in step 1 against the installed version, and report an assertion that a newer release adds as a kit change. "User namespaces" are the namespaces the manifest autoloads outside the test folder. A PHPUnit project builds one detector class per line, with the line as its failing example.

| Preset | It asserts | Where the kit already says it |
| --- | --- | --- |
| `php` | none of these is used: the debug functions (`dump`, `var_dump`, `print_r`, `var_export`, `debug_zval_dump`, `debug_backtrace`, `debug_print_backtrace`, `phpinfo`, `ray`, `ds`, `trap` and every `xdebug_*` function), `die`, `echo`, `print`, `goto`, `global`, and the removed database and pattern functions (`mysql_*`, `ereg`, `eregi`) | "Debug and exit" (`catalog/backend-laravel.md`); the preset is stricter: `print_r` and `var_export` are banned in their returning form too |
| `security` | none of these is used: `md5`, `sha1`, `uniqid`, `rand`, `mt_rand`, `tempnam`, `str_shuffle`, `shuffle`, `array_rand`, `eval`, `exec`, `shell_exec`, `system`, `passthru`, `create_function`, `unserialize`, `extract`, `mb_parse_str`, `dl`, `assert` | "Narrowing" bans `assert()`. The rest has no other row: the preset is the guard. A checksum that needs `md5` or `sha1` for an outside format uses `hash('md5', ...)`, which names the algorithm at the call; a random value comes from the framework's string helper or `random_int()`; data is stored as JSON, not serialized; a process starts through the framework's process helper, which a test can fake |

The `strict` preset makes six assertions, and two of them forbid what the framework's own extension points are made of: an abstract class, and a protected method (the framework declares a model's `casts()` and `booted()` and a form request's `prepareForValidation()` protected). The kit stays as close to the stock framework as it can, and a preset cannot be called in part, so the preset is not called. The kit's own guards hold the four assertions it adopts (the rows are in `catalog/backend-laravel.md`):

| The `strict` preset asserts | The kit guard |
| --- | --- |
| every file of a user namespace declares strict types | the formatter rule `declare_strict_types`, and the row `strict-types-missing` ("Formatting") |
| no file of a user namespace holds ` == ` or ` != ` | the formatter rule `strict_comparison`, and the row `loose-comparisons` ("Strict comparison") |
| `sleep` and `usleep` are not used | the banned calls of "Wait" |
| every class of a user namespace is final | the formatter rule `final_class`, and the dashboard row `open-classes`, for every concrete class ("Final by default") |
| no class of a user namespace is abstract | not adopted: a parent class is abstract, where the framework or a real shared base needs one ("Final by default") |
| no class of a user namespace has a protected method | not adopted: a framework hook keeps the visibility the framework declares. The formatter rule `protected_to_private` makes private what a final class that extends nothing declared protected |

The `laravel` preset pins classes to the stock folders: "no enum outside `App\Enums`", "nothing throwable outside `App\Exceptions`", "no mailable outside `App\Mail`", and the same for notifications, console commands, models, form requests and providers. The kit's layout puts enums, exceptions, mails, notifications and commands in module folders (`catalog/backend-laravel.md`, "Structure"), so the preset fails a tree that follows the kit, and a preset cannot be called in part. Its assertions are held by the kit's own guards, in the kit's layout:

| The `laravel` preset asserts | The kit guard |
| --- | --- |
| a kind of class sits in its folder and nowhere else (traits, enums, exceptions, models, requests, commands, mails, notifications, providers, controllers, policies) | `ModuleLayoutArchitectureTest.php`, `ModuleLayoutGuard.php` |
| suffixes: `Request`, `Command`, `ServiceProvider`, `Controller`, `Policy`; a model has no `Model` suffix | the same layout guard, from the name column of the layout table |
| what a class extends or implements: a model the model class, a request the form request, a command the console command, a mail the mailable, a notification the notification class, a provider the service provider, an exception `Throwable` | an architecture test of the class-shape kind (`04-guards.md` C1), one case per folder of the layout table |
| a middleware, a job, a listener and a command have `handle()`; a request has `rules()` | the same architecture test |
| a job and a mail are queued | the kit does not assert it: whether work is queued is a decision per class; a queued class has its limits ("Limits of a queued class") |
| a controller's public methods are among the framework's seven and `__invoke` | `ArchHttpTest.php` (single action) |
| the HTTP layer is used only by itself and the providers; a provider is used by nothing | an architecture test of the "who may use what" kind (`04-guards.md` C1) |
| `dd`, `ddd`, `dump`, `env`, `exit` and `ray` are not used | "Debug and exit" and "`env()`" (`catalog/backend-laravel.md`) |

## Top level in tests

Method: `05-program.md` D7. Shared causes, fixed first; the file names are examples under `tests/Support/` of the starter.

- Pest: expectation chains (`expect($x)->property->toBe()`) are untyped. Two analyser extensions type them: `PHPStan/PestHigherOrderProperty.php` and `PHPStan/PestHigherOrderMethod.php`. PHPUnit has no such chains.
- A `require` of a migration file returns `mixed`: one typed loader (`Migrations.php`).
- Pest 5 needs its own analyser extensions in the support folder, one per kind of call it types by `$this` or by a pending-call object: (a) the closure `$this` of `it()`, `test()`, `beforeEach()` and `afterEach()` (a function-parameter extension: the base test case of the project, so its name is the project's own: the reference names `Tests\FeatureTestCase`); (b) the closure `$this` of `->beforeEach()` and `->afterEach()` on the pending call of `pest()->extend(...)` or `->use(...)` (a method-parameter extension on Pest's `UsesCall`); (c) the function `arch()` and its call type, which has `expect()` (returning `Expectation<mixed>`) and `preset()`: without `expect()` every named `arch('rule')->expect(...)` is "Call to an undefined method" at level 10. Copy the three by kind, not by name: `PestClosureThis`, `PestUsesCallClosureThis`, `PestArchFunction` with `PestArchCall` in a project that has them split (`PestTestFunction` of the reference types `test()` and `arch()` in one class).
- Under Pest, `$this` inside a test closure and `test()` are typed as the DSL, so `$this->artisan()` is "undefined method on mixed" and the baseline grows with every new test file. The support folder ships one typed accessor (`CurrentTest::case()` and `::app()`: read the running test case and narrow it with `instanceof`), and the test guide says new tests reach the application through it; raw `DB::select()` rows go through typed helper methods. An analyser baseline entry for an anonymous class is keyed by file line numbers: any edit above it moves the key, so regenerate in the pipeline's image after a formatter or refactoring pass and check that the entry count did not rise.

The one list of fix patterns every builder gets. Example helpers: `Narrow.php`, `NestedValue.php`, `InstancesOf.php`.

| # | Error | Fix |
| --- | --- | --- |
| 1 | a closure or data-set parameter typed bare `array`, passed where a keyed array is expected | narrow at the call (`Narrow::map()`, `InstancesOf::list()`); a `@param` on a closure does nothing |
| 2 | offset access on `mixed` (shared props, decoded JSON, a required file) | read the whole path in one call: `NestedValue::get($data, 0, 'key')`, or a typed variant |
| 3 | property or method on `mixed` | `Narrow::row()` for a database row, `Narrow::instance($x, X::class)` for an object, a return type on a local closure, a typed collection at its source |
| 4 | `mixed` where a string, int or array is expected | `Narrow::string()`, `Narrow::int()`, `Narrow::array()`; never a cast on `mixed` |
| 5 | an empty `collect()` for a typed collection parameter | `new Collection()` |
| 6 | callback parameter types on a `mixed` collection | type the input, not the callback |
| 7 | a support helper that declares a precise `@return` and returns `->all()` or `pluck()` | narrow inside the helper |
| 8 | small kinds: negation of `mixed`, `foreach` over `mixed`, a `mixed` array key, increment of a by-reference counter | `Narrow::bool()`, `NestedValue::array()`, `Narrow::string()` as key, a typed parameter |

Never: an ignore, a baseline, `assert()`, an inline `@var`, a cast on an unchecked value, a type widened to `mixed`, a changed assertion or set-up. Dead-method errors that appear when only the tests are analysed are an artifact of the scope: ignore them in the scratch run. Typed tests expose what untyped ones hid: a public method that only a test called on an untyped value turns out dead and is deleted (step 9).

## Proof that tests can fail

"A test names the class" and a coverage percentage are both satisfied by a test that asserts nothing useful, and agents write such tests easily.

**The framework-usage provider.** A member that the framework calls by name has no caller in the source, so the detector reports it as dead (`shipmonk.deadMethod`). The detector's own providers cover part of that (overrides of vendor methods, and its Laravel and Eloquent providers, by version): one starter's first run still reported the constructor of a container-built action, and the larger set of the table below (policy abilities, `__invoke` of controllers, `handle` of middleware, `rules()`, `casts()`, `definition()`, seeders) was reported in an earlier one. Run the detector once without the provider, read the first report and keep each line of the table the report shows; the provider holds them all, so a detector release that changes its own coverage changes nothing. The provider is one class in the test support folder (`tests/Support/PHPStan/LaravelMagicUsage.php`), registered in `phpstan-tests.neon` with the tag `shipmonk.deadCode.memberUsageProvider`, and it marks used, by the class's folder or parent and the method name (reflection, never a list of class names):

| Member | Called by |
| --- | --- |
| `__construct` of a class of the application | the container, which builds the class and injects it |
| public methods of a policy | the gate, by ability name, from the route and from `can` |
| `__invoke` of a controller | the router |
| `handle` of a middleware | the router |
| `rules` of a form request and of a DTO; the `from*` creation methods and `defaultWrap` of a DTO | the validator, the DTO library |
| `casts` and static `boot*` and `initialize*` methods of a model and its traits | the model, when it builds its attributes and boots its traits |
| `definition` of a factory; `run` of a seeder | the factory, the seed command |
| `boot` and `register` of a provider | the container |
| the queue hooks `shouldQueue`, `viaQueue`, `viaConnection` of a queued listener; `via`, `broadcastAs` and `broadcastType` of a notification; the handler of a queue job (`Class@method` strings) | the dispatcher, the notification channels, the queue |
| `setUp*` and `tearDown*` hooks of a test trait | the test runner |

The reference provider covers every row of the table (`tests/Support/PHPStan/LaravelMagicUsage.php` of the starter; the namespace prefixes in it are the reference's own folders). A project adds a line for each other class kind it has (a Livewire component, an MCP tool): the first report of the detector on that kind is the reason, and the note on the line says who calls the member. The provider is not an ignore list: it marks a kind of member by its role, never a class or a file by name. Test-only dead-member findings from running the detector on `tests` alone are an artifact of the scope: the run is on source and tests together.
