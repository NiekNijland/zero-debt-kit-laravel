# Tools

Ten scripts and tools, the config file they share and a caps file. They name no project: each script starts with one config block, and everything a project sets is in that block, in `kit-config.sh` or in the table of rows. The skeletons that call them are in `ci/`. The starter holds a copy of each with its own config block (`scripts/` there); the kit's body wins. The scripts carry no executable bit: every call is `bash <file>`, in the pipeline too.

How they get into a repository, in which order, and how they meet a pipeline that already exists: `05-program.md` D2, step 2. In the target repository they live in `scripts/`.

| File | What it does |
| --- | --- |
| `ci-ratchets.sh` | fails a pull request when a counter moves the wrong way between the merge base and the head |
| `debt-dashboard.sh` | prints every counter with its target; the gate of the checks step |
| `debt-caps.json` | the cap of every dashboard row, one key per row |
| `kit-config.sh` | the values more than one script reads; each script sources it from the folder it is in |
| `ci-commit-messages.sh` | fails a pull request with a commit that does not start with the ticket and a type |
| `ci-parallel.sh` | runs named commands side by side, with a time limit, and reports each |
| `keyed-baseline.sh` | the baseline for a tool that has none of its own: one line per finding, compared with a committed file |
| `audit-gate.sh` | the dependency audit with time-boxed exceptions: reads the audit's JSON, prints the number of advisories no active exception covers plus the broken entries, exits 1 above 0 |
| `mutation.sh` | the mutation run of the stack's tool, whole tree or the changed files, with the minimum score read from the committed floor file; the pipeline calls it as a script (an inline command with `": "` in a YAML list item parses as a map) |
| `map-normalise.sh` | maps the names in a text back through the move map (or forward), longest name first, doubled backslashes too: the lists of an old and a moved stack can then be diffed |
| `move-ts.mjs` | moves TypeScript or JavaScript files from a map and rewrites every specifier (relative, alias, `import()`, mocks); `--verify`, `--reverse`, idempotent. Copied to `tools/codemods/`, which `UNCOUNTED_PATHS` names |
| `doctor.sh` | compares a project's copies of the scripts with the kit's and plans or applies the upgrade (see "`doctor.sh`") |
| `proof/proof.sh` | proves every script in scratch repositories (see "Proof"); it stays in the kit |
| `ci/checks.sh` | the one command: CI runs it in the checks step, one pipeline step per part (`--part <name>`), a developer runs it before a push |
| `ci/prepush.sh` | runs every part of `checks.sh` side by side in one place, before a push, so CI only confirms |
| `ci/bitbucket-pipelines.yml`, `ci/github-actions.yml`, `ci/gitlab-ci.yml` | the pipeline per host, with the five runs of `04-guards.md` C4 |

## Requirements

- `bash` 3.2 or later (the version macOS ships) and `git`. No GNU-only tool: no `timeout`, no `wait -n`.
- `grep`, `awk`, `sed`, `sort`, `comm`, `wc`, `tr`, `xargs`, `mktemp`: the POSIX ones.
- For `checks.sh`: `gitleaks` 8.19 or later, on the runner and on a developer's machine (the secret scan is one of its lines). `checks.sh` scans the commits of the range; a scan of a whole worktree with dependencies installed reads `vendor`, `node_modules` and a copied env file: run it before the install, or filter to `git ls-files`.
- For `json` rows and the caps file: one of `jq`, `node` or `php`. The script takes the first it finds, in that order; `RATCHET_JSON_TOOL` forces one. With none of them a `json` row fails with "a json row needs jq, node or php".
- For `block` rows: `node` or `php`. For `neon`, `return`, `const` and `call` rows: `php`. A row whose files are all missing or whose config value is empty counts 0 and needs no tool.

## `kit-config.sh`

The values more than one script reads are set once, here. The scripts source the file from the folder they are in and stop when it is missing. It is a guarded file.

| Value | Read by | Meaning |
| --- | --- | --- |
| `DEFAULT_BASE_BRANCH`, `REMOTE` | ratchets, commit messages, `checks.sh` | the base branch on a developer's machine; the remote |
| `BASE_BRANCH_VARS`, `HEAD_BRANCH_VARS` | ratchets, commit messages, `checks.sh` | the names of the CI host's variables |
| `CAPS_FILE` | ratchets, dashboard | the caps file |
| *(none)* | every script that sources it | a `.git` that is a file (a git worktree) and points to a folder that does not exist here, as when a worktree made on the host is opened in a container, stops the run with exit 64 and the reason: run the kit scripts on the host, and the project's own tools (`php`, `composer`, `npm`) in the container |
| `DATABASE_IMAGE` | no script: the contract test over the CI files | the database service image of the backend test run and the smoke run: the production engine in the production major version (`04-guards.md` C4); empty in a project without a database. ### The table

One row per counter: `name  max|min  method  paths  spec`. Columns are split on whitespace; `paths` is a comma list of paths, `@NAME` values and git pathspecs that start with `:` (the `comments` row uses `:(exclude)*.md`); `spec` is the rest of the line. A `max` row may only go down, a `min` row only up.

A row needs at least one real path. An exclude pathspec narrows the paths before it: a row whose paths are pathspecs alone fails with "a row needs at least one real path". Tests that live next to the source (`create-order.test.ts` beside `create-order.ts`) therefore set `TEST_PATHS` to the source folder, never to a glob.

| Method | Counts | Needs |
| --- | --- | --- |
| `grep` | matches of the extended regular expression in the tracked files under the paths (`git grep -a -o -E`: several matches on one line each count, adjacent ones that share a separator character count once; every tracked file is read as text, so a `.gitattributes` line cannot hide a file, and files with an image, font, archive, audio or video extension are left out) | git |
| `without` | two expressions: the tracked files under the paths whose name matches the first and that hold no line matching the second. It counts files that lack a line, which `grep` cannot | git |
| `number` | the whole number that the one capture group of the expression captures, first match per file | git |
| `json` | `<operation> <path>` over the JSON file. Operations: `value` (the whole number at the path), `count` (entries of the list or object), `leaves` (scalars below the path). `count?` and `leaves?` give 0 when the key is missing; without `?` a missing key is an error. The path is keys joined by dots, `.` for the root, `*` for "every child". A fourth operation, `keys`, prints the keys of the object at the path: the scripts read the caps file with it, and it is not for a row | jq, node or php |
| `block` | two expressions: the first captures blocks (it may span lines), the second is counted inside them. Keep to the syntax PCRE and JavaScript share | node or php |
| `neon` | entries under a dotted key in a NEON or simple YAML file; a `count:` under an entry adds up. A trailing `?` on the key gives 0 when it is missing | php |
| `return`, `const`, `call` | leaves of a PHP file that returns an array, of named constants, of the arguments of named method calls | php |

`return`, `const` and `call` execute code from the pull request. On a runner that builds forks or holds secrets, use the other methods only.

What the `comments` row cannot tell, because it reads one line at a time:

- Not counted: `#[Attribute]`, `#!shebang`, `http://` and other `//` that follow a colon or a quote, `#` inside a quoted string (`'#fff'`, `href="#top"`), a `#comment` with no space after the `#`, a docblock line that holds only a tag, Markdown files.
- Counted although it is no comment: `<!--` or `{{--` inside a string; `//` or `# ` after a space inside a string or a multi-line string (`"see // here"`, a Markdown `# heading` inside a heredoc or a template string of a test), `/// <reference>` lines, a line that starts with `* ` and continues a multiplication.
- A line with two `//` runs separated by a space counts twice.

The same holds for every `grep` row (`loose-comparisons` counts `==` in a string that holds a GitHub expression, a YAML example or source text): the row cannot tell code from text, and the kit offers no exclusion inside a file. Three ways out, in this order: build the text at run time from two parts (the operator or the slashes as two strings joined), so that no line holds the pattern; move the fixture into a data file that no row reads (a path under `:(exclude)` in the row's path list, a change of the table that needs `[ratchet: script]`); or accept the count and keep the row's cap at it. A test that builds its text at run time and passes the byte-string row does so with `mb_strlen($x, '8bit')` (the multibyte function with the `8bit` encoding counts bytes and is not on the row's list); the fixture of `--self-test` holds that spelling. A guard copied from the starter holds docblock prose for the reader of the kit: the `comments` row counts every such line (a docblock line that holds only a tag is not counted), so a project deletes the prose and keeps the ``, `` and `` tags when it copies a guard; the row is right, the copy is what has to change.

The row is shrink-only, so an over-count costs nothing and an under-count hides nothing that review does not see. Test a changed expression with `git grep -o -E -e '<expression>' HEAD -- <paths>`, which is what the script runs.

### What a run checks

1. **Each row.** The merge base is counted with the base's own definition of the row (its line and the base's config block), the head with the head's.
   The rules for a wrong-way move, the override tag, a new row and a removed row are `04-guards.md` C2. The mechanics beyond them:
   - **The tag** is a line of the commit message that starts with `[ratchet: <name>]`, one space or more and a reason; the same words in the middle of a line, in a quote or without a reason are no tag. It must be in a commit that touches a file of the row's paths. A `max` row at 0 takes none, except the rows of `OVERRIDE_AT_ZERO`.
   - **Redefined row:** when the two definitions differ, the row prints `was:` and `now:` and fails, unless a commit that touches the script carries `[ratchet: <name>] <reason>`. When only the config block or `kit-config.sh` changed, `[ratchet: script] <reason>` in a commit that touches that file is enough. The wrong-way rule still applies.
   - **Removed row:** the tag goes in the commit that removes the line from the table, for example `[ratchet: layout-list] list emptied and deleted`: the row is at 0 only on the head, and the base still counts the list. Keeping the row and deleting only the file fails with "missing <file> at the head". A rename is a removal plus a new row: the removal of a row that stands at 0 on the base needs no tag, and a new row is a first measurement, so a rename takes no tag either (the commit touches the script's table only; a change outside the table still needs `[ratchet: script]`).
   - A required file or key that is missing at the head fails with "a list, file or key moved".
2. **The script itself and the guarded files** (`04-guards.md` C2): a file in `GUARDED_FILES` is checked when it exists on the merge base. This holds in the first run too, when the ratchet script itself is new: a pipeline file that was already there is guarded. A row cannot be named `script`. **When the tag is needed for the installed scripts:** a script is guarded from the moment a copy of it is on the merge base, whatever its content. Copy and configuration in one pull request need no tag (the scripts are new on the base). When the copy was merged first (or is the first commit of a local series that is the base) and the config blocks are filled in later, every configuring change is a change to a guarded file: the commit carries `[ratchet: script] configure the installed scripts`, once per commit that touches a script. The failure message says so.
3. **The caps file.** Every key needs a row `cap-<key>`; a key without one fails.
4. **Coverage of the tree.** Every tracked file with an extension from `SOURCE_EXTENSIONS` lies under `SOURCE_PATHS`, `TEST_PATHS`, `FRONTEND_PATHS` or `UNCOUNTED_PATHS`. A new top-level folder fails until it is in one of them.

5. **The expressions themselves.** `ci-ratchets.sh --self-test` runs every regex row against a built-in fixture (`selftest_cases` in the script): spellings the row must count and spellings it must not, one line each, with the count expected. It builds a scratch repository, so it needs no checkout and no network, and it uses the same counter as a run. It fails when a row under-counts (an expression that silently stopped matching, a new spelling that is not covered) or over-counts. It also takes every alternative of a regex row (each name of a list, each side of a `(a|b)` group, the anchors) out of the expression, one at a time, and fails when removing it changes no count on the cases of that row: a misspelt or dropped name leaves a row under-counting with the cases still green unless some case needs it. A new name in a row needs its own case. A case of a project's own file that names a row the table lacks fails (a typo does not silently stop testing). `ci/checks.sh` can run it with one line, `bash scripts/ci-ratchets.sh --self-test`, next to the other script checks. The exclude pathspecs of a row are tested too: for every `grep` row with a `:(exclude)<glob>` in its paths, the first spelling the row counts is written into a file that the glob names, committed, and counted with the row's own pathspecs: it must be 0 (and above 0 without them), so a pathspec that does not exclude what it names fails. A project that changes an expression changes its cases in the script in the same commit (the script tag), or keeps its own cases in a file it passes as the second argument (`<row>[@<file name>] <expected count> <text>`, one line per case; `~NL~` is a line break). A file name that starts with `/` is a path from the root of the scratch repository and the case is counted with the row's pathspecs: a project that excludes a folder from a row writes one case into it (`loose-comparisons@/tests/Guards/Fixture.php 0 if ($a == $b) {`), which must count 0. The fixture also holds the expressions of "Adding a row", point 6.
6. **The expressions read what a pull request cannot move.** Every grep reads files as text, so an attribute line that marks files binary hides nothing, and `.gitattributes` is itself a guarded file. A value of the three long expressions in the config block that holds a backslash, a dollar sign or a backtick stops the run (exit 64), because the base side would read it differently from the head side.

The limit of check 2 (a pull request runs its own copy of the script) and what covers it: `04-guards.md` C2. `ci/checks.sh` runs the base's copy with `--guard` from a temporary folder, the base's script next to the base's `kit-config.sh`.

The script deepens a shallow clone until it finds the merge base, and fails with "Clone with full depth" when it cannot. On a merge-first checkout (Bitbucket's pull-request pipeline, GitHub's `pull_request` checkout of the merge ref) it compares that merge with the base, so `CHECK_HEAD` stays unset there; GitLab checks out the source branch itself and sets `CHECK_HEAD`. The head branch variable is only a courtesy fetch: a pull request from a fork has no branch of that name on the remote, and the run goes on. A branch name that starts with a dash or is not a branch name is refused for the base and ignored for the head, so a name can never be read by git as an option. A head that does not hold the script fails with "merge the base branch first". There is no skip for a pull request from the main line to a release branch: every override is in the range, so it passes on its own.

### Adding a row

1. Add the line to the table, in the pull request that adds the guard or finds the list.
2. Run `bash scripts/ci-ratchets.sh --head` and check that the number is the one you expect. For a `grep` row, run the `git grep` line above and read the matches. Add the spellings the row must and must not count to the cases of `--self-test`.
3. For a dashboard counter of the project's own: add the key to the caps file, the row `cap-<key>  max  json  @CAPS_FILE  value <key>` to the table, and a `COMMAND_ROWS` line to the dashboard. The dashboard script is a guarded file, so that commit carries the script tag. A row of the project's own also needs its line in `ROW_ADVICE`, or it prints `UNKNOWN`. Example, the CI duration: the key `ci-duration-minutes`, the row `cap-ci-duration-minutes  max  json  @CAPS_FILE  value ci-duration-minutes`, the `ROW_ADVICE` line `"ci-duration-minutes::speed up or split the slowest step"`, and the `COMMAND_ROWS` line `"ci-duration-minutes::online::<command>"` with the command of the host, which prints the median, in whole minutes rounded up, of the last ten successful push pipelines on the main branch (`<main>`). The median is the statistic of the cap: one slow run (a retried step, a cold cache) does not set it, and the cap still goes down when the pipeline gets faster. Only push runs count: the scheduled run holds the whole-tree mutation and is the longest, and a pull request run is not the pipeline of the main branch. The median is the element at zero-based index `floor(n / 2)` of the sorted durations, so four runs give the third-fastest; with no run the command prints nothing and the row is `?`:
   - GitHub: `gh run list --branch <main> --workflow <workflow file> --event push --status success --limit 10 --json startedAt,updatedAt --jq 'map((.updatedAt | fromdate) - (.startedAt | fromdate)) | sort | if length == 0 then empty else (.[length / 2 | floor] / 60 | ceil) end'`, with `GH_TOKEN` set to the job's own token and `actions: read` in the job's permissions (the expression was run on sample JSON: durations of 540, 600, 690 and 2700 seconds give 12);
   - Bitbucket (the host's own API; names as at the time of writing): `curl -s -H "Authorization: Bearer $PIPELINES_READ_TOKEN" "https://api.bitbucket.org/2.0/repositories/$BITBUCKET_REPO_FULL_NAME/pipelines/?target.branch=<main>&sort=-created_on&pagelen=10" | grep -o '"duration_in_seconds": *[0-9]*' | grep -o '[0-9][0-9]*$' | sort -n | awk '{ d[NR] = $1 } END { if (NR) print int((d[int(NR / 2) + 1] + 59) / 60) }'`. The list has no filter for the trigger that this text has verified: where the host offers one (a `q` query on the trigger and the result), add it, so that scheduled and failed pipelines do not count;
   - GitLab (the list has no duration, so each pipeline is asked once): `for id in $(curl -s -H "PRIVATE-TOKEN: $PIPELINES_READ_TOKEN" "$CI_API_V4_URL/projects/$CI_PROJECT_ID/pipelines?ref=<main>&source=push&status=success&per_page=10" | grep -o '"id": *[0-9]*' | grep -o '[0-9][0-9]*$'); do curl -s -H "PRIVATE-TOKEN: $PIPELINES_READ_TOKEN" "$CI_API_V4_URL/projects/$CI_PROJECT_ID/pipelines/$id" | grep -o '"duration": *[0-9]*' | grep -o '[0-9][0-9]*$'; done | sort -n | awk '{ d[NR] = $1 } END { if (NR) print int((d[int(NR / 2) + 1] + 59) / 60) }'`.

   `PIPELINES_READ_TOKEN` is a read-only token for the pipelines API (Bitbucket: a repository access token with the scope "pipelines: read"; GitLab: a project access token with `read_api`), stored as a secured variable of the pipeline. Making it is the owner's step (`05-program.md` D2, step 2). The parameter and field names are the hosts' at the time of writing: check them against the host's API reference when the row goes in.
   **A row with no subject, and a row that needs a host.** A row may be absent from the table, or present at 0: a counted list that does not exist in a new project (`model-strictness-violations`: the violations of existing models, a greenfield project has none) is not added, and "lists stay deleted" forbids an empty file to keep it at 0; or the row names the file with a trailing `?`, and a missing file counts 0. A row that needs the host (`ci-duration-minutes`) is added only once the repository is hosted and the command can run; until then the row, its cap key and its `COMMAND_ROWS` line are absent. `--offline` prints such a row as `skipped (--offline)`. Without `--offline`, a row that cannot be measured (no host, no CLI, no token) is `UNKNOWN (could not be measured)` and fails, in `--final` too: `skipped` is never a pass of the end state, and `--final --offline` says so in a `Final:` line. A cap that a host measures starts at 0 in the caps file, so its first measurement is a raise from 0: the project names the cap in `OVERRIDE_AT_ZERO` (above) and tags that commit. The cap cannot reach 0 (no pipeline takes 0 minutes), so it is in `SHRINK_ONLY` by a decision row with its end date, equals the median of the last ten runs and moves with it (`--final` fails "the cap N is above the row" when the median falls below it).
4. A percentage (coverage, mutation score) is a number in a committed config file with a `min` row over it, method `number`. The rows have the same names in every project: `coverage-floor  min  number  scripts/coverage-floor.txt  ^threshold: ([0-9]+)$` (see "Coverage"); where the project has a frontend, `frontend-coverage-floor  min  number  <the frontend test runner's config>  <expression with one capture group>` over the threshold of the whole frontend and `frontend-logic-coverage-floor`, the same form over the threshold of the logic folders; and `mutation-floor  min  number  scripts/mutation-floor.txt  ^threshold: ([0-9]+)$` (see "Mutation").
5. A baseline is counted per entry, not per file: `neon` for a NEON baseline, `json` with `count` or `leaves` for a JSON one, `grep` with `^.` for one entry per line.
6. Files that lack a line are a `without` row. The one every PHP project adds in step 2 where it has such files: `strict-types-missing  max  without  @SOURCE_PATHS,@TEST_PATHS  (^|/)[^/.]+\.php$ ^declare\(strict_types=1\);` (the first expression leaves out templates such as `page.blade.php`). The row stays when it reaches 0. Three more rows of this kind count the sites of a formatter rule that is still off (`templates/tool-configs.md`, "Rules that can change behavior"), with the same names in every PHP project, and stay at 0 afterwards:
   - `loose-comparisons  max  grep  @SOURCE_PATHS,@TEST_PATHS  (^|[^=!<>])(==|!=|<>)([^=]|$)`
   - `mutable-dates  max  grep  @SOURCE_PATHS,@TEST_PATHS  (^|[^A-Za-z0-9_])(DateTime|Carbon)(::|[[:space:]]*[(;,)])` (also `new DateTime;`)
   - `byte-string-functions  max  grep  @SOURCE_PATHS,@TEST_PATHS` and the expression `(^|[^A-Za-z0-9_>:$\\])\\?(strlen|substr|strpos|strrpos|stripos|strripos|strstr|stristr|strrchr|substr_count|str_split|strtolower|strtoupper)[(]`: the thirteen functions the formatter rule rewrites, also written fully qualified (`\strlen(`), not as a method or a static call. `ci-ratchets.sh --self-test` holds the cases of these four expressions and of `strict-types-missing` and `guide-future-tense`: add the row, then run it.

   The three rows read the guard tests too, where example text (YAML, PHP source in a string) is counted as code. The kit's start does not exclude those folders: a project found real byte-string calls among the hits of its guard folders (18), so an exclusion that is not checked hides code. Where every hit in `tests/Guards` and `tests/Support/Architecture` is text (read each hit: `git grep -n -E -e '<expression>' -- tests/Guards tests/Support/Architecture`), the project adds `:(exclude)tests/Guards,:(exclude)tests/Support/Architecture` to the paths of that row only, as a change of the table (`[ratchet: script] <reason>`), and one case in an excluded folder to `--self-test` (`<row>@/tests/Guards/Fixture.php 0 <the text>`).

   One row of the same kind goes in later: `model-strictness-violations  max  grep  <the counted list of step 4>  ^.` with the recording PR of step 4.
7. The guides get one row in step 3, with the same name in every project: `guide-future-tense  max  grep  <every AGENTS.md and the review rubric, as a comma list>  (^|[^A-Za-z])([Ww]ill|[Ff]or now|[Uu]ntil)([^A-Za-z]|$)`. A guide describes the final state, so the row goes to 0.
8. The ignore list of the unused-code tool has the same name in every project, in the form its config allows. A JSON config (knip's `knip.json`): `unused-ignore  max  json  <the tool's config>  count? <key of the list>`, one row per list key when the tool has several. A PHP config (composer-unused's `composer-unused.php`), which the `json` method cannot read: `unused-ignore  max  grep  composer-unused.php?  (NamedFilter|PatternFilter)::fromString`, one match per filter entry (the form the kit's `extra_rows` carries, with its cases in `--self-test`). Another PHP tool names its own filter calls in the expression. `queue-bus-fake-all  max  grep  @TEST_PATHS,:(exclude)*.md  (Queue|Bus)::fake(For)?\([[:space:]]*(\[[[:space:]]*\])?[[:space:]]*(\)|$)` is in `extra_rows` too, so both rows have fixtures: a row the kit names and the self-test has no case for fails it, and a project's own row without cases is listed as `no fixture for`.
9. Two package managers in one project (a PHP backend with a React frontend) keep the three dependency keys and the shown row `dependencies-behind`: each `COMMAND_ROWS` command adds up both managers. A command inside double quotes is expanded when the array is defined, so a command substitution is written `\$( ... )` there, or the whole entry is in single quotes (and then holds no single quote). Ready lines for the config block:
   - advisories: `audit-gate.sh` reads one manager's JSON (its `ID_PATTERN` is that manager's key). The second manager is a count added in the same row, for example `'dependency-advisories::online::echo $(( $(composer audit --locked --format=json --no-interaction | bash scripts/audit-gate.sh) + $(npm audit --omit=dev --json | json "value metadata.vulnerabilities.total") ))'`, until the project gives the gate a pattern per manager;
   - majors behind, npm: `npm outdated` prints one entry per package with `current` and `latest`, and the `json` helper cannot compare two fields, so use a one-line node count in single quotes: `'dependencies-majors-behind::online::echo $(( $(composer outdated --locked --direct --major-only --format=json --no-interaction | json "count locked") + $(npm outdated --json | node -e "let s=\"\";process.stdin.on(\"data\",d=>s+=d).on(\"end\",()=>{const o=JSON.parse(s||\"{}\");console.log(Object.values(o).filter(v=>v.current&&v.latest&&v.current.split(\".\")[0]!==v.latest.split(\".\")[0]).length)})") ))'`;
   - `npm outdated` and `npm audit` exit 1 when they find something: the dashboard runs the command without `pipefail` and reads the printed number, never the status, so no `|| true` is needed (and one in a script counts in `ci-skipped-steps`).
   Composer: add `--abandoned=report` to `composer audit` in the checks line, or an abandoned package fails the audit (the dashboard caps abandoned packages in their own row).

10. `autoload-conformance` is a dashboard counter with a command, not a pattern in the files, so it is a `COMMAND_ROWS` row with a cap, like the CI duration of point 3: the key `autoload-conformance` in the caps file, the row `cap-autoload-conformance  max  json  @CAPS_FILE  value autoload-conformance`, a `ROW_ADVICE` line (`"autoload-conformance::move or rename the class to the name its path says, or the file to its class"`) and a `COMMAND_ROWS` line `"autoload-conformance::always::<command>"`. The command is `composer dump-autoload -o --dry-run --no-scripts --no-interaction 2>&1 | grep -c 'psr-4'`: it prints how many of its lines say that a class does not comply with the PSR-4 standard (Composer 2.11: `Class X located in ./app/Y.php does not comply with psr-4 autoloading standard`; verify the wording against the installed Composer in step 2). `--dry-run` writes nothing: without it the command rewrites the autoload files in `vendor` (the row is `always`, so also in `--offline`), and a run from a copy whose `vendor` is a link re-points the real classmap at the copy and every later coverage run reads 0%. Verified: `find vendor -newer <marker>` lists nothing after a `--dry-run` that printed the warning. Never use the command without `--dry-run`. `--strict-psr` with `--dry-run` exits 1 on a violation, but it gives no number for a cap; a class that the autoloader skips is only logged, never failed, so the number is the only place it shows. It starts at the measured value in step 2 and goes to 0.

### A counted list in a row that is at 0

A `max` row at 0 takes no override (`OVERRIDE_AT_ZERO` names the three that do), so a list that arrives later cannot go into it: `lint-baseline` and `type-baseline` start at 0 and the first strict lint or unused-code list is a move from 0 to N, which fails. The mechanism is a rename, not a start value:

1. In the pull request that introduces the list, rename the row in the table (`lint-baseline` to `lint-suppressions`, `type-baseline` to `keyed-baselines`) and keep its paths and expression. On the base the old name stands at 0, so its removal is free (`removed at 0`); the new name does not exist there, so it is a first measurement (`new row`) at N, and from then on it only goes down.
2. No tag is needed for either half. Name the old row, the new row and the list in the commit message, so `git log` tells the reader why the row moved.
3. Add a case for the new row to the `--self-test` cases if its expression differs, and put the new name in the caps and in `ROW_ADVICE` only where the project has a cap or an advice line of that name (the ratchet rows themselves need neither).
4. The list is generated by the tool (`keyed-baseline.sh --init`, or the linter's bulk-suppress), never edited by hand; at zero the file is deleted with its line in `checks.sh`, and the row stays at 0.

This is the same rule as for a cap such as `cap-dependencies-abandoned`: a row that is new on the base is measured, not compared. The alternative, a one-time `[ratchet: <row>]` start value on a row that is at 0, is not offered: it would make every row at 0 raisable once, which is the hole `OVERRIDE_AT_ZERO` closes. Proven by the scenarios `PT14` to `PT17`.

### Coverage

The test step measures the coverage and holds it at the committed floor:

- PHP, in Pest and in PHPUnit: the test runner's own coverage with `pcov` as the driver writes a clover report (`--coverage-clover <file>`), and the next line of the test step is `bash scripts/checks.sh --coverage <file>`. It fails when the statements of the report's project metrics are below the line `threshold: <number>` of `scripts/coverage-floor.txt` (row `coverage-floor`), and prints the number to raise the floor to. The two lines are the composer script `test:unit`. The floor file is the one number: the test runner gets no minimum of its own (`--min`, `--exactly`), which would be a second place to change.
- React frontend: vitest's own `coverage.thresholds` in its committed config; the row is `frontend-coverage-floor`. A frontend has two numbers there: the threshold of the whole frontend, and a threshold keyed by the glob of the logic folders (hooks, utils, lib), which the row `frontend-logic-coverage-floor` holds. The glob-keyed form (`thresholds["<glob>"]`) was seen to work on vitest 5 in a real run; verify in step 1 against the installed version, and on any other runner. The row `frontend-logic-coverage-floor` is not in the start set: the project adds it with the committed threshold (`MIN_ROW_TARGETS` names it, and `--final` fails a name without a row).
- The end goal: `--final` fails `coverage-floor` and `frontend-logic-coverage-floor` below 95 (`MIN_ROW_TARGETS`). The floor reaches 95 by being raised to the measured value at the end of each step, never by writing 95 in the file ahead of the tests.

The `--coverage` line is proven against a clover file written by hand, not against a real coverage run.

### Mutation

The floor is one file in every project: `scripts/mutation-floor.txt`, one line `threshold: <number>`, held by the row `mutation-floor` ("Adding a row", point 4). Below, `<floor>` is `$(sed -n 's/^threshold: //p' scripts/mutation-floor.txt)` and `<changed>` is the comma list of `git -c core.quotePath=false diff --no-renames --name-only --diff-filter=AM "origin/$CHECK_BASE"...HEAD -- <source folders>` (`--no-renames`: a renamed and edited file is a changed file; `core.quotePath=false`: a non-ASCII path is passed as it is); the list keeps the files that match `MUTATION_FILE_PATTERN` and not `MUTATION_EXCLUDE_PATTERN` of the config block (source files of PHP and TypeScript/JavaScript, no test file: Stryker stops with an error on a `.css` and mutates a test file it is named, which is a false score); a pull request that changes no such file skips the run. Per tool: the whole-tree run of the scheduled job, then the run on a pull request, from step 9 on. The pipeline calls `bash scripts/mutation.sh` (whole tree) and `bash scripts/mutation.sh --changed`, never an inline command; the script holds the commands below and reads the floor file.

- **Pest**: `vendor/bin/pest --mutate --everything --parallel --processes=<n> --min=<floor>` and `vendor/bin/pest --mutate --parallel --processes=<n> --path=<changed> --min=<floor>`, with `<n>` the `MUTATION_PROCESSES` of the script (default 4: without `--processes` Pest starts one worker per core, and on a 12-core machine the same code scored 75% with 29 untested and 10 timeouts, against 94.59% with 4; raise it only on a runner that holds the score at the floor). Verified on Pest 5.3.7 (2026-11-26, PHP 8.5.12, pcov 1.0.12): `--mutate`, `--everything`, `--parallel` and `--min` are in `pest --help` ("MUTATION TESTING OPTIONS"); a run below `--min` prints `FAIL  Mutation score below expected: 62.5 %. Minimum: 95.0 %.` and exits 1, at or above it exits 0; `--path` takes a comma list (`--path=src/Calc.php,src/Other.php` mutated both files), a repeated `--path` keeps only the last. Without `--everything`, `--path` or `--class`, Pest mutates only what a test declares with `covers()` or `mutates()`, and otherwise answers "Mutation testing requires the usage of the `covers()` function" with exit 1. A run on a sample, as run in one project on Pest 5: `vendor/bin/pest --mutate --parallel --processes=6 --passthru-php="'-d' 'memory_limit=-1'" --path=<the ten files>`. It needs a coverage driver (`pcov`); without the memory passthrough the workers die at 128 MB with "Premature end of PHP process", which reads like a crash of the tool. The summary lines are `Mutations: <n> uncovered, <m> tested` and `Score: <x>%` (ten classes: 335 s wall, 32 s of it mutating); uncovered mutations count in the score. The workers are separate PHP processes: a driver loaded only with `php -d extension=...` on the command line is not loaded in them ("One or more workers failed to generate coverage files"); put it in the ini, or pass `--passthru-php="'-d' 'extension=<file>'"`.
- **Infection** (a PHPUnit project): `vendor/bin/infection --threads=<n> --min-msi=<floor>` (`<n>` is `MUTATION_PROCESSES` too) and the same with `--git-diff-filter=AMR --git-diff-base=origin/$CHECK_BASE`. Verified on Infection 0.35.12 with PHPUnit 13.4.8 (2026-11-26, PHP 8.5.12, pcov 1.0.12): `--threads`, `--min-msi`, `--git-diff-filter` and `--git-diff-base` are in `infection --help`; `--min-msi=90` with an MSI of 80 prints `The minimum required MSI percentage should be 90%, but actual is 80%.` and exits 1; `--git-diff-base=origin/main` (a remote-tracking name) works. On a branch that renamed and edited a file, `--git-diff-filter=AM` printed "Could not find any modified files in the configured sources" and exited 0 (a green run that mutated nothing), while `AMR` mutated the file: `R` is needed. Infection needs a coverage driver (pcov or Xdebug); a driver loaded only on the command line needs `--initial-tests-php-options="-d extension=<file>"`, a driver in the ini needs nothing, and without one Infection stops with a PHPUnit warning "No code coverage driver available". Not verified: Infection with Xdebug or phpdbg (only pcov was built on the machine of the check), and `--git-diff-lines`. Infection is installed through a Composer plugin: `composer.json` must hold `config.allow-plugins.infection/extension-installer: true` (`composer config allow-plugins.infection/extension-installer true`, before `composer require --dev infection/infection`), or Composer blocks the plugin and the binary is not set up. `mutation.sh` fails with that instruction when `MUTATION_TOOL` is `infection` and a `composer.json` is there without the line. Never pipe the output of `composer require` or `composer install` into `head`: the closed pipe aborts the install half way. Infection needs a coverage driver (pcov or Xdebug); a driver loaded only on the command line needs `--initial-tests-php-options="-d extension=<file>"`, a driver in the ini needs nothing, and without one Infection stops with a PHPUnit warning "No code coverage driver available". Not verified: Infection with Xdebug or phpdbg (only pcov was built on the machine of the check), and `--git-diff-lines`.
- **Stryker** (TypeScript, vitest): `npx stryker run`, and the same with `--mutate <changed>` (the comma list as one argument). Verified on Stryker 10.1.1 with `@stryker-mutator/vitest-runner` 10.1.1 and vitest 5.1.2 (2026-11-26): `stryker run --thresholds.break 40` is rejected ("unknown option"), so the break threshold has no command-line option; `thresholds: { break: <N> }` in the config works: below it the run prints `Final mutation score 47.37 under breaking threshold 60, setting exit code to 1 (failure).` and exits 1, at or above it `... is greater than or equal to break threshold 40` and exit 0. `mutation.sh` sets the environment variable `MUTATION_FLOOR` from the floor file and `stryker.config.mjs` reads it (`thresholds: { break: Number(process.env.MUTATION_FLOOR) }`; unset it is `NaN` and Stryker refuses to start, an empty one is a threshold of 0), so the floor file stays the one place of the number. A config that ignores the variable holds no floor and exits 0 below any score, so `mutation.sh` also requires the output of the run to name the floor (`break threshold <floor>` or `breaking threshold <floor>`) and fails when it does not. `--mutate a.ts,b.ts` mutated both files. `--mutate` replaces the `mutate` list of the config with its `!` exclusions, so a named test file is mutated, and a file Stryker has no parser for (`.css`) stops the run with an error: `mutation.sh` filters the list (see above). The values are globs: `src/[id].ts` and `src/(grp)/page.ts` match nothing, even escaped with a backslash, while `src/?id?.ts` and `src/?grp?/page.ts` match, so `mutation.sh` writes `[ ] ( ) { } * !` as `?`. A glob that matches no file is no error: Stryker mutates nothing and scores nothing, which the floor check above catches. Not verified: a path with a comma in it (it would split the list) and runners other than vitest.

Everything above was run with the tools named in scratch projects; the recorded outputs are in `tools/proof/fixtures/real/`, and the scenarios `VX15` to `VX24` of the proof run `mutation.sh` against them with a fake `npx` and fake `vendor/bin` scripts that print the recorded output. The proof does not run the mutation tools themselves.

`mutation.sh --changed` takes the changed files of the source folders only and skips test files, so a branch that only adds or changes tests mutates nothing: it prints "this pull request changes no source file; nothing to mutate" and exits 0. That is a pass with no evidence about the new tests. For such a pull request the author runs a sampled mutation run over the source the tests cover, with the tool's own filter, and puts the score in the pull request description: Pest `vendor/bin/pest --mutate --parallel --processes=<n> --filter=<test name or class> --min=<floor>`; Infection `vendor/bin/infection --threads=<n> --filter=<source file> --min-msi=<floor>`; Stryker `npx stryker run --mutate <source file>`. Whether each option selects what a test-only branch needs was not run here (unverified): read the tool's `--help` first. The reviewer's break sample (`09-reviewer-brief.md`) is the check the pipeline does not make.

A whole-tree run that does not fit the maximum time of one job is split by module over parallel jobs of the scheduled run; the floor is the lowest score of the parts.

## `debt-dashboard.sh`

Every counter in one table: the ratchet rows (from `ci-ratchets.sh --head`), the row `files-outside-row-paths`, and the rows it measures itself. It counts tracked files only.

| Row (and caps key) | Counts |
| --- | --- |
| `source-files-over-limit`, `frontend-files-over-limit`, `test-files-over-limit` | files over `MAX_LINES` |
| `open-classes` | source files with a line that matches `OPEN_CLASS`: a concrete class declared without the closing keyword (indented, or after an attribute on the same line, too). An abstract class is not counted; a concrete class that another class extends is, like any other open class. It is the counter of the formatter rule that closes classes (`05-program.md` D8) |
| `classes-no-test-names` | behavior classes that no test file imports or names before `::`. An import is a line with `use`, `import`, `from`, `export ... from` or `require(`; the name is the last part of the imported path, with and without its extension, so `use App\Actions\CreateOrder;` and `import { createOrder } from "./create-order";` name `CreateOrder.php` and `create-order.ts` |
| `classes-without-own-test`, `support-classes-without-own-test` | classes without a test file named `<Class><TEST_NAME_SUFFIX>`: `CreateOrderTest.php` for `Test`, `create-order.test.ts` for `.test`. A file that matches `TEST_FILES` is never counted as a class |
| `frontend-logic-without-test`, `frontend-components-without-test` | files without a `<file>.test.*` next to them |
| `docs-older-than-limit` | docs whose last change is older than `DOCS_MAX_AGE_DAYS`. A repository whose first commit is younger than the limit cannot have such a doc: the row reads 0 and the run prints `docs-older-than-limit cannot fire before <date>`, so 0 is not read as "the docs are fresh" |
| `dependency-advisories`, `dependencies-abandoned`, `dependencies-majors-behind` | the `COMMAND_ROWS` of the config block: each is a command that prints one whole number |
| `dependencies-behind` | the same, as the one `shown` row: packages a minor or patch version behind. It has no cap and never fails; the updates are the dependency bot's work |

`--counted` lists, under each test row, the files it counted (the "of N" set); every run ends with one line of the four counts. A row that reads low or 0 is usually an expression that misses a folder: the example values name the kit's folders only, and in the first real project the kit's folders alone counted 15, 21 and 10 files where today's folders held 40, 69 and 15. Read the lists before trusting a number, and add today's folders as alternatives until step 5 has moved the files. `FRONTEND_LOGIC` is every TypeScript file (`.ts`) in any folder under the frontend root, plus `use-*` hooks in `.tsx`; `FRONTEND_NOT_COUNTED` takes out tests, stories, declarations, mocks and `types/`; what remains in `.tsx` is a component.

The frontend test rows count every file that matches `FRONTEND_LOGIC` and `FRONTEND_COMPONENTS`, so pages, entry points (`app`, `ssr`), vendored UI primitives and test helpers count too unless `FRONTEND_NOT_COUNTED` names them by category; a project decides in step 1 whether primitives are covered by stories or by tests, and keeps helpers in a folder the expression excludes (`test/mocks/`).

Blind spots: two classes with the same name in different folders count as one for the test rows; a test file found by name may sit in any test folder; a class is matched by its file name; an import of `./order.service` also names a file called `order`; an attribute with a `]` inside its arguments in front of `class` hides the class from `open-classes`, and a line of a multi-line string that starts with `class` counts as one.

### Modes

The rules of the gate, of `--final` and of the caps are `04-guards.md` C3; this is what the script prints.

- **Default, the gate.** A measured row above its cap is `OPEN`. A ratchet row has the status `held`. A row below its cap passes and says "lower the cap to N". The row `files-outside-row-paths` has no cap: it must be 0 in both modes.
- **Every `OPEN` row is followed by one line, "do this: ..."**: what brings the row to its target. The lines of the rows that ship are in the script; a row the project adds takes its line from `ROW_ADVICE`.
- **`--final`.** Every row must be at zero: ratchet `max` rows, caps and measured rows. A cap that is above its row fails with "the cap N is above the row". The rows in `SHRINK_ONLY` are shown as `shrink-only`: a ratchet row by its name, a cap as `cap-<key>` (its measured row is then held to the cap and prints `ok (shrink-only by a decision row: held to the cap)`). An abandoned package that a tool the kit prescribes requires, with no replacement yet, is the typical case: a decision row, the cap `dependencies-abandoned` at the measured number, `cap-dependencies-abandoned` in `SHRINK_ONLY` (the owner's approval and an end date, `01-principles.md` "Shrink-only rows"). Which rows may be in it: `01-principles.md`, "Shrink-only rows". A `min` row is `held`, except the ones with an end goal: `analyser-switches` fails below `ANALYSER_SWITCHES_TARGET`, and a row named in `MIN_ROW_TARGETS` fails below its number there; each prints `UNKNOWN` when the goal is no number, and a name in `MIN_ROW_TARGETS` without a ratchet row prints `UNKNOWN (no ratchet row ...)`. In the gate such a row is `held` and shows its goal in the target column.
- **A `shown` row** (`dependencies-behind`, and no other) is printed with its value in both modes, skipped by `--offline`, and never fails.

`UNKNOWN` is printed, and fails both modes, for: a row that cannot be counted (`ci-ratchets.sh --head` prints why); a measured row whose key is missing from the caps file; a caps key without its `cap-<key>` ratchet row; a caps key that no dashboard row measures; a caps file that cannot be read; a `COMMAND_ROWS` key of the project's own without a line in `ROW_ADVICE`.

**Not measured is never 0.** A `COMMAND_ROWS` command that reads the installed packages prints an empty list when the folder is missing, and the row would read 0: an auditor with no `node_modules` saw `dependencies-majors-behind` at 0 and nearly lowered its cap. Before it runs a command, the dashboard looks for what the command needs: `node_modules` (a command with `npm`, `pnpm` or `yarn` and `outdated`, `ls` or `list`, or with `npx`, or that names `node_modules/`), `vendor` (a command that names `vendor/bin/`, or `composer outdated` or `composer show` without `--locked`), and the package managers `composer`, `npm`, `pnpm` and `yarn` themselves (a sum of two counts reads the missing one as 0). A folder that is absent or empty, or a manager that is not installed, makes the row `UNKNOWN (not measured: <what is missing>)`: it fails the gate and `--final`, and prints no "lower the cap" line, because a cap is lowered only to a measured number. A `shown` row prints `not measured (...; never fails)`. A command that reads the lock file (`composer outdated --locked`, `npm audit`) needs no folder. The ratchet rows read the commit's files with `git grep`, so no folder can make them 0; a row that needs `jq`, `node` or `php` and finds none is `?` (`ci-ratchets.sh --head` says why). Run `--final` after an install: the scheduled job and an auditor install first.

| `MAX_LINES` | the kit's limit for a file, 400 |

The default scope of `SOURCE_FILES` covers the same folders as `SOURCE_PATHS` of the ratchet script (`app`, `bootstrap`, `config`, `database`, `routes`, `lang`, `resources/views`; the rows read tracked files only, so the generated `bootstrap/cache` is never counted, and the analyser and refactoring paths, which read the disk, name `bootstrap/app.php` and `bootstrap/providers.php` instead of the folder); a project changes `SOURCE_PATHS` and `SOURCE_FILES` together, and `--uncovered` lists what lies outside; a long config file is a source file. The numbers are the kit's. A project removes the entry of a row whose subject it lacks, or lowers the number where the subject exists only in part: the organisation hosts the formatter config and it lacks rules, so `formatter-rules` is held at the number the hosted config has, with the decision row of every missing rule in the plan. The command prints one whole number on one line; anything else (text, two lines) is `UNKNOWN`. `json '<operation> <path>'` is available in it. This is where a project puts its package manager, and any counter of its own (CI minutes, a count from a tool's report). The dashboard script holds no number and no file name outside its config block.

Every expression of the block is compiled once at the start: an invalid one stops the run with exit 64, so a typo cannot make a row read 0. A skipped row names its reason (`skipped (--offline)`, `skipped (shallow clone)`). `docs-older-than-limit` dates a doc by its last commit, so in a shallow clone the gate skips it and `--final` prints `UNKNOWN (shallow clone ...)`: the scheduled run fetches the full history.

The dashboard reads the ratchet rows at the last commit and its own rows from the working tree, so run it on a clean tree.

## `debt-caps.json`

One object, key to whole number. Every key is a dashboard row and has a `cap-<key>` ratchet row. The rules of a cap (it only goes down, the tag that raises it, the lead lowers it to its row at the end of every step) are in `04-guards.md` C3.

## `audit-gate.sh`

`composer audit --locked --format=json --no-interaction | bash scripts/audit-gate.sh` (the audit of each package manager, as JSON). It prints one whole number, the advisories that no active exception covers plus the broken entries of the exceptions file, and exits 1 above 0: the same line is the `Audit` task of `checks.sh` and the command of the dashboard row `dependency-advisories`.

The exceptions file is `scripts/audit-exceptions.json`, one entry per line so a reviewer reads one line: `{"id": "<advisory id>", "reason": "<why the code path is not reachable, or what mitigates it>", "added": "YYYY-MM-DD", "expires": "YYYY-MM-DD"}`. An entry fails the gate when a field is missing, a date is not a date, `added` is in the future, `expires` is more than `MAX_DAYS` (7) after `added`, `expires` is in the past, or the id is listed twice. An exception is never renewed: it is replaced by the fix, and the line is deleted with it. Input that is not one complete JSON document with the advisories key (empty, truncated, an error object) fails too, so a crashed audit is not a green one. An advisory id that the audit lists twice counts once; an `id` with a space, a reason of spaces and two entries on one line are broken entries. Dates are UTC (`added` and `expires` are UTC days, as in the dashboard header).

What it cannot see: that `added` is the real day (a reviewer reads the commit date), and that the reason is true. `EXCEPTIONS_FILE` and `MAX_DAYS` are in its config block. `DOCUMENT_PATTERN` is the key a complete audit holds (Composer: `"advisories"`); `ID_PATTERN` is Composer's `advisoryId`; for another package manager it is the key of the audit's JSON that holds one advisory id (verify in step 1 that it appears once per advisory). `AUDIT_GATE_TODAY` sets the date for the proof.

## `ci-commit-messages.sh`

One form: `<TICKET> <type>[(scope)][!]: <subject>`, for example `PROJ-123 feat: add the export`. The config block holds `TICKET`, an expression such as `PROJ-[0-9]+` (a project without a ticket system sets its fixed prefix, `TICKET='NOTICKET'`); `TYPES`, the accepted types (`feat`, `fix`, `refactor`, `test`, `docs`, `chore`, `style`, `ci`, `perf`, `build`, `revert`); and `EXAMPLE`, the example the failure message prints. `TICKET` and `EXAMPLE` ship as placeholders, and the script refuses to run with one. `GENERATED`, also in the config block, is the pattern of the titles that pass without the form; a project that keeps a tool-made title adds its exact text there, with the script tag. The base branch and the remote come from `kit-config.sh`. `type(TICKET): ...` is not accepted.

These pass without the form: a commit with more than one parent, a revert whose quoted subject has the form (`Revert "PROJ-1 feat: x"`, `Reapply "..."`, also nested; the quote must end the subject, and a revert of a subject without the form is rejected), and the subjects that match `GENERATED` over the whole subject (the default `^$` matches none). `Merge branch ...`, `Merge pull request ...`, `Merge <sha> into <sha>` and `Merged in ... (pull request #N)` are not listed: they are merge commits, which have two parents and are skipped, and on a commit with one parent they would hide work behind a generated-looking title.

It reads the commits between the base and the head. With no base branch in CI it fails. It deepens a shallow clone and fails when it cannot. What landing it does to open branches and bots: `07-process.md` section 10.

## `ci-parallel.sh`

`bash scripts/ci-parallel.sh "Name::command" "Name::command"`. Each command runs in its own process group with its output in a file; the output is printed under the name when the command ends; a summary of `PASS`, `FAIL` and `TIMEOUT` closes the run. Any failure fails the run. A command over the limit is stopped with its children and reported as `TIMEOUT`. The config block holds `DEFAULT_TIMEOUT` (600 seconds; `CI_CHECK_TIMEOUT` overrides it for one run) and `GRACE`, the seconds between stop and kill; both are whole numbers of seconds, or the run fails with 64. A task without `::`, with no name or with a blank command fails with 64 before anything runs (a command that expanded to nothing is not a green check). Stopped with INT or TERM, it stops every command and every watchdog. It needs no `timeout` and no `wait -n`, so it runs on macOS bash 3.2; the copy in the starter's `scripts/` is this file.

## `keyed-baseline.sh`

`bash scripts/keyed-baseline.sh <baseline file> --format <name> -- <command>`, as a line of the parallel call in `checks.sh`, one line per check: one per type-checker flag that is not at zero yet, and one for the unused-code tool. Examples: `"Flag noUncheckedIndexedAccess::bash scripts/keyed-baseline.sh baselines/no-unchecked-indexed-access.txt --format tsc -- npx tsc --noEmit --noUncheckedIndexedAccess"` and `"Unused code::bash scripts/keyed-baseline.sh baselines/unused-code.txt --format knip -- npx knip --no-progress"`.

- `--format` names the tool whose output the command prints; it is required. The config block holds, per name in `FORMATS`, three values and an optional fourth: `FINDING_<name>` (the output lines that are findings), `NORMALIZE_<name>` (a `sed -E` expression that removes line and column numbers), `SECTION_<name>` (empty, or the expression of a heading line: a finding is then written as "heading: finding", so one line under two headings is two findings; with a section expression, a line before the first heading is no finding) and `SKIP_<name>` (optional: a heading whose lines are not findings). Two formats ship: `tsc`, the TypeScript compiler (a finding has a position, `file(1,2): error TS1234` or `file:1:2 - error TS1234`; a start-up error without one is no finding, so the run fails), and `knip`, the unused-code tool in its default reporter (a heading per kind, one line per finding). A tool with another output gets its own values and its name in `FORMATS`.
- It runs the command, keeps the findings, normalizes and sorts them, and compares them with the file. A finding that occurs twice is two lines.
- It fails on a finding that is not in the file ("fix them; a line is never added") and on a line that is no longer found ("drop them by running this command with --write"). It fails when the command fails without a finding, so a crashed tool does not read as zero findings.
- `--init` writes the file from the findings: step 2 writes each file once with it. `--write` rewrites an existing file and only drops fixed lines: it refuses (exit 1, the file untouched) when the command prints a finding the file lacks, and a missing or empty file lacks every finding, so it needs `--init`. The ratchet row `type-baseline` counts the lines of every file under `KEYED_BASELINES` and fails a file that grows.
- At zero the file is deleted with its line in `checks.sh`, and a flag goes into the config, where `analyser-switches` holds it.
- The `knip` format drops the tool's "Configuration hints" section (`SKIP_knip`): those lines are not findings, so fix the hints in the tool's config first. Verified against knip 6.48.0 and TypeScript 7.0.2 (2026-11-26, real runs in a scratch project, recorded in `tools/proof/fixtures/real/`, scenarios `VX01` to `VX14`): knip prints a heading per kind (Unused files, Unused devDependencies, Unlisted dependencies, Unresolved imports, Unused exports, Unused exported types, Configuration hints), a line per finding with its columns padded, exit 1 on findings, **no output at all and exit 0 on a clean run** (the "Excellent, Knip found no issues." line of older versions is gone; zero findings is the empty output), exit 0 with only the hints, exit 2 with an `ERROR:` line when its config cannot be read (the script then fails: a crashed tool is not zero findings). The padded last column leaves a trailing space after `file:line:col`; the normalizer removes it first, or the position stayed in the key (found with the real output). A kind of finding that knip 6 does not report by default (class and enum members) is not in the baseline. For `tsc` the plain output of `--noEmit --noUncheckedIndexedAccess` gives `file(line,col): error TSnnnn`, the continuation lines are indented and no findings, and `--pretty` (colours even into a pipe, and `file:line:col - error`) gives the same keys: the script strips colour codes and writes ` - error` as `: error`, so a baseline survives a change of `--pretty`. A start-up error (`error TS5058`, `error TS5023`) has no position and fails the run. Not verified: other knip reporters (`--reporter json` and others are not parsed), `knip --production`, and a workspace project (headings per workspace).

## `move-ts.mjs` and `map-normalise.sh`

`node tools/codemods/move-ts.mjs <moves.tsv> [--reverse] [--verify] [--alias @=src] [--roots src,tests]`: for each map line `git mv` of a file still at its old path, then a rewrite of the specifiers in the tracked files under the roots. A file that moved gets its relative specifiers recomputed from its new folder; an importer of a moved file gets the new specifier; an alias specifier follows. The map may have CRLF line ends. Before the first `git mv` every line is checked: a `from` that is not tracked, a `to` that already exists next to its `from`, or two lines with one `to` stop the run with exit 1 and nothing moved. The rewrite covers `from`, `import()`, `import` for side effects, `require()`, `require.resolve()` and the calls `mock`, `doMock`, `unmock`, `doUnmock`, `importActual`, `importMock`, `requireActual`, `requireMock` and `setMock`, and `new URL(...)`; a specifier in double quotes, single quotes or a template literal without `${...}` is rewritten (a template literal with `${...}` is built at run time and left alone); paths are read with `-z` and unquoted, so non-ASCII names work. A second run changes nothing; `--verify` exits 1 when an old path exists, a new path is missing, a specifier names an old path, or a moved file has a relative or alias specifier that names no file (a half move). `--reverse` swaps the columns; a forward and a reverse run are valid but not byte-identical (`"../a"` becomes `"./"`, an `/index` is dropped). A path built from a string at run time is the text pass of the move (`05-program.md` D9). `bash scripts/map-normalise.sh <moves.tsv> [--forward] < dump > normalised`: see its header.

## `ci/`

- `checks.sh` is the one command; what it runs and in which order is in `04-guards.md` C4. Its config block holds `DASHBOARD_MODE` (empty, and `--final` from the exit of step 10 on) and `COVERAGE_FLOOR_FILE`; the base branch and the remote come from `kit-config.sh`. Every `<placeholder>` is the project's command; the script refuses to run while one is left outside a comment line in it, in `kit-config.sh` or in the config block of the commit-message check, and names the file and the line. The guard tests line is the test runner's command for the guard group and nothing else (PHP: `--group arch` in Pest and in PHPUnit; vitest: the guard project or folder). The secret scan line is `gitleaks` over every commit between the base and the head. The `Audit` line has two forms: the full audit, and in `--main` (a deploying branch) the production dependencies only (`04-guards.md` C4, point 21). The project adds its other whole-tree checks to the `TASKS` list. In a PHP project the lines are the commands of the composer scripts (`catalog/tests-database-ci-docs.md`, "Composer scripts"): `Format` is the formatter with `--test` (and the frontend formatter's check as a line of its own), `Refactor` is the refactoring tool with `--dry-run`, `Analyser` is the analyser (and the type checker as a line of its own), `Type coverage` is the command of `test:type-coverage`, and the project adds `Manifest floor::composer bump --dry-run`, which exits 1 while a requirement is behind. It calls the tools as `scripts/ci-ratchets.sh`, `scripts/debt-dashboard.sh`, `scripts/ci-parallel.sh` and `scripts/ci-commit-messages.sh`.
- `PARTS` in the config block groups the tasks, one entry `<part>::<task names split by a vertical bar>`; the script stops when a task is in no part or in two, so a split pipeline cannot drop a check, and `--part gate` runs the guard of the ratchet script, the ratchets and the dashboard. The `Commit messages` and `Secret scan` tasks exist in a pull-request run only.
- It stops, and says so, when the base cannot be fetched, and when a CI run has no base branch and is not `--main` and the run reads the base. A part that reads no base (`static`, `guards`: no `Commit messages` or `Secret scan` task) runs in CI with no `CHECK_BASE`, no pull request and no `--main`, so a scheduled or manual run can call `--part static` as it is. **No remote:** on a developer's machine, in a repository with no `REMOTE` (a fresh `git init`), the local branch `DEFAULT_BASE_BRANCH` (or `CHECK_BASE`) stands in for `REMOTE/<base>` (`kit_local_base` in `kit-config.sh` writes it to `refs/remotes/<REMOTE>/<base>`), so the ratchets, the commit-message check, the guard and the secret scan run against it. On that branch itself nothing differs from the base: work on a branch to compare. With no remote and no such local branch the run fails with "no base, so the script guard cannot run". In CI the stand-in is never made: a CI run without a remote has no base and fails.
- The three pipeline files hold the five runs of `04-guards.md` C4. A repository that already has a Bitbucket or GitLab pipeline takes their steps and jobs into its own file; on GitHub the skeleton is a file of its own, `.github/workflows/kit-checks.yml`, and the existing workflow is not edited (`05-program.md` D2, step 2; `04-guards.md` C4).
- `prepush.sh` fetches the base once and then runs every part side by side; it takes `--main` or nothing. `checks.sh` takes its flags in any order (`--main`, `--scheduled`, `--coverage <file>`, `--part <name>`, `--list-parts`) and rejects a combination it does not list: `--part` goes with a pull-request run or `--main` only, the rest stand alone. A part fetches the base only when it reads it.
- `CODEOWNERS.example` covers the files that carry the guards with a code-owners rule (`04-guards.md` C4, point 22; `07-process.md` section 12); copy it to the host's path and replace `<owner>` with people or teams.
- A drift check of a generated file (a typed client, a route list) in a `TASKS` line generates the file to a temporary path and compares it with the committed copy: `gen --out "$tmp" && cmp -s <committed file> "$tmp"`. A line that asks version control for a diff reads as a check over changed files, and the contract test over `checks.sh` fails it, even when it only compares a generated file.
- The test step of a pull request in the skeletons sets `CHECK_BASE` from the host's variable, for `mutation.sh --changed`.

## `doctor.sh`

Which of the kit's scripts in a project have drifted from the kit's copy, and how to bring them back (`UPGRADING.md` has the whole procedure). In the project: `bash scripts/doctor.sh --kit <kit folder> [--json] [--upgrade-plan [--apply]]`; from the kit: `bash tools/doctor.sh --project <project folder>`. For each of `ci-ratchets.sh`, `debt-dashboard.sh`, `ci-commit-messages.sh`, `ci-parallel.sh`, `keyed-baseline.sh`, `audit-gate.sh`, `mutation.sh`, `checks.sh`, `prepush.sh` and `kit-config.sh` it compares the body with the kit's copy and ignores what the project owns: the config block, the rows of the ratchet table and the commands of the task lines of `checks.sh` (the commands the kit itself puts on those task lines are therefore not compared either). It reports `identical`, `config-differs` (the keys whose values differ, with the project's value and the kit's default), `body-differs` (line counts and the first lines of the diff), `config-holds-code` (the config block holds a line that is no assignment, comment or blank, or an assignment that runs something: `exit 0`, `X="a"; touch /x`, `X="$(id)"`; a divergence, with the lines shown), `missing` (an optional script is only listed) and `project-only`. A config key that only the kit has is a divergence (the script needs a value). A key that only the project has is the project's own addition when a row of its table or a task or the body outside the config block reads it (`@KEY`, `$KEY`): listed, kept, no divergence; any other project-only key is one the kit dropped or renamed: a divergence, and `--apply` keeps it too, at the end of the config block, with a note (a key is never dropped); where another kit script's config block defines the same key the report says so. A different value is not a divergence, unless the project's value, ratchet row or task line equals an older kit commit's and not the current one (status `kit-changed`, exit 1): the kit changed it, the project did not decide it, and `--apply` brings the kit's, and prints each such value as a conflict with the project's value and the kit's (a counted value such as `SOURCE_PATHS` or `REFACTOR_SETS` can move a ratchet row: run the gate); a value that carries a trailing comment with a reason (`KEY="..." # why`) is the project's decision and is never listed as the kit's change; a row the project edited itself equals no kit commit and is kept (without a kit git history the doctor lists the rows that differ and keeps them). A row the project defined itself (not in the kit's table or EXTRA rows, or different from them and equal to no older kit row) has its own self-test cases: the lines of that row in the `EXTRA` and `CASES` fixtures of `ci-ratchets.sh` are the project's, are not part of the body comparison, and `--apply` keeps them in place of the kit's (the report lists those rows). The task lines a project added to `checks.sh` are kept at their place (after the kit task line they followed) and are not a body difference. With `--kit` a git clone, it names the newest kit commit whose bodies equal the project's (`matches kit v0.9.0 / commit abc1234`), or says `diverged: body edited locally`; "behind" counts only kit commits that changed `tools/` or `ci/`, and a shallow kit clone is named as the reason no version is found (fetch its full history). Exit 0 when nothing diverged, 1 otherwise, 64 on a usage error. `--upgrade-plan` prints the steps and the tag and code-owner reminder and writes nothing; `--apply` writes the kit's body with the project's config values, table rows and task lines put back (except those the kit changed since, see above), under `scripts/` only (code found in a config block is not carried over: the lines go, a value that ran something is the kit's default again). A changed script that `GUARDED_FILES` lists (by default every script but `prepush.sh` and `doctor.sh`) is a guarded file: the commit needs `[ratchet: script] <reason>` and a code-owner review. **Carried ratchet rows need their own tags:** a row that `--apply` takes from the kit changes the table, so the gate of the pull request fails it as `redefined, FAILS` unless a commit that touches the script carries `[ratchet: <row>] <reason>`; `--upgrade-plan` lists, and `--apply` prints at the end, one such line per carried row (`[ratchet: frontend-test-skip] take the kit's changed row from v<version>`) to put in the commit message next to `[ratchet: script]`; after `--apply` the list is read from the table before and after, so it names every row the new file changed, added or removed. `--apply` then runs the project's `debt-dashboard.sh --offline --report` before and after the change and lists the rows whose count rose, or that are new above zero (a path list or a definition the kit widened, such as `SOURCE_FILES` gaining `database/`, makes a row count more files); the project fixes them in the same pull request. Without a git repository, one of the three scripts, or `git`, or when the dashboard prints no rows, it says `not run` and why; `--upgrade-plan` alone names the step and changes nothing.

## Proof

`tools/proof/proof.sh` builds scratch repositories in a temporary folder and runs its scenarios against the scripts in `tools/` and `ci/`. Run it when the kit's scripts changed since its last run on this machine: `bash tools/proof/proof.sh /bin/bash` and, where `command -v bash` is another binary, `bash tools/proof/proof.sh "$(command -v bash)" other` (the second argument names the log). One run takes seven minutes or more: run the filter while developing, the full run before a release. `PROOF_ONLY='<extended regular expression on the scenario id>'` runs only the scenarios whose id matches (`PROOF_ONLY='^DX'` for the doctor, `PROOF_ONLY='^R0[1-3]'` for three ratchet scenarios); the others are not run and not counted. A filter that is no valid expression or matches no scenario id stops with exit 64 before anything is built (a typo is no green run). A check that writes files or commits, and that a later check reads, is a step (`PROOF_STEPS` in `proof.sh`): under a filter it still runs, silently and uncounted, so a filtered run gives the verdicts of the full run. When every selected scenario lives in a scenario file that builds its own scratch repositories (no `# proof-needs: main` in its head: `^DX`, `^GR`, `^RX`, `^VX`), the fixtures of `proof.sh` itself are not built. Any other filter builds them (about 25 seconds). Scenario ids are unique: a duplicate stops every run with exit 1. `PROOF_AUDIT=1` records the checks that change the scratch tree in `proof-steps-<label>.txt`: that list is where `PROOF_STEPS` comes from, to refresh after a scenario is added that a later one reads. `PROOF_LIST=1` prints the scenario ids (every check, `message_case` and loop-variable id) and runs nothing. Without them every scenario runs, as before; the exit status is 0 when no scenario that ran was wrong. The kit's own CI (`.github/workflows/proof.yml`) runs the full proof on Linux and macOS. It prints one line per scenario (scenario, expected, got, ok or WRONG) and exits non-zero when one is wrong: that table is the list of what is proven. It needs `jq` and `node`. Without `php` on the PATH the scenarios that count a NEON file are printed as "skipped: needs php" and the run still ends with 0 wrong; the scenarios that run no PHP run everywhere. The strictness rows are proven against the configs of `templates/tool-configs.md` themselves: the proof cuts the formatter and refactoring configs out of that file and counts them. What the proof does not do: it runs no real analyser, formatter, refactoring tool, coverage tool, unused-code tool or CI host, and it replaces the secret-scan line by `true`. `PROOF_OUT` names the folder for the scratch repositories, the full log and the table (default: a new temporary folder); `KIT` names the kit folder to prove (default: the one the file is in).
