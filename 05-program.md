# The program: ten steps

Skip a part of a step the project does not have. Never reorder across a dependency (D1). There is one standard and the program ends at step 10 with the definition of clean met: a project that has not reached it is not done, whatever steps it has finished.

## D1. Dependencies the steps encode

- The definition of clean is fixed before any code changes, or "zero" is declared against counters that miss half the debt.
- The platform is at the version floor before the checks go in: a check at its final strictness needs the versions the patterns need.
- Every check becomes whole-tree and blocking with a generated baseline **before** the burn-down: product work continues, and without the check the old way grows while you remove it.
- Dead code goes first: nobody formats, moves, types and splits what is then deleted.
- Migrations become independent of application classes before any class moves.
- Layout moves come before other code work, so later work lands in final places. A test moves with its class.
- Typed config comes before the analyser burn-down: many top-level errors sit on config lines.
- A split empties the size, method-length and single-use-trait lists in the same PR, so size is removed and not hidden.
- Authorization on the route comes before the route-permission list can empty.
- Frontend types generated from the backend wait for final backend names.
- A dependency upgrade is never mixed with a move. A major is its own PR. **"Do or pin each major" is a budget question, not a version bump**: a major can move the package's configuration (a config file that becomes a service provider, a changed module writer) and rewrite generated files (generated frontend types, DTO or resource classes: one first run needed real work for a type-generator major, including `readonly` types the generator now emits). Before the owner chooses, read the package's upgrade guide and count what it touches; a major that touches generated types is a PR with the generated files as their own commit and the frontend checks as part of its proof, or it is pinned with the reason and the date to look again in the decisions table.
- Tests go on the real path (real request, real middleware, real exception handler) before classes are closed for extension: both change what a test may double, and a fatal error in one hides the failures of the other.
- Classes are closed after the splits and merges of step 7, or the split undoes the work, and before the missing tests of step 9, so new tests are written against closed classes. A concrete class that another class extends becomes abstract, or its children are folded into it, before the closing rule goes on.
- A formatter rule that changes behavior, and the strictness of the models, land after tests are on the real path and hermetic: those tests are what shows the break. Each lands after a count of its sites to zero, so the PR that switches it on changes nothing that is still in use.
- The coverage goal of 95 is reached last, in step 9: before that, tests are moved, converted and rewritten, and the number means little.
- A check that fails every open PR when it lands waits for a moment with few open PRs (`07-process.md` section 10).
- Docs describe the final state, so the docs pass is last.

"Empty queue" means the program's own open PRs. Product PRs keep flowing; a big move is announced a day before and product branches rebase after it.

## D2. The steps

Every step ends with an "Exit:" line that names the artifact that proves it. The lead pastes that artifact into the step's row of the plan.

**1. Discover and define** (`02-step-1-discover.md`). Measurement, the catalog mapped onto the project, the start audit, the definition of clean. No code changes.
Exit: `zero-debt-plan.md` with section 4 signed by the owner and every question of 1.10 answered in the decisions table.

**2. Make the checks tell the truth.** Three kinds of PR, in this order.
- **First PR: the smoke suite, alone** (`catalog/tests-database-ci-docs.md`, "Smoke suite" and "Seeded test user"): the suite, its seeded user and its job in the pipeline. A repository that has a pipeline file adds the smoke job of its host's skeleton in `ci/` to it. A repository without one copies the skeleton whole in this PR and takes out the three runs that call `scripts/checks.sh` (checks, checks on the main branch, scheduled) and the coverage line of the test run: they go in with the tools. Every step after this one that changes source code ends in the runtime check (D4, point 5), which is this suite plus the main pages; the platform PRs each end in one.
- **Then the platform PRs, when the owner said yes to the floor** (`02-step-1-discover.md` 1.10): language, framework, analyser, linter and test runner up to the catalog's "Version floor per row", one major per PR, each ending in the runtime check (D4, point 5).
- **Tool swaps.** A project on another tool than the catalog's for a need (`catalog/backend-laravel.md`, "Tooling per row") swaps it, one tool per PR: the test runner, linter, formatter and analyser here, before the baselines are generated; the validation, DTO and permission packages in step 8, in the theme of their rows. A swap that changes stored data or what a user is allowed is a behavior change: the owner's question in 1.10, with the migration plan. A swap of something the organisation manages (a hosted formatter config, a pipeline image, an autofix commit) is never made here: it is the question of 1.1, answered before any pull request. No other swap is asked.
- **Then one integration branch, mostly generated:**
  - **First, list the flakes**: run the suite in random order on the base, several times, in CI (a throwaway draft pull request with empty commits, no reviewers, deleted after: a pipeline on a branch without a pull request starts no steps of a pull-request run, runs on the same branch can stop each other, and a trigger is single-shot: never a shell fallback that can start a second run). A flaky test in the base turns the main branch red later and blocks a deploy for hours, so the ids go in the backlog before any guard is built; step 4's sweep proves them fixed.
  - Format the whole tree once with the formatter and the refactoring tool. The formatter's config is the organisation's where it manages one (a hosted URL stays the source, never copied into the repository), otherwise the kit's (`templates/tool-configs.md`); the refactoring sets are the kit's. CI checks the whole tree and blocks; it is check-only unless the owner kept an autofix commit in step 1. Announce it first (`07-process.md` section 10). Run the full suite before and after the refactoring tool's first whole-tree pass and compare the failing test ids, and grep the whole diff for each miscompile class of `templates/tool-configs.md` ("Rules that can change behavior"): a wrong return type on a closure no test calls passes the suite. Fix an idiom by hand in a commit before the pass, never with a skip. Commit `.git-blame-ignore-revs` and list the format commit in it. Where the project merges by squash or rebase (the profile says which), the commit gets a new hash on the main branch: the file is then committed without a hash, and the line is added in the first PR after the merge, with the hash it has there.
  - **Some formatter rules are not formatting.** The kit's formatter config holds rules that change what the code does: they add the strict-types line, turn `==` into `===`, close classes, make dates immutable and swap byte string functions for multibyte ones. The format commit runs with each of them off, and one counting row per rule goes in with the tools (`strict-types-missing`, `loose-comparisons`, `mutable-dates`, `byte-string-functions`; `open-classes` is on the dashboard already), so new code adds no site. Which rules, what each changes, its row and the step it lands in: `templates/tool-configs.md`, "Rules that can change behavior", the one place that lists them. The row `formatter-rules` starts at the count of the rules that are on and rises with each PR that switches one on.
  - Tooling the later steps need: analyser extensions, lint plugins, the secret scanner (gitleaks), the mutation tool of the stack (`tools/README.md`, "Mutation"), the framework sets of the refactoring tool, the advisory-blocking package (`catalog/tests-database-ci-docs.md`, "Advisory-blocking dependency": where it refuses to install because a locked version has an advisory, that update comes first, in this branch). The lead runs installs.
  - The analyser config gets the bleeding-edge include, the extensions by name and every folder with PHP of the project in its paths, before the baseline is generated, so the baseline holds what they find (`catalog/backend-laravel.md`, "Analyser").
  - The six composer scripts (`catalog/tests-database-ci-docs.md`, "Composer scripts"), the one update command and the dependency bot's config (`templates/tool-configs.md`). After the in-range updates, `composer bump`, and its dry run becomes a line of `scripts/checks.sh`.
  - Every check runs on the whole tree and blocks, at its final strictness, made green by a generated, counted baseline (`04-guards.md` C5): the analyser's baseline (row `analyser-baseline`), the linter's bulk suppressions (row `lint-baseline`), and one keyed baseline per type-checker flag (`--format tsc`) and one for the unused-code tool (`--format knip`), written once by `scripts/keyed-baseline.sh --init` (afterwards `--write` only drops fixed lines; row `type-baseline`).
  - **The tools**, in this order:
    1. Copy `tools/*.sh` (`mutation.sh` included) and `tools/debt-caps.json` to `scripts/`, `ci/prepush.sh` to `scripts/prepush.sh` (every part of the checks side by side before each push: CI is then only a confirmation, not the feedback loop) and, where a step needs them, `tools/move-ts.mjs` to `tools/codemods/` in the repository (make the folder where there is none), and `ci/checks.sh` to `scripts/checks.sh`. The proof in `tools/proof/` stays in the kit. A repository with several package roots keeps this one `scripts/` folder, at its root, and the config paths list every package root. A file with one of the kit's names that is already in `scripts/` is renamed first, in a commit of its own: the kit's names are the same in every project.
    2. Fill in `scripts/kit-config.sh` (the values the scripts share), the config block at the top of each script, `ANALYSER_SWITCHES_TARGET` among them (`MIN_ROW_TARGETS` holds the kit's numbers and loses only the entries whose subject the project lacks), and every `<placeholder>`: the commands of `scripts/checks.sh`, `DATABASE_IMAGE` in `kit-config.sh`, and `TICKET` and `EXAMPLE` in the commit-message check. The dashboard's expressions are the ones measured in step 1, today's folders included (`02-step-1-discover.md` 1.6). Every value is explained in `tools/README.md`.
    3. The pipeline. The file exists by now (the first PR made it where there was none) and it is never replaced by the skeleton. On Bitbucket and GitLab, add the jobs and triggers of the skeleton that it lacks (the checks step, the checks on the main branch, the test steps where they are missing, the coverage line of the test step, the scheduled job with its whole-tree mutation run), fill in their placeholders, and keep every deploy, service and cache definition. On GitHub the existing workflow is not given the skeleton's triggers (its deploy job would run on every pull request and every night): copy `ci/github-actions.yml` to `.github/workflows/kit-checks.yml`, fill in its placeholders, move the existing workflow's own test jobs into it (a suite runs once per trigger), and keep the existing workflow's push trigger and deploy; a deploy that must wait for the tests becomes a workflow on `workflow_run` of the kit's workflow, or a job of the kit's file with `needs` (`04-guards.md` C4). Copy `ci/CODEOWNERS.example` to the host's code-owners path with the owner's names (never a bot) and keep it in the same commit as the pipeline (`04-guards.md` C4, point 22).
    4. Set the caps, before the commit, from a **clean clone with the pipeline's own install** (a counter measured in a builder's container can differ from CI's): run `bash scripts/debt-dashboard.sh --report --details`. Every measured row that is above zero reads OPEN, because the caps file still holds zeros: write the "now" of each such row into `scripts/debt-caps.json` as its cap. The ratchet rows are read from the last commit, so in this one run the rows that read a file this branch adds (the `cap-<key>` rows, `ci-skipped-steps`, the floor rows) print UNKNOWN; that ends with the commit.
    5. Commit the scripts, the caps file and the pipeline file in one commit. The pipeline file is on the base, so it is guarded in this PR already (on GitHub the new workflow sits in the guarded workflow directory): that commit carries `[ratchet: script] install the kit's checks step` (`04-guards.md` C2). The scripts in `scripts/` are new in this PR and need no tag of their own.
    6. Run `bash scripts/checks.sh`. It passes from this commit on: it prints that there is no copy of the ratchet script on the base to guard with, every ratchet row reads "new row", and every dashboard row is at its cap or held.
    7. Read every number of `bash scripts/ci-ratchets.sh --head` against a hand count (`tools/README.md`, "Adding a row"). A `?` prints its reason.
    8. Run the kit's proof on the lead's machine, from the kit folder, when the kit's scripts changed since its last run there (`tools/README.md`, "Proof", has the commands and what a run costs). It proves the kit's scripts with the tools installed there, not the project's config. On the runner, the first pipeline run of the integration PR is the proof of the project's config: read its ratchet table against the `--head` output from the machine.
  - These things here are the owner's to do, because they need admin rights on the host; they go in `CONTINUE.md` under "What the owner must do by hand": make the schedule of the scheduled job where the host keeps schedules outside the pipeline file (on GitHub it is the cron of the kit's file, UTC, from the default branch's copy); make the read token the CI duration row needs on Bitbucket and GitLab (on GitHub the scheduled job already has `GH_TOKEN` and `actions: read`; `tools/README.md`, "Adding a row"); after the merge, set the required checks of the main branch and of every other deploying branch to the job names the pipeline now has (GitHub: `checks-result`, `backend-tests`, `frontend-tests`, `smoke`, selectable only after they ran once, so open a draft pull request first; GitLab has no required checks per job: there the setting is "Pipelines must succeed", and every job of the skeleton is in that pipeline; the contract test holds that the merge request pipeline contains the checks job); and make the review of the code owners required (`04-guards.md` C4, point 22): GitHub "Require review from Code Owners" with no bypass, GitLab "Require approval from code owners", Bitbucket default reviewers and the merge checks. On GitHub also: "Require branches to be up to date before merging" (the run checks the merge as it was when it started), default workflow permissions read-only, the fork-pull-request policy (secrets never go to forks), the Actions minutes of the plan (the split costs about 2.7 times the build minutes, times the matrix, plus the tests, the smoke run and the nightly mutation run), one test of a stacked-pull-request retarget with "Automatically delete head branches" on (the checks must run again), no merge queue until a `merge_group` trigger exists, and the gitleaks version and checksum copied from the release's `checksums.txt`. After the first pull request: the log of `checks (gate)` prints "scripts/ci-ratchets.sh is not on origin/<base> yet" for the installing pull request only, `checks (repo)` counts only the pull request's own commits and gitleaks prints a number of commits scanned above 0; the next morning the scheduled run exists on the default branch, `ci-duration-minutes` is not `?` and the mutation run found its database.
  - The ratchet script with its start set of rows and a row per existing list (`04-guards.md` C2); the dashboard as a blocking step in its default mode, the gate (`04-guards.md` C3).
  - The coverage floor in a committed file at the measured value, held in the test step, with its `min` row `coverage-floor`, and for a frontend the rows `frontend-coverage-floor` and `frontend-logic-coverage-floor`, each at its measured value (`tools/README.md`, "Coverage"). The end goal of 95 is step 9's; nothing here is set to 95 by hand. The mutation score: the whole-tree run in the scheduled job, with its minimum in `scripts/mutation-floor.txt` at the measured value and the `min` row `mutation-floor` (`tools/README.md`, "Mutation"). The run on the changed files of a pull request starts in step 9, when the missing tests exist; from then on it uses the same number (`catalog/tests-database-ci-docs.md`, "Mutation testing").
  - Dependency audit fixes and in-range updates; audits block.
  - The commit-message check, manifest validation, the PR template. A bot that opens dependency PRs is configured to the form first (`07-process.md` section 10).
  - Every lint rule, analyser switch and type-checker flag the tree already meets is switched on now, by name: it costs nothing and closes a door. The row `analyser-switches` counts the switches that are on and only goes up.
  - The secret scan on every pull request (the line is in `scripts/checks.sh`).
  - The contract test over the CI files (`04-guards.md` C4, "What the contract test asserts"). It is the first test in the guard group, so that group is never empty.
  - The CI duration cap: the caps key `ci-duration-minutes`, a row the project adds (`tools/README.md`, "Adding a row"), set from the first green run of the new pipeline on the main branch.
  - Batches of this branch that share no files can be built at the same time: process files (PR template, commit-message check); the ratchet script and CI steps; lint config; analyser config and baseline. Only the lead edits the files two batches share (package manifests, the check scripts).
  - **Split the checks into parts** (`ci/checks.sh`, `PARTS`): one pipeline step per part, and the backend tests sharded with a coverage merge step if the suite passes four minutes (`04-guards.md` C4).
  - **CI speed comes first in this branch**: caches, the analyser's result cache, parallel jobs, the process timeout off for long scripts (`04-guards.md` C4, "CI speed"). The later steps push many times; every minute here is paid again then.
  - **Before the push**: merge the base branch (the pipeline checks a merge of it on Bitbucket and GitHub, and a hotfix on the base can bring new analyser errors; GitLab checks the source branch unless merged results pipelines are on), apply the generated passes to what came in, regenerate the baselines in the pipeline's own image (never on a developer's host: `04-guards.md` C5), and run `bash scripts/checks.sh` there. Push once, after the checks ran in the image the pipeline uses. A new file the lead adds (a script under `scripts/`) passes the same rules as the rest from its first line, and its folder is in `SOURCE_PATHS`.
  - **Type coverage at 100** is held by its measured number in the config and a `min` row, not by baseline entries (`catalog/backend-laravel.md`, "Analyser").
Exit: the pipeline of the integration PR, green, with the output of `debt-dashboard.sh --offline --details` and `ci-ratchets.sh` in its log; no step is scoped to changed files (the contract test over the CI files); every cap at the measured value of its row.

**3. Freeze the patterns.**
One integration branch and one PR for the whole step; no source file moves. Commits are grouped by guard and read one by one. The reason: guard PRs in a series all read and rewrite the same guide rows (the guards read their sentences from the guide), so each merge conflicts with the next in meaning, not only in text, each push voids the approvals, and a day of merging follows hours of building.
- **First commits: the shared reader, then the documents.** The reader is the family of `reference-project/tests/Support/Architecture/` (`PhpSource`, `PhpFileInspector`, `PhpCallReader`, `ClassGraph`, `CountedList`), copied whole and landed as the first commit of this step, before any guard branch starts; every builder branches from that commit and depends on it (`08-builder-rules.md`, "Guards you write"). Then the documents (`03-conventions.md` B2: one-pattern table, layout table, test conventions, rubric, decision record, the list of guard names), with the guard over the guides, the guard over the guard folder (`catalog/tests-database-ci-docs.md`, "Guard shape") and the row `guide-future-tense`. The rows a guard reads live in one file per guard (`docs/guards/<guard>.md`), so two guards never edit the same lines. The guard over the guides fails a path in backticks that does not exist, so a row whose example lands in step 8 says "lands with <PR>" in its Copy column, and nowhere else.
- **Then the guards those documents name, one commit group each**, each with its counted list and its ratchet row: layout, class shape, architecture (named by topic: layers, data access, errors and logging), banned calls, one spelling per construct, size (the method-length guard shares its scope with the file counter), test conventions, schema, coverage over the entry points, the register of stored names. The functions the `php` and `security` presets ban go into the banned-call rules here, with today's sites in the analyser's baseline; a preset has no list of its own, so its call lands in step 8, when its count is zero (`catalog/tests-database-ci-docs.md`, "Architecture presets"). Builders may work on disjoint guards at the same time; the guide sentence of a guard is written last, after the guard (`03-conventions.md` B2). **The test spelling is decided before the first brief** (one spelling per construct, `catalog/tests-database-ci-docs.md`, "One spelling in a test", after the formatter check of step 1) and written in every guard brief, with the same text: a builder that keeps the project's old spelling in the tests it adds makes the spelling guard's first run red. **The guard branch that owns test conventions lands first**, then the others branch from it (or merge it before their first test); the rest may run in parallel.
- **Agents review before humans do**: each guard is read cold by an agent that did not write it, against the standing blind-side list of `04-guards.md` C1, and its findings are fixed before anything is pushed. The owner's and colleagues' review is then of a branch that is final.
- A sweep of every rule the rubric holds as review only: each one that can be checked mechanically goes through the candidate method (`04-guards.md` C7). What stays is a judgement with a rubric number.
- **One push per round of review**: collect every thread first, answer all in one push, and ask for review only when the branch is final (`07-process.md` section 5). The lead merges the base into the branch before asking for the approval, so the approval is not voided by a merge afterwards.
Exit: the merged PR, and the green run of the guard over the guides, which fails a row of the one-pattern table without a guard or a rubric number. A "lands with <PR>" that is left names an example file of step 8, never a guard. Every cap is lowered to its row (D4, point 2). The owner sees the domain list and the deviations from the catalog, not the patterns: those are the kit's.

**4. Test foundation.**
- **Dead code, first pass**: unused packages (each proven on a clean clone with a fresh install: the proof needs the private registry credentials as a transient variable and a read-only key mount, and the package manager in the image must be the one that wrote the lock file, or a remove rewrites it), unused exports and files, feature flags on for everyone, test-only routes and methods (after checking sibling repositories). Run the unused-code tool to a fixed point: a deletion makes more files, exports and packages unused. A binary that another package manager's script runs (a dev script of the PHP manifest calling `npx`) is invisible to the tool and an ignore entry is counted: run it from a script of the package manager the tool reads.
- **One test framework.** A PHP project that has both Pest and PHPUnit tests converges to the one the owner named in step 1, as its own theme with its own commit; the count of files in the other framework is a ratchet row the PR adds and empties.
- Test conventions that do not depend on where a file lives: helpers, fixtures, the one way for config, clock and container, shared fakes, banned calls, skips, one spelling per test construct by codemod. For a bare queue or bus fake, a recording run gives the list exactly (`catalog/tests-database-ci-docs.md`, "Fake events and queues").
- Tests on the real path: no test switches off middleware or exception handling, and a request to a named route is built from the route name. This is a bug-finding step, not a rename (`10-hazards.md`, "A test with exception handling off"). The fix goes in the same PR, under "Behavior that changes on purpose".
- **The hermetic base set-up** (`catalog/tests-database-ci-docs.md`, "Hermetic base set-up"), as its own commit group. Run the workers with a memory limit: a lock wait with a faked sleep and a frozen clock spins until the worker is killed, which aborts the whole parallel run, and a limit makes the spin die as a fatal error that names the test. It is a bug-finding step too: a test that reached the network, waited, or relied on the clock moving now fails, and each failure is fixed in the test (a fake for the request, a `travelTo()` for the moment), never by allowing the call (`10-hazards.md`, "Tests").
- The test suite runs on the production database engine (`catalog/tests-database-ci-docs.md`, "Database").
- Characterization tests for the classes that steps 7 and 8 will split or rewrite by hand. They sit next to the class as it is now and move or split with it later.
- **The flake sweep**: the full suite ten times in CI in random order. Random order is switched on in the test runner's committed config, where it stays, so every run picks its own order. The lead gets the ten runs from a throwaway draft pull request with empty commits (no reviewers, deleted after), or by re-running the test step of the step's PR through the host; no pipeline file is edited for it, and runs are started one at a time (parallel runs on one branch can stop each other). Before the sweep, grep for the known causes: orderings without a unique tail, helpers that sort an expectation, unseeded random values (the data generator is seeded per test from the test name) and timer-dependent UI delays. The ids of the failing tests of the ten runs are compared; the sweep passes when no id differs between runs, which with a green suite means ten empty lists.
Not here: moving tests to their final location (step 5) and splitting big test files (step 7).
- **The strict-types rule**, where step 2 left it off: its own PR, when the tests are on the real path and hermetic (D2, step 2). **Then the strict-comparison rule**, the same way: its own PR, after `loose-comparisons` is at 0 in PHP files by hand-read fixes.
- **Strict models, the recording commit**, last in this step. Read first whether the strictness is already on: where it already throws in every environment, "recording, not throwing" relaxes production, and a swallowed exception (a resolver that catches `Throwable`) becomes a loaded relation, which is behavior that changes (`10-hazards.md`, "Strict models"). The three checks of `Model::shouldBeStrict()` go on in every environment, each with a handler that records and does not throw (`handleLazyLoadingViolationUsing`, `handleDiscardedAttributeViolationUsing`, `handleMissingAttributeViolationUsing`): it reports the violation to the error tracker and, in a test run, writes its key (model, kind, relation or attribute) to a file per worker. A last check of the test step (it belongs to the composer scripts: reset, the run without the guard group, then the union test of its own group; never in the guard group, which the fast checks run before any test run) compares the union with one committed counted list (`04-guards.md` C5): a key that is not listed fails, and so does a listed key that no longer occurs. The row `model-strictness-violations` counts the list. The runtime check of this PR and of every later step reads the same reports on the production-like environment; a key found there and not in the tests is added to the list in a PR of its own with the override tag, and gets a test. Step 8 empties the list.
Everything in this step is one integration branch, with the hand-written or risky parts (strict types, the real-path conversions, the strict-model recording) as separate PRs where D3 says so. Agents that build tests in parallel get **one test database server each** and never run two suites on the same database; fewer, larger builders (three or four) finish more than seven that hit a usage limit together.
Exit: the dashboard output with the test-convention lists gone and `strict-types-missing` and `loose-comparisons` at 0; the green test of the base set-up; `model-strictness-violations` at its measured value; the ten run logs of the flake sweep; per class on the split list, the name of its characterization test; every cap lowered to its row.

**5. Layout.**
- Migrations stop referencing application classes.
- Moves by the move tool from a map file, by domain group, in risk order: areas without stored names first. Tests move with their classes. Path-keyed lists (baselines, allowlists, every counted list) are rewritten from the same map in the same commit, with the count check of `04-guards.md` C5 (the same count minus the entries the move fixed), never regenerated. The move tool, the map and what a move really needs: D9, "The move tool". Before cutting commits **probe all groups in the working tree and run the guard group once**: a move into a folder switches on the guards of that folder (a service provider moved into the providers folder becomes a new entry of a shrink-only list), so every fresh violation is a class that stays out of the map, written down with its reason, never a line added to a list; the probe also finds the opposite (a move that fixes an entry). Build the map by a rule table over folder names and check the layout guard over the new paths before anything moves. A heuristic that gives a test its new home needs a floor: a test follows its class by folder only at a mirrored path, and by name only when the class is behaviour (action, service, command, controller, middleware, support) and the match is unique; data, exception, enum, value-object and contract classes never attract a test by name. The analyser baseline holds paths in three forms (the `path:` key, the path inside an anonymous class name with its line number, and the regex-escaped path): the rewrite covers all three, the line numbers shift, so the one allowed regeneration is not optional, and the check that survives it is the total per identifier (a rise of one identifier is a finding to read). After a scripted move, run the refactoring tool and the formatter over the whole tree, then regenerate nothing but the analyser baseline once, then the suite. Functions that become classes in a namespace break four things no analyser sees at once (`10-hazards.md`, "Path arithmetic and moved code").
- A PR that moves listeners or commands extends the framework's discovery to the module root in the same PR (`10-hazards.md`, "Stored names").
- A group that renames a stored name ships in three releases (D9). Steps 6 to 9 start when release 3 is deployed and its watch is clean.
- The PR that completes the moves removes the old-folder alternatives of step 1 from `BEHAVIOR_CLASSES` and `SUPPORT_CLASSES` in the dashboard, with the script tag; the rows do not move. The frontend expressions lose theirs in the PR of step 8 that moves those files.
- Alias removal by the alias rule (D9) is an open loop with its "start when" signal in the backlog; it is the only place aliases are removed, and step 10 does not close while an alias is left.

## D3. PR shape

- **One integration branch and one PR per step** for everything scripted or mechanical, and for the guards of step 3. Builders work in parallel in their own worktrees on disjoint file sets; they do not commit or push (`07-process.md` section 0). The lead merges their branches into the integration branch, runs the checks in the pipeline's image, has it cold-reviewed (by agents that did not build it, against the standing blind-side list for guards), pushes once; it is reviewed once.
- **Chain the PRs.** A PR that depends on another, or follows it in the same step, targets that PR's branch (`07-process.md` section 9). Side-by-side PRs over the same register, guide row or provider list conflict at the first merge, and each conflict fix is a push that voids the approvals. A merge button merges into the destination the PR was opened with, so read the destination before every merge and check the head with `git merge-base --is-ancestor`.
- **Guide rows that a guard reads live in one file per guard** (`docs/guards/<guard>.md`), so two guards never edit the same lines.
- Inside the PR, commits are grouped by theme (by guard in step 3), scripted and hand-written parts apart, each theme verifiable by one rule with the review aid. A reviewer reads commit by commit.
- **Collect every review thread, answer all in one push**, and ask for review only when the branch is final. A push voids approvals on many hosts. The lead merges the base into the branch before asking for the approval.
- **Before merging, verify the destination branch** (`destination.branch.name`, or the host's equivalent) and, after the merge, confirm `git merge-base --is-ancestor <head> origin/<base>`: the commits of the PR must be in the branch the team deploys from.
- **Merge by automation when the gate is met.** Where the owner agreed in 1.1, a green pull request with its one required approval merges by the host's auto-merge, and the integration branch merges once per step: a push voids approvals and a merge that waits for a person is the longest wait of the program.
- **Plan merges around releases.** An automerge or release flow (a release PR, a merge-back bot) conflicts with the program: step merges are planned between releases (the question of 1.1), never in a freeze.
- **A separate PR** for: hand-written work beyond what one reviewer can read (effects, splits of core classes, the analyser fixes that are not mechanical); anything that changes authorization (the sweep gets two independent security reviews and a before and after entry-point table); anything that needs its own deploy and watch (stored names, column types on big tables, lock files, a behavior change); anything that needs a human step first.
- Steps 6 and 8 are therefore several PRs: one scripted integration PR and a short series of hand-written ones, each independent of the others' files.
- Plan at step level. Write PR rows only for the current step; later rows go stale before they are used.
- **One chain per area.** There are two areas, backend and frontend; they share no files, and a PR that touches generated types, a root config file or an `AGENTS.md` counts as both. Within an area the PRs form one chain, merged from the bottom. Codemod branches are never stacked on each other (`07-process.md` section 6).

## D4. The end of a step

1. The step's exit artifact exists (D2) and is pasted in the plan with the commit hash.
2. The dashboard is re-measured, coverage included, and the plan's numbers updated; no counter moved the wrong way. A shared fake can stop real modules being exercised, so coverage can fall with every test green. The lead raises the committed coverage threshold and mutation score to their measured values, and lowers every cap in the caps file to the measured value of its row (the dashboard prints "lower the cap to N"; `04-guards.md` C3). The full run (`bash scripts/checks.sh --scheduled`) measures the rows `--offline` skips.
3. An auditor that did not build the step answers one question (an auditor can be wrong as well as the lead: before the lead changes a row on a disagreement, it runs the row's own regex and reads the matching lines, and keeps the row where the regex is right, for example an intended exception the auditor counted as a miss): "what debt of this step's kind is still there that no counter shows?" A finding becomes a counter now, not after "zero" (`04-guards.md` C7).
4. The smoke suite passes on the integration branch.
5. **The runtime check**, for every step that changes source code. Green CI and counters at target do not prove that nothing is broken: tests run on an in-memory cache and a synchronous queue, and a real cache store can refuse to unserialize what the in-memory one returned unchanged. So the step's result runs on a production-like environment with the real cache store, queue and database engine (staging, a preview, or a stack booted with the production drivers; never production). The check is the smoke suite against that environment plus the main pages requested twice, so the second load reads from the cache. For every step that moves or renames a class, the check includes a payload that crosses the deploy: dispatch on the old stack (a chain must be created by the old tree: the first queued job of a flow may hold no closure, the job it dispatches does), process on the new, then the other way for the rollback; the suite, the smoke suite and the main pages all run on the new code only and cannot see class names in payloads. The lists (routes, events, the schedule, commands, queues, the classmap) are diffed after mapping names back with `tools/map-normalise.sh`; keep the dumps as the move step's runtime script. The lead signs in as the seeded test user of 1.1. Where the lead cannot reach the environment (the pipeline's runners are refused, or the lead cannot hold the secret of that environment), the answer of 1.1 names the form: allow the runner; a custom pipeline with a secured variable that runs the suite against that environment; the owner runs it and reports the table; or a stack booted in the pipeline with the production drivers. The fields below are filled the same way in each form. The runtime-check row in the plan records: each URL with its status, both times; the error-tracker query and its count; the failed jobs before and after; the result of the deploy pipeline itself. On a stack booted for the check there is no deploy pipeline and no error tracker: those two fields read "not applicable", and the count of error lines in the application log of that stack takes their place. Until this row is filled in and clean the step is not done and nothing merges on from the main line to a release branch. Guards for this class: `catalog/tests-database-ci-docs.md`, "Runtime and contracts".

**Stop for the owner's go** after steps 1, 3 and 10, when a question about behavior comes up, and when point 3 adds a counter that needs an owner decision: a kind of debt the signed definition of clean does not cover, or a fix that changes behavior. A row that must stay above zero is a decision row with an end date, and the lead stops for the owner's approval of it at once, like any counter that needs an owner decision (`01-principles.md`, "Shrink-only rows"); without that approval the row is open debt. Every other counter goes on the dashboard, in the backlog and in the definition of clean, and the program continues. Report the five points either way, with every decision row the lead wrote since the last gate; a new entry in `SHRINK_ONLY` is one (`01-principles.md`, "Shrink-only rows").

Watching a deploy (error tracker, queue, failed jobs) is part of the lifecycle of the PR that needs it (`07-process.md` section 2), not a gate for the next step, unless that step depends on the deploy.

## D5. What never runs at the same time

- two move or rename branches;
- a move and anything touching the same folders, the architecture tests, the lint or analyser config, the package manifests and lock files, generated files, or config;
- a column-type migration and a move that renames stored names, in one release;
- two changes to authorization rules;
- a pattern change and an open product PR that edits the same files (check with `git diff --name-only` first).

A backend PR and a frontend PR of the program may be open together (D3); nothing else may.

## D6. Size

Size shapes how the steps are cut and never how many of them there are. Choose size in step 1, from the measurements. Check in this order; the first match decides: Large when a table is too big for a plain schema change, or the moves cannot be reviewed as one PR; Small when both of its signals hold; otherwise Medium. Stored names do not set the size: they add the three releases of D9 to step 5 at any size.

| Size | Signal | Shape |
| --- | --- | --- |
| Small | under about 300 source files, one area | steps 1 to 3 as written; the scripted parts of steps 4 to 9 as one integration branch, in step order, one theme per commit; every PR that D2 and D3 name as separate stays separate (strict types, authorization, stored names, behavior changes); one runtime check per merged PR; the six exit artifacts are read from the dashboard output of that branch; step 10. The audit (D4, point 3) at the start and the end only |
| Medium | one backend and one frontend, a few thousand files | all steps |
| Large | many domains, big tables | all steps; steps 5 and 8 split by domain group and by deploy |

Every size keeps the four hand-off files, the module layout and the ten exits. Steps 1 to 3 and 10 are never shortened: they are what makes the result hold.

## D7. The top analyser level

The top level is strict about every value without a type, so the errors are many and repetitive.

1. **Measure with a scratch config** that includes the project config and sets only the level and its own cache directory. Never edit the project config to measure.
2. **Find shared root causes first.** Group the errors by message and by the symbol they point at. A few untyped producers cause most of them (a client helper without a return type, the untyped chains of the test framework, a loader that returns an untyped value). The lead fixes these before anyone else starts.
3. **Split the remainder by folder** over parallel builders, with one shared list of fix patterns in every brief, so the same error is fixed the same way everywhere (`07-process.md` section 7).
4. **Fix the type where the untyped value starts**: a return type or an array shape on the producer, a checked narrowing helper where data enters from outside. Never an ignore, a baseline, an assertion, an inline cast annotation or a cast on an unchecked value.
5. **The level is already in the config** (step 2), held by the rows `analyser-level` and `analyser-switches` (`tools/README.md`, "The rows that ship"). The last commit deletes the baseline file and its include; the row `analyser-baseline` stays, at 0.
6. **List what changes for unexpected input.** A checked helper returns an empty value where a cast used to coerce or a type error was raised. Behavior for valid input stays the same. Every such site goes in the PR description under hazards.

The PHP fix patterns and traps: `catalog/backend-laravel.md` ("Top level in source") and `catalog/tests-database-ci-docs.md` ("Top level in tests").

## D8. Closing classes for extension

Every concrete class of the source is closed (`final`). An abstract class stays where the framework or a real shared base needs one: a parent is abstract, and a concrete class is never extended. One mechanism does it and keeps it: the formatter rule `final_class`, which leaves an abstract class alone, switched on in this sub-step, with `final_internal_class`, `protected_to_private` and `final_public_method_for_abstract_class` in the same commit. `protected_to_private` changes a protected member only in a final class that extends nothing, so a hook the framework declares protected (`casts()`, `booted()`) keeps that visibility (both read in Pint 1.30). The formatter's own run is the codemod. What it breaks is in the tests, and a text search for the class name does not find it. This is the one place the forms are listed; other files point here.

The formatter decides for a class nothing extends and no test doubles. It cannot decide for the others: it would close a parent and break its children, and it knows nothing of the tests. Those are the pre-scan's.

0. **Concrete parents first.** List every concrete class of the source that another class of the source extends. Each becomes abstract, when it is a shared base that nothing builds by itself, or its children are folded into it. Nothing exempts a concrete parent: `open-classes` counts it until then.

1. **Pre-scan, before the codemod.** List every class that a test reaches other than by its own name, and decide each one:

   | How a test reaches the class | What the scan looks for | What to do |
   | --- | --- | --- |
   | A double of a class named in a variable, where the name comes from config or a parameter | every double whose argument is not a class constant; then where the value comes from | double the interface the config chooses between, not the chosen class |
   | A facade or static proxy: the test sets expectations on it, the mocking library then doubles the class behind it | every facade the tests set expectations on, and the class behind it | the tests stop mocking the facade (the real class, or a fake bound in the container) and the class is closed. Until they do, the class stays open as a decision row, counted |
   | A subclass built from a string (an evaluated string, an anonymous class template, a generated stub) | evaluated code, class declarations inside strings, code generators in the test support folder | build the object the test needs directly; never extend the class |
   | A fallback in a generic helper ("if I do not know this class, mock it") | doubles inside loops and helpers over a list of classes | give the helper a real instance for each class it meets |
   | A partial mock or a spy of the class | the partial and spy calls of the mocking library | the real class, or it stays open until the test is rewritten |

   A class that stays open is a decision row with its reason, and carries the docblock tag `@final`: the formatter rule skips a class with that tag, and nothing else exempts one. The dashboard row `open-classes` is the rule's counter, with its cap and the ratchet row `cap-open-classes` (`04-guards.md` C3): it counts every concrete class declared without the closing keyword, a concrete parent included and an abstract class not, so before the rule is on it is the burn-down, and afterwards it is exactly the tagged classes. The cap only goes down. A cap that is above 0 at the end is in `SHRINK_ONLY` by its decision row (`01-principles.md`, "Shrink-only rows"). The formatter rule is the guard; `ClosedClassGuard.php` in the reference project reads the same docblock tag `@final` (it holds no list of class names) and adds a check of the concrete-parent rule and of a stale tag on a final or abstract class; it is not a second definition of the rule.
2. **Tests on the real path first** (step 4): fewer doubles are left to break.
3. **The formatter run with the four rules on, in its own commit**, with the list of classes that carry the tag and why. Property defaults on queued classes survive (`10-hazards.md`, "The refactoring tool"); a class that is read-only as a whole may not be able to declare a property with a default, so a queued class that needs one moves the read-only marker to its constructor properties.
4. **Expect one pipeline run per layer.** Extending or doubling a closed class is a fatal error, not a failed test. Under a parallel test runner a fatal error kills a worker: the run ends without a report, without test names, and every other failure is hidden behind it. Fix the fatal, run again, read the next layer. Where the verification policy allows it, run the test suite once locally before the push; this is the change where that pays most.
5. **A reviewer's "no test extends or doubles a newly closed class" names its method** and what the method cannot see (`09-reviewer-brief.md`, "Say how you know"): the five forms of the table above are what a text search does not see.

## D9. Moving a class whose name is stored: three releases

A name from code can be stored in data: a class name in a row, in a queue payload, in a cache entry. The register of stored names (`04-guards.md` C1) says which classes those are. Moving or renaming one never ships in one release: a worker of the old release cannot load a job queued under the new name, and a rolled-back release cannot read rows already rewritten.

**The map file** is the single source: one line per class, old name and new name (format and the key per language: `templates/pr-description-and-brief.md`, "Move map"). The move tool, the alias list, the data migration, the rewrite of path-keyed lists and the reviewer's zero-grep all read it. **The move tool.** TypeScript: `tools/move-ts.mjs` of the kit (map-driven: files, relative and alias specifiers, `import()`, mocks; `--verify` checks nothing names an old path, `--reverse` takes a group back out, a second run changes nothing). PHP: the refactoring tool's rename rules generated from the map are one fifth of the tool; `RenameClassRector` rewrites references and nothing else (not the file, the `namespace` line, the declaration, or the imports a file in the old namespace never needed). The tool has five phases, in this order, and is idempotent (a crash in phase 3 leaves a half-moved tree): (1) in each moved file an explicit import for every name that resolved through its old namespace (found with the parser, docblock words included), written before anything moves; (2) the refactoring tool with the rules from the map, on the old tree, where every name still resolves; (3) `git mv`, the `namespace` line and the declaration rewritten, same-namespace imports removed; (4) a text pass for the old name in strings, comments, config and documents (single and doubled backslash, and the regex-escaped path in the analyser baseline), and a grep of every docblock tag that names a class (`@mixin` and the like, which the rename rules do not know: the dead-import rule then removes the import of the renamed class and the analyser reports undefined properties); (5) the path-keyed lists rewritten from the same map. The first analyser run on the moved tree is part of the tool. A "return" mode (the same tool with the map reversed, and the lists restored for exactly those files) takes a group out of a finished move; keep the map direction-neutral. `tools/map-normalise.sh` maps names in a text back through the map, for the runtime check of a move (D4, point 5). The kit ships the map format and these tools, not a generator for the aliases or the data migration: that small script is committed in the PR, and the reviewer re-runs it.

| Release | Ships | Rollback |
| --- | --- | --- |
| 1 | aliases in both directions for every line of the map, as one lazy autoloader on the map (the registration is valid in all three states: before the move, after it, and during a rollback), and the register lines: every class of the register, the classes that serialized closures name included, not only the scope classes. The register lists both names of an alias line while the alias list exists and the guard expects the other name of a line next to every stored class (failing examples: an alias line that names no stored class, a stored class outside the new layout without a line, an unsorted or duplicate line), so release 2 needs no register edit. No class moves, no data changes. Its runtime check has three runs on one stack: (a) the old code queues and the new code processes, (b) the same payloads rewritten to the new names (nested strings, closures re-signed) processed by the release-1 code, which is the rollback direction of release 2, and (c) the control: the rewritten payloads processed by the old code, which must fail, or the rewrite proved nothing | redeploy the release before it; nothing was written |
| 2 | the move itself. Workers restart with the deploy, so no worker runs old code against new names. Then the watch: error tracker, queue, failed jobs | redeploy release 1: it reads both names, so payloads queued under either name still load |
| 3 | after the watch is clean: the data migration that rewrites stored rows, with a `down()` generated from the same map read in reverse, and a test that the old names are gone. A payload holds nested serialized strings (every length is recomputed) and signed closures (re-signed with the application key, or left alone until their rows are pruned): the test covers a payload with a chain and a signed closure, before and after, then unserialized | run `down()`, then redeploy release 2 |

**One-release variant (owner's choice, recorded in the plan).** Where the owner accepts that the deploy of the move cannot be rolled back safely, the three releases collapse into one: aliases, the move and the data migration (with its generated `down()`) ship together. Conditions: the queues and `job_batches` are drained before the deploy (workers paused, a query shows no pending payload under an old name), the deploy restarts every worker, and the owner names the rollback in advance (drain again and retry `failed_jobs`, because old code cannot read payloads queued under new names). The runtime check keeps run (a) of release 1 (old code queues, new code processes) and the data-migration test of release 3; run (b) and (c) fall away because there is no rollback direction to prove. Alias removal stays its own PR, after the longest payload life. The default stays the three releases; this variant is chosen by the owner per programme, never by the lead.

Then **alias removal**, as its own PR: after the longest life of a payload the profile names, counted from the deploy of release 2, and only when a query on the queue and failed-job payloads finds no old name. The PR description shows the query and its result.

Rules:

- The PR description of each release names who rolls back and how that person is reached (`02-step-1-discover.md` 1.1), and the exact rollback of its row above.
- An alias does not carry private properties of a payload queued before the move (a private key is written with the class name, even one declared in a parent): a queued class with private state becomes not-private in a release before release 1 (protected is fine); the scan and the lifecycle hooks that set state before serialization are in `10-hazards.md`, "Stored names".
- A serialized closure is a stored name (`10-hazards.md`, "Stored names"): the register names its defining class, every class its body names and every captured type, and release 1 aliases them all.
- Alias removal also waits for the retention of the failed-job and batch tables when closure rows are not rewritten.
- A test of a stored payload needs `unserialize`: the one counted allowed place is a test support class (`04-guards.md` C1).
- Alias every moved class that can sit in a payload, enumerations included.
- A class whose name is stored nowhere (the register does not list it) moves in one release, with no alias.
- What else a move touches is in `10-hazards.md`, "Stored names".
