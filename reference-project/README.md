# Read before copying: where this reference falls short of the kit

This folder is another project's end state: a multi-tenant Laravel and React application with Postgres and Pest (which host its pipeline ran on is not stated here: the pipeline guard of this folder is the Bitbucket form, and the GitHub and GitLab readers are tested on examples only). It is an anonymized extract: the domain is rewritten to an example web shop platform, the rows of its guides are cut to the ones that illustrate the kit's patterns, the lists (stored class names, aliases, route tables) are shortened, and the application code the guards run against is not included, so nothing here runs as it stands. Copy the idea and the shape of a guard, a config or a guide from it. Never copy these: where the reference and the kit differ, the kit wins.

- **The `scripts/` folder: never copy it.** It is the project's own pipeline glue and has drifted from the kit's `tools/`, which win in every case: its commit-message check passes silently when the base-branch variable is missing and names the project's ticket prefix, its ratchet script holds tool-named rows, a row that lists seven test files by name and one row over the sum of the caps, its dashboard uses other row names than `04-guards.md` C3, and its check scripts carry a bot that formats the changed files and commits (`CI_AUTOFIX`) and run the checks side by side on one tree. Copy `tools/`, and from the check scripts only the `Formatting` commands. Its parallel runner (`ci-parallel.sh`) is a copy of the kit's, which has no GNU-only call. What to read in this folder for an idea is the guards, the configs and the guides, not the scripts.
- **How the guard folder follows the kit's guard rules.** Every detector is a `<Subject>Guard` class in `tests/Support/Architecture/` and takes the repository root and every folder, file or table it reads as an argument; the literals are in the thin tests, with the exceptions listed under "What remains" (`GuardShapeGuard` over this folder reads them: no detector holds a literal path, and a test without failing examples, passing examples or a real-tree case in the group `arch` fails). The suffix `Helpers` is not used for a detector: the mirror guard (`TestHelperMirrorGuard.php`) applies to `*Helpers` and `*Scenario` classes of a mirrored test tree, and `tests/Support/Architecture/` has no mirrored test folder, so the two rules do not meet (the decision is written in `catalog/tests-database-ci-docs.md`, row "Helpers"). Every guard test is in the group `arch`, is thin, and names a guard class by import; it has failing examples carrying the words of the message, passing examples with near misses, a case under a dot directory in most of the tests of a guard that scans a tree (`SourceSandbox::create(..., prefix: '.checkout-')`; the tests of the guards that read a fixed list of files or no folder at all, such as `ActionNaming`, `EventDispatch`, `Exit`, `FlashMessage`, `FormRequest`, `FrontendDataNaming`, `LikeSearch`, `LogMessage`, `ManualTransaction`, `PerTenantState`, `QueuedClassLimits`, `RouteParameter`, `ScheduledTask`, `StringBackedEnum`, `TenantCreation` and `TestAssertion`, still lack it), and one real-tree case. A detector reads a missing folder or a missing named file as an error: `PhpFileInspector::phpFiles()` and `PhpSource::statements()` throw, so a real-tree case over a renamed folder or file fails instead of passing empty (`mayBeAbsent: true` for a list of folders of which some may be absent). The guards that read a folder of their own (`MigrationShapeGuard`, `MigrationClassGuard`, `TestClassGuard`, `TestHelperMirrorGuard`, `ScheduledOneServerGuard`, `JsonEndpointGuard`) and `TestTierGuard::pureLayerViolations()` (when none of its layers exists) throw on a missing folder, and each has an example that proves it. Not covered: a glob pattern that matches nothing in the other guards (`Globs::of` returns an empty list for a literal pattern whose folder is gone). A Pest `arch()` rule over a namespace with a wildcard is the other case of a rule over a folder that may be absent: Pest throws when no folder matches, so the rule takes its namespace from `ArchNamespaces::existing()` (an empty list while the folder is absent), and the rule is on before the first exception, command or job exists.
  What remains:
  - `FileSizeGuard` exempts a data file (a file that only returns an array) by what the code is, not by folder; `TestTierGuard` names the framework's booting classes (built from two parts, so the formatter's `X::class` rewrite cannot turn the guard file into a booting support type of its own check) and takes the project's base test cases and database concerns as a constructor argument.
  - The CI guards (`CiContractGuard`, `CiSafetyGuard`, `GithubWorkflowGuard`, `GitlabPipelineGuard`, `CodeOwnersGuard`) keep literals that name the skeleton of a pipeline, a script or a code-owners file (`bash scripts/checks.sh`, the workflow and pipeline file names, `ci/CODEOWNERS.example`): they read the CI files of a repository, the one category of guard where that is the subject. Their fixtures (`CiExamples`, `CiHostExamples`, `CiHostVariants`) carry path lists as data and sit in `tests/Support/Ci/`, outside the guard folder. `tests/Support/PHPStan/` holds analyser extensions with test-folder literals; they are not guards.
  - A path in a failure message comes from a constructor argument (`QueueNameGuard`, `RateLimiterGuard`, `QueuedClassLimitsGuard`); the wording is the project's guide wording and a copy rewrites it.
  - Tests that are not a guard class's three parts, by design: the Pest `arch()` rules (namespace shape rules, in the `Arch*Test.php` files that remain, `FinalReadonlyArchitectureTest.php` and `ActionNamingArchitectureTest.php`: the files that used to hold a dozen guards each are one thin test per guard now), the schema and coverage tests under `tests/Feature/` (they ask the booted application, and a feature test does not carry the guard group), `CiContractArchitectureTest.php`, and the reader test `PhpFileInspectorTest.php`.
  - Examples that need the application's own classes (`Data` classes, scoped models, the registries of the stored-name guards) fail without them: the scratch run has no application, so they fail there and are reasoned, not run (the examples of `ModelMagicStaticCallGuard` use the framework's own user model, and the tenant half of `DatabaseRuleGuard` and the page response of `JsonEndpointGuard` are proved on a model and a controller declared in a sandbox file: those run).
  - `ClosedClassGuard` takes no list of class names: a concrete class that has to stay open carries the docblock tag `@final`, the one marker the formatter rule skips, with its decision row elsewhere; the guard fails a tag on a class that is final or abstract and a concrete class that another class extends, tag or not. This is the reference's decision for D8 of the kit, and the guard is kept only as the proof of that shape and of the concrete-parent rule: the formatter rule is the guard of closing classes.
  - Some detectors still autoload application classes (`DatabaseRuleGuard`, `RegistryGuard`, `FrontendDataNamingGuard`, `PhpNewArgumentTypes`, `FlashMessageGuard`, `BareDataReturnGuard`, `JsonEndpointGuard`, `ModelMagicStaticCallGuard`, `TenantCreationGuard`, `RateLimiterGuard`, which imports the rate-limit provider): they read a model's scope or a registry through the autoloader, so their examples need those classes. The kit's rule ("keep the parsed tree for the project's own classes") holds for the shape guards (`ClassGraph` parses a vendor class from its file) and is not applied there. Reasoned, not run: whether `QueuedClassLimitsGuard` still autoloads (it shows no `class_exists` call).
  - A receiver that a guard reads by type (`TypedReceivers.php`) is read when it is declared in the file, in its own class or function, through a nullable, union or intersection type and through a plain alias variable (`$d = $this->db`). Still unread: an untyped receiver, a property declared in a parent class, a getter such as `getConnection()`, and an alias made by anything but a plain assignment.
- **PHP 8.4.** The reference writes `new X()->method()` and `array_any()`, which are PHP 8.4; the kit's floor is 8.4 for that reason (`catalog/backend-laravel.md`, "Version floor per row").
- **Analyser, refactoring and lint configs that fall short.** `phpstan.neon` switches off one strict rule (`dynamicCallOnStaticMethod`, a project choice with no decision row here) and holds the 18 analyser switches the kit counts (7 in `phpstan.neon` with the bleeding-edge include, 11 in `tsconfig.json`; copyable in `templates/tool-configs.md`, "PHP analyser and type checker"); `phpstan-tests.neon` relies on the analyser merging the `paths` list of the included file, names `phpstan/tests.stub`, which is not in this extract, and turns the `internalTag` toggle of the bleeding-edge include off (a stub cannot); `rector.php` has the public folder and not the tests, and holds 5 of the 18 refactoring switches the kit counts; `eslint.config.js` reads `resources/js/types/generated.ts` and the three enum names in it (an invented list: it throws when the file or an enum is missing, on purpose) and uses `padding-line-between-statements`, a deprecated formatting rule in ESLint 9; its `knip.json` points its schema at the installed package. Copy the shape and read the tool versions from `templates/tool-configs.md`, not from these files.
- **One spelling of a test.** `it(...)` only: `BannedTestCallGuard` fails `test('...')`, `it('it ...')`, `sleep()`, the stray-request switches and `->ignoring()`.
- **A placeholder for the coverage upload.** `scripts/ci-php-tests.sh` and `scripts/ci-frontend-tests.sh` call `scripts/upload-coverage.sh`, which stands for the uploader of the coverage service and is not in this extract; `coverage-service.yml` shows the shape of that service's config under a neutral file name.
- **Guards it does not have.** A coverage test for object-level access is `tests/Feature/Http/ObjectLevelAccessTest.php` (one test over every route with a record id and a map from model to a factory of a foreign record; reasoned, not run: it needs the application). No secret scan, no smoke suite, no contract test over its own CI files (the kit's example is `tests/Unit/CiContractArchitectureTest.php`, see "The guard library" below), no config test over the discovered listeners and commands, no row for the analyser's switches, no keyed-baseline script, no scheduled job, no dashboard row for open classes or for the CI duration, none of the rows `refactor-sets`, `formatter-rules` and `advisory-block`, and no row that counts a formatter rule's sites. Each of these is "not in the reference project" in the catalogs: the kit prescribes it and says how to build it.
- **The strictness the kit added later.** This project predates it. It has none of: the framework's strictness calls in one provider with their config test (the provider is not in this extract, and the project left the missing-attribute check off), the hermetic base test set-up, the two architecture presets, the 21 strictness rules in its formatter config (its `pint.json` is not in this extract), the `codingStyle` set and the framework sets in `rector.php` (which also does not read the framework version from the manifest), the advisory-blocking package, the manifest floor, the committed bot config, the six composer scripts, a browser smoke suite, a coverage floor with the goal of 95. Copy none of its configs for these: `templates/tool-configs.md` and the catalogs are the source.
- **Checks that came late or differ.** Its dashboard became a blocking step only after "zero"; its coverage gate uses an automatic target with a tolerance. The kit: the dashboard blocks from step 2 and the coverage floor is a committed number.
- **Not built, by the owner's decision.** Code owners, a guardian group and scheduled drift and update pipelines; the drift scan and the updates are run by hand there.

## What a run of this folder shows

Run as a whole with Pest in a scratch setup (the guards' own dependencies, no application): 1381 examples and real-tree cases pass and 53 fail. Every failure is a real-tree case or an example that needs the application (its folders, its routes, its classes, its scoped models), which the extract does not include; a missing folder or file is an error and not an empty pass, so they fail where an empty tree would pass. The guard over the guard folder (`GuardShapeArchitectureTest`) passes on this folder: no detector holds a literal path, and every guard test has its three parts in the group `arch`. Reasoned, not run: a PHP 8.4 runtime (the scratch setup used 8.5 and Pest 4; the syntax of the files parses at 8.4), the translation-key test (it needs the application), the coverage tests under `tests/Feature/Http/` (they boot the application), the examples of `DatabaseRuleGuard` and `JsonEndpointGuard` that name a model or a Data class of the application, `LaravelMagicUsage` (it needs the dead-code package) and `RoutePermissionCoverageHelpers`.

**The prose here is for the reader of the kit.** The comments in the thin tests and the docblock sentences of the older guards explain a rule to someone who has not seen it. The row `comments` counts every one of them, so a project deletes the prose when it copies a file (the `@param`, `@return` and `@var` tags stay). The newest guards (`TypedReceivers`, `ReportNotLogGuard`, `RawTableGuard`, `GlobalImportGuard`) carry no prose, and the guards hold no operator and no byte-string function in a literal the rows would count (`04-guards.md` C1, the guard that passes the project's own checks); the proof scenarios `RG01` to `RG03` read both. The example files of `tests/Support/Ci` and the thin CI tests are the exception: they hold YAML text, which has the `==` of a GitHub expression, and a project builds those operators from parts or keeps its own examples.

**Analyser status, measured.** `TypedReceivers` passes PHPStan level 10 with the kit's `phpstan.neon` (it had 11 errors: a stack offset that might not exist, a list that lost its type, an `instanceof` that is always true). The rest of the guard folder does not: in a scratch project with the kit's strict rules and disallowed calls, `tests/Support` has 89 errors in 21 files with the dead-code reports left out (the scratch run has no application and not the tests that call the helpers). 69 of them are in the guards, 47 of those in the CI readers, which read parsed YAML as untyped arrays (`offsetAccess.nonOffsetAccessible`, `cast.string`, short ternaries, `empty()`, `json_encode()` without the flag); `ClassGraph`, `RegistryGuard`, `PerTenantStateGuard`, `FlashMessageGuard` and `CodeOwnersGuard` hold the rest. A copy goes through the project's analyser before the first push, as `04-guards.md` C1 says of every guard, and a typed reader for the YAML (one class that narrows each node to a string, a list or a map) is how a project closes the CI readers.

Still not done in this folder: the failure messages of the CI guards mostly say what is wrong and not the value to write; the untyped receivers and the glob pattern named above; a case under a dot directory in the tests listed above; the detectors that autoload application classes.

## The shared source reader

One family in `tests/Support/Architecture/`, copied first and as a whole (`04-guards.md` C1; the first commit of step 3). A guard depends on these and never parses, resolves names or reads a list on its own:

| Class | Answers |
| --- | --- |
| `PhpSource` | the one parser: `parse()` (names as written), `resolved()` (names resolved; `preserveOriginal: true` keeps the spelling), `statements()` (a named file, throws when missing) and `traverse()`, the visitor entry that takes any node visitor |
| `PhpFileInspector` | the folder and file questions: `phpFiles()`, `declaredTypes()`, `referencedNames()`, string and keyed-array literals, swallowed catches, and `calls()` / `callsIn()` through the call reader |
| `PhpCallReader` | the call reader: every function, method, nullsafe and static call with callee, receiver, line and printed arguments, and every `new` |
| `ClassGraph` | the declaration reader: classes, interfaces and traits with parents, interfaces, traits, methods, properties and attributes |
| `CountedList` | the counted list of `04-guards.md` C5: a committed file, one key per line, `added()` for a key not listed, `stale()` for a listed key no longer found, `violations()` for both |

Reasoned, run once in the scratch Pest set-up: the guards of this folder were moved onto `PhpSource` by a codemod (31 files), and the run of the folder shows the same failing tests before and after, plus the five new tests of `CountedListTest.php`. `TypedReceivers.php` still builds its own traverser around a visitor class of its own.

## The guard library

Each of these is a complete worked example: a detector class, a thin test with failing examples (each with the words the message must contain), passing examples with the near misses, and one real-tree case. The blind sides of `04-guards.md` C1 ("The standing blind-side list") are the checklist for the next guard you copy from them.

| Guard | Detector, test | Teaches |
| --- | --- | --- |
| A queued class | `tests/Support/Architecture/UniqueJobGuard.php`, `tests/Unit/UniqueJobArchitectureTest.php`, `tests/Support/Architecture/ClassGraph.php` | the contract through a parent, a sub-interface, an alias, a group import and a fully qualified name; the key from the class, a parent or a trait (an interface that only declares the method does not count), a promoted or default-less `$uniqueId` property as the per-instance form and a property with a default as the per-class lock; an abstract base skipped; the lineage questions of every shape guard come from the one reader `ClassGraph`; the shape of every shape guard, with a case for a checkout under a dot directory |
| The paths the guides name | `tests/Support/Architecture/DocumentedPathGuard.php`, `tests/Unit/DocumentedPathArchitectureTest.php` | the document spellings, a sandbox tree for the examples, the folders of another repository (the kit's `tools`) as an argument |
| The pipeline and its scripts (Bitbucket form) | `tests/Support/Architecture/CiContractGuard.php` and `CiSafetyGuard.php` (two classes, each under three rule groups), `CiExamples.php`, `tests/Unit/CiContractArchitectureTest.php` | what runs is derived from `pipelines.*`, never from step names; exact script lines, comments stripped; the owner exceptions are constructor arguments; every mutation of the example is checked to exist, so an example cannot silently change nothing. Its real-tree case needs `bitbucket-pipelines.yml`, `scripts/checks.sh` and `scripts/kit-config.sh` in the repository: this extract has none (its pipeline is another host's), so copy the guard with the pipeline. The other hosts change only the reader of the triggers |
| The words the guides must keep | `tests/Support/Architecture/GuideRulesGuard.php`, `tests/Unit/GuideRulesArchitectureTest.php`, `docs/guards/unique-job.md` | one table, two directions: a rule without a row, a row without a rule, words the guide lost |
| Stored class names as registers | `tests/Support/Architecture/StoredNameRegisterGuard.php`, `tests/Unit/StoredNameRegisterArchitectureTest.php`, `database/stored-names/` | one sorted register file per kind, compared with the code in both directions (a class on no register, a line that names nothing, unsorted or doubled); a queued class found through inheritance and an aliased contract; a closure given to a queue (chain callback, `dispatch()`, `Queue::push()`) puts its defining class and every class of its body on a register, and a lock callback is the near miss; an alias list (old name, new name, one tab, sorted) that adds the other name of a pair to the expected register and demands a line for a stored class outside the new layout; the guide sentences the guard reads. It is the register form of `StoredClassNameGuard`, which keeps its snapshots in PHP arrays and its aliases in a provider |
| Classes closed by default | `tests/Support/Architecture/ClosedClassGuard.php`, `tests/Unit/ClosedClassArchitectureTest.php` | an open concrete class, a concrete class that another class extends, and a stale line of the counted list of open classes: three rules in one pass, each with a message that names the fix; abstract bases, interfaces, traits, enums and anonymous classes as near misses. Converging an existing tree is per class (a double of the class stops, or a concrete parent becomes abstract or its children are folded in first: `05-program.md` D8), and the real-tree case runs with an empty list |
| The guard folder itself | `tests/Support/Architecture/GuardShapeGuard.php`, `tests/Support/Architecture/PestExampleReader.php`, `tests/Unit/GuardShapeArchitectureTest.php` with `tests/Support/Unit/GuardShapeArchitectureHelpers.php` | a guard over the guards: no detector holds a literal path, every `<Subject>Guard` is named by a guard test, and every guard test has failing examples (a message matcher, a count, an exact non-empty result), passing examples (an empty result, built over a temporary root) and one real-tree case (an `it` with no dataset that builds its root from `dirname(__DIR__, n)`, calls `violations` or `findings` and asserts an empty result), in the group `arch`; the examples build whole trees in a sandbox, a dot-prefixed one included |
| Limits the guide states | `tests/Support/Architecture/MethodSizeGuard.php`, `tests/Unit/MethodSizeArchitectureTest.php` | the numbers come from one sentence of the guide, so a guide that lost the sentence fails the guard instead of the guard keeping a stale number; a stricter limit for a controller action, found by the folder name and not by a substring; what does not count (docblock, attributes, interface methods, closures outside a class). The older method-length test and its helper are deleted: this guard replaces them |
| The module folders from a guide table | `tests/Support/Architecture/ModuleLayoutGuard.php`, `tests/Unit/ModuleLayoutArchitectureTest.php` | the rules generated from the `Folder`, `Holds`, `Name` table of the guide and the module root named in it, with no folder literal in the detector; two findings (`place`, `name`) and messages that say which of the two; a guide without the table fails instead of passing empty; suffixes read from the Name column, a forbidden suffix, one subdomain folder |

The other guards in `tests/Support/Architecture/` are the same shape and carry their own examples; the ones that hold literal paths or whose tests are not the three-part shape (both listed above) are to be copied for their idea only. A receiver that a guard reads by type (`TypedReceivers.php`: an injected dispatcher, logger or connection, and the container string `app('events')`) is read only when it is declared in the file; an untyped receiver is a blind spot that the guide sentence of the rule names. The global helper `event()` is the analyser's rule (`phpstan.neon`), not `EventDispatchGuard`'s. The register, closed-class, method-size and module-layout guards were added from a later run of the kit and are rewritten onto this example domain. The tests of those four, run with Pest against a scratch copy, pass all their examples and the real-tree cases of three of them (`ClosedClassGuard`, `MethodSizeGuard`, `ModuleLayoutGuard`: the extract has the folders they read); the real-tree case of `StoredNameRegisterGuard` needs application classes that the extract does not include and fails without them (a missing folder is an error, not an empty pass). Reasoned, not run: the attribute spelling of queue limits in `QueuedClassLimitsGuard` (the attribute names of the installed framework release are to be verified in step 1).

## Rules whose guard is not in the reference project

In a new run each of these is a counter from step 1 and gets its guard by the kit's `04-guards.md` C7.

| Rule (catalog row) | To converge |
| --- | --- |
| "HTTP clients" | a macro per external system, then the banned-call rule |
| "Iterating many rows" | `lazyById` or the by-id batching reader of the framework, then the banned-call rule |
| "Search": a case-sensitive match with a variable pattern | a decision per site (does case matter), then through the helper |
| "Locks": the banned-call rule per layer | through the lock class, then the banned-call rule |
| "Scheduled work": the lock expires at most at the task's interval | a decision per task (the longest honest run against the interval) |
| "Middleware around the next handler": the call shape | the guard class on the call shape |
| A test named after a class references that class (a candidate of `04-guards.md` C7) | converging means reading each file: a decision list (`04-guards.md` C7) |

Where a run taught the kit a lesson, it is a line in `record-source-project.md` in the kit's root, with the place where it became an instruction (the later run's lessons too, as far as the kit has taken them up). A run does not need it.

## The example data is invented

Every list in this folder that looks like an inventory (route names and middleware, rate-limit categories and limiters, controller verbs, role and permission names, queue names, stored class names, aliases of moved classes, translation keys, table names, host names, numbers of days) is a short invented one for an ordinary web shop. It keeps the shape the guard needs and says nothing about a real application. The tests cannot be run from this folder: the application they run against is not included.
